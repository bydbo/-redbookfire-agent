# 可观测（对话全链路）

> S7.19–S7.22 落地。本文是**使用手册**：三层各自的职责、阶段口径、日志字段字典、调用链层级与排查路径。
> 契约的权威版本在《数据契约》§3.3 / §3.7、《API 契约》（SSE 事件与消息字段）与《配置契约》§3.12；
> 代码口径在 `core/progress.py` / `core/tracing.py` / `core/logging.py` 的模块 docstring——改了要一起改。

## 一、三层各有职责（别混用）

| 层 | 记什么 | 权威性 | 什么时候看 |
| --- | --- | --- | --- |
| 应用内事件 / 阶段快照 | 当前在做什么、走到哪一步、在哪个节点失败、第几次尝试 | 运行状态的**事实源**（落库，刷新可读） | 实时与回看 |
| 结构化日志 | 开始 / 结束 / 失败 / 重试与关键上下文（`turn_id` / `run_id`） | 单轮追查的第一入口 | 按 id grep |
| Langfuse 调用链 | span 父子层级、模型用量 / 成本 / 错误、各段耗时 | 事后分析 | 解释耗时与用量 |

云导出与页面显示有延迟，**不能当实时状态用**；反过来阶段快照不记用量——分工不重叠。

## 二、阶段口径（快照）

### 2.1 阶段键与标签

| 阶段键 | 标签 | 出现在哪 |
| --- | --- | --- |
| `supervisor` | 理解与决策 | 每次 supervisor 调用（多轮决策＝多次，`attempt` 递增） |
| `image_parse` | 解析图片 | 工具内：单图 / 多图合并解析（含跨轮回落） |
| `submit_analysis` | 提交分析 | 工具内：落库并投递 |
| `queue_wait` | 排队等待 | 由 `runs.status = queued` 推导（S7.20） |
| `material_sync` | 素材同步 | worker 前置：索引新鲜度同步 |
| `embedding_backfill` | 向量回填 | worker 前置：缺向量补齐 |
| `embedding_query` | 向量化查询 | 检索服务的查询 embedding（只有 span 与日志，不进快照——它发生在 worker 检索节点内部） |
| `clue` | 拆解 | 五节点之一（预置线索时短路 → `skipped`） |
| `retrieve` | 检索 | 五节点之一 |
| `gaps` | 缺口 | 五节点之一 |
| `draft` | 撰稿 | 五节点之一 |
| `report` | 报告 | 五节点之一 |
| `final_reply` | 整理回复 | **只出现在成功轮次**：正文已流式回吐，覆盖写库与终态整理（不代表生成耗时） |

「分析中」是工具的**临时进度文案**（带 done/total），**不映射阶段键**——否则轮询会把当前阶段来回切回"排队等待"。排队等待由 `runs.status = queued` 推导，worker 阶段由各自的 `runs.stage` 上报。

### 2.2 状态机与合并语义（`core/progress.py`）

- 状态：`running` / `succeeded` / `failed` / `skipped` / `interrupted`，后四者为终态。
- `skipped`：预置线索（S6.7）短路拆解，不冒充 `succeeded`。
- `interrupted`：进程中断 / 超时兜底——读会话时按 `[chat].turn_stale_seconds`（默认 300 秒）把过期 `running` 标 `interrupted`，**不会永远停在 running**。
- **终态映射（R2）**：失败轮次的消息 `failed`，快照里**真实失败阶段**终结为 `failed`（类别 `timeout` / `llm_error` …），**不出现 `final_reply`**；被取消的轮次消息 `interrupted`、当前阶段同步终结为 `interrupted`（类别 `cancelled`），取消继续沿控制流传播；成功轮次才有 `final_reply`——它覆盖**写库与终态整理**区间，**不代表回复生成耗时**（生成区间看对应 supervisor 尝试）。
- 合并规则：
  - 只记阶段切换，不逐 token、不逐轮询；
- **单调合并（R3 / OBS-12）**：迟到的 `begin` 不回退尝试号；同一执行的终态不因重复 `begin` 重开；只有更高的 `attempt`（重试）或新阶段才能启动新的运行；后端 `core/progress.py` 与前端 `stores/chat.ts` 的合并规则一致；
- **节点身份（R3 / OBS-05）**：`nodes` 元素可带可选 `run_id`——对话轮次里同轮多次分析（不同 run）的节点互不覆盖；缺身份时按旧口径合并（兼容旧快照）；
  - `nodes` 按 `(stage, attempt)` 去重、最多 30 条（超出丢最早的）；
  - 同一阶段重复 `running` 只刷新 `updated_at`，不重置计时；
  - 旧尝试（`attempt` 更小）的迟到更新**不覆盖**新状态（重试场景）；
  - 对话轮次切到新阶段时，上一个还在 `running` 的阶段自动收成 `succeeded`（阶段是顺序推进的）；
  - 错误只存**类别**（白名单），不存错误正文 / 提示词 / 用户原文 / 素材路径。

### 2.3 快照结构与存放

字段：`stage` `label` `status` `started_at` `updated_at` `attempt` `retries` `error_category`
`last_finished_stage` `run_id` `job_id` `nodes[]`；`nodes` 元素比顶层多 `latency_ms`、`ended_at`，可带可选 `run_id`（R3 身份）。

| 放哪 | 读出来给谁 | 迁移 |
| --- | --- | --- |
| `chat_messages.progress` | 会话详情（刷新后恢复阶段 / 失败说明） | `0007` |
| `runs.stage` | 任务详情 `stage` 与 `current_step`（不再恒为 `None`） | `0006` |
| `chat_messages.turn_id` / `trace_id` | 轮次关联与调用链回看（不加外键） | `0007` |

### 2.4 SSE 阶段事件（事件名不变、字段只增）

`stage` 事件：`stage` `label` `status` `attempt` `started_at` / `updated_at`，失败时带
`error_category`，收尾时带 `last_finished_stage` 与 `run_id`；所有非 `text_delta` 事件统一补
`turn_id` 与 `message_id`。`tool_progress` 事件带 `stage_key`（登记过的中文标签 → 阶段键），
`tool_started` / `tool_finished` 带 `call_id`、`attempt` 与耗时。
`error` 事件（R2）：带**真实失败阶段**（`stage`）、安全类别（`error_category`）与已捕获的
`trace_id`，与消息终态、落库快照三处一致；失败轮次**不会**再发虚构的 `final_reply/failed`。

## 三、日志字段字典

### 3.1 恒在三件套

| 字段 | 含义 | 无上下文时 |
| --- | --- | --- |
| `request_id` | 每请求一个 | 空串 |
| `run_id` | 一次分析运行 | 空串 |
| `turn_id` | 一轮对话（**独立业务头** `x-xhs-turn-id`，不混进 traceparent） | 空串 |

### 3.2 上下文绑定与复位

- `bind_run_id` / `bind_turn_id` 进 ContextVar，`reset_*` 复位（嵌套绑定逐个还原，单测钉住）。
- 对话轮次：`run_turn_task` 起始绑定，`finally` 复位；worker：`_run_job` 查到 run 后绑定，
  `finally` 复位。`execute` 层的重试 / 超时日志只有 `job_id`（绑定在任务体内，边界口径）。
- Celery 重试：`turn_id` 每次投递随消息头重发，重试不丢轮次关联。
- 显式 `extra={"turn_id": ...}` 优先于上下文（测试钉住）。

### 3.3 关键日志行（对照表）

| 日志 | 含义 |
| --- | --- |
| `对话轮次异常：<turn_id>`（exception） | 整轮失败；随后消息标 `failed`，快照标 `interrupted` |
| `调用追踪：turn <id> 的 trace <id>（<url>）` | 轮次收尾，按 id 去云上回放 |
| `调用追踪：run <id> 的 trace <id>（<url>）` | 运行收尾（S4.2 起） |
| `投递未带 traceparent：本次运行自开一条 trace（不伪装已串链）` | 缺失 carrier 的关联缺口，如实记录 |
| `调用追踪（Langfuse）未启用：<原因>` | 三件套不齐；每进程只警告一次，业务照常 |
| `Langfuse generation / span / turn 上报失败`、`flush 失败`（warning） | 旁路失败，绝不影响业务 |
| `W3C traceparent 注入失败（不影响分析）`（warning） | 传播失败按缺 carrier 处理 |
| `job <id> 已是终态 <status>，跳过（重复投递幂等）` | 重复投递 |
| `对话事件订阅中断：<turn_id>`（warning） | 订阅断了只停转发，后台轮次继续 |

级别口径：INFO = 正常生命周期；WARNING = 旁路组件失败（不影响业务）；`logger.exception` = 业务失败（整轮 / 整批）。

### 3.4 脱敏口径

- 默认不记提示词、用户原文、图片、素材路径、完整工具参数 / 返回值与敏感错误正文；
- 工具失败在追踪里只记 `tool_failed` 类别；
- 错误类别白名单：`llm_error` `embedding_error` `schema_error` `config_error` `timeout`
  `cancelled` `dependency_unavailable` `internal`（白名单外一律 `internal`）；
- **手写云字段只允许安全投影**（R1 / OBS-02）：`status_message` 一律经 `core/tracing.py::safe_error_text`
  ——白名单类别 + 固定安全词（`tool_failed`）之外的内容折成 `internal`；异常 / 结果错误一律用
  `safe_error_of(exc)` 投影，**不把 `str(exc)` 作为云字段**；
- **业务异常不交给 SDK 的 `__exit__`**：追踪门面手动进入 / 退出观测（退出永远传 `None`），
  SDK 底层的 OTel span 无从自动 `record_exception` 把正文与堆栈写进云端载荷；
- 自建 DB span 显式关闭 OTel 自动异常记录（`record_exception=False` / `set_status_on_exception=False`）
  ——驱动异常正文可能内嵌行值（如唯一键里的素材路径）；
- 旁路故障告警只带异常**类型名**，不带 `exc_info` / 正文；
- `LANGFUSE_CAPTURE_CONTENT=true` 才带提示词与正文（ADR 0005）；显式开启只放开 `input / output`，
  **不放开错误字段** ——任何开关下错误字段都只发安全类别。

## 四、调用链（Langfuse）

### 4.1 span 层级

```
chat.turn                         ← 一轮对话（挂 ASGI 请求 span 下；物理根是请求 span，不强行当根）
├─ tool.run_hotspot_analysis      ← 工具 span；提交分析时的 traceparent 取自"当前 span"
│  ├─ image_hotspot_clue[_multi]  ← 视觉调用的等价 generation（R3 / OBS-06：真实模型与
│  │                                `[vision].price_*` 单价；一次多图调用只记一个；缓存命中不记）
│  └─ db.submit_analysis          ← 投递发生在它内部（工具 span 的子 span），worker 挂它下面
│     ├─ worker.material_sync / worker.embedding_backfill（node span）
│     └─ analyze                  ← worker 进程接住 traceparent
│        ├─ node.clue / retrieve / gaps / draft / report
│        │  └─ hotspot_clue / material_select / copy_draft（generation，叶子用量）
│        └─ node.embedding_query  ← 查询 embedding（耗时 + 成功 / 失败状态）
└─ chat_supervisor（generation，每次决策一次）
```

- worker 的**父 span 是投递时刻的当前 span**——真实链路里投递在 `db.submit_analysis` 内执行，
  所以 worker 整棵子树挂在**工具 span 之下**（不是轮次根，也不是新开一条 trace）——
  真云回放与集成用例 `tests/integration/test_otel_chain.py` 都按"链上有工具 span"钉住；
- 缺失 / 无效 carrier：worker 自开一条 trace 并打日志，不伪装已串链；
- 一次多图合并调用只计一次 generation；每个 token、每次轮询不建 span、不在回调里 flush。
- **用量口径（R3 / OBS-07；R5 / E7OBS2-04 闭合语义）**：`usage_status` 四值——`actual`
  （上游给了 usage，**零值也是实际**）/ `estimated`（字符估算下界；分析 run 的汇总保守标
  `estimated`，不冒充供应商账单）/ `unknown`（调用发生或可能发生、无可靠用量）/ `cached`
  （本轮缓存命中，**无新增消费**，与"免费真实请求"区分）。该口径贯穿模型记录 → 服务结果
  （`ImageClueParse` / `ClueRecord`）→ 工具 payload（含部分成功后失败的已知消费）→
  轮级汇总（`finish_turn` 的 `usage_complete` / `usage_unknown_calls`）→ 刷新可读结果；
  `usage_complete` 的语义 = "本轮计费调用**均可解释**"（actual 与 estimated 都算可解释；
  是否全部为供应商实际用量是另一个维度）。查库 / 读运行不参与核算；**零成本也参与**
  （价格配零不掩盖请求），缺来源却有数字的记录按未知单列。
- **轮次时间窗**：进入 `run_turn` 到返回的起止时间随 `finish_turn` 元数据上云
  （`run_started_at` / `run_finished_at`）——与落库 `latency_ms` **同边界**，回放脚本优先
  用它比对；入口 span 含轮次准备与收尾，只在没有时间窗时作参考（边界差异如实写明）。

### 4.2 按什么查

- 消息 → `trace_id` / `trace_url`（`chat_messages.trace_id`；界面「查看调用链」，追踪关闭时整行不出现）；
- 日志 → `turn_id` / `run_id` / trace 链接；
- 任务详情 `GET /api/jobs/{id}` → `stage`（节点明细与 `current_step`）。

### 4.3 回放核对脚本

```powershell
uv run python scripts/check_trace_chain.py --turn-id <uuid> --expect tool,workers,vision --save runs/_smoke_e7_r6/trace_<id>.json
uv run python scripts/check_trace_chain.py --trace-id <id> --json
```

核对项（R6 / OBS-08 + R5 / E7OBS2-05 加固后）：入口 span 唯一（多个 `chat.turn` 判失败）→
引用完整（孤儿 parent 即失败）→ 工具 span 挂在轮次根下 → worker / 节点挂在工具 span 下 →
视觉 generation 按名匹配（`--expect vision` / `no-vision` 硬口径）→ 叶子 generation 有
**有效**用量与成本（字符串、bool、负数、NaN、Infinity、不支持形状一律判无效——不"转换失败
按 0"；显式零合法），或 metadata 如实标 `usage_status=unknown`（ERROR 级别不再自动等于未知；
**非法数字不因 unknown 声明被隐藏**）→ 账本核对：generation 求和（与叶子同一解析结果）
vs 落库 `prompt_tokens` / `completion_tokens` / `cost_cny`（token 精确、成本 ±0.01，
人民币按配置单价折算；失败轮 / `usage_unknown_calls>0` 判"待验证"）→ 耗时口径 = 优先
**轮次时间窗**（与落库同边界），没有才退回入口 span（边界不同、如实写明；并行 worker
拉宽的墙钟只作展示）vs 落库 `latency_ms`（容差默认 2000 ms）。`--expect
tool,vision,no-vision,workers` 声明本轮应有环节，缺失从"跳过"升级为"失败"。只读；
404 / 429 按 `--retries` 有界重试（退避 5s×n）。`--json` 的 stdout 是可直接解析的
**纯 JSON**（存证提示等人类说明走 stderr）。

退出码：`0` 全部通过（无失败、无待验证）；`1` 有失败；`2` 用法 / 配置错误；
`3` 仅待验证（unknown 用量 / 缺一边证据，需人工确认，不能视为完整通过）。

### 4.4 关闭追踪时

`NullTracer`：阶段、日志、界面照常；`trace_id` / `trace_url` 为空，界面不显示链接；
初始化 / 建 span / 上报 / 导出失败全部只记 warning，不阻断业务（集成用例 `test_tracing_disabled.py`）。

### 4.5 观测隔离（R1 / OBS-01）

所有观测（`run / hotspot / generation / turn / tool / node`）走同一条**安全观测上下文**：

- SDK **创建 / 进入 / 退出**观测失败：只记一条 warning（带异常类型名），业务块照常执行且
  **只执行一次**；没有真正建立的观测**跳过字段写回**（避免把更新误挂到外层 span）；
- SDK 清理失败**不覆盖**原业务异常、不吞取消；业务异常与取消全部原样传播；
- **失败兜底路径**（轮次异常后再建 `chat.turn` 发失败事件）即使遇到 SDK 整体故障也不崩：
  消息照常落库、`error` 事件照常广播（单测 `test_crash_path_survives_whole_sdk_failure`）。

## 五、排查手册

| 症状 | 先看 | 再查 | 常见原因 |
| --- | --- | --- | --- |
| 界面停在某阶段不动 | 消息 `progress`（阶段 + 已耗时） | 任务详情 `stage` / `current_step`；日志按 `turn_id` grep | worker 没消费 / 卡在素材同步 / 模型慢 |
| 轮次一直「正在回复」 | 最近活跃时间（快照 `updated_at`，心跳续约）超过 `turn_stale_seconds` 后刷新 | 日志 `对话轮次异常` | 活跃长轮次**不会**被误判（R3 / OBS-11：心跳租约）；心跳停止（执行者消失 / 进程重启）才收敛 |
| 轮次显示「中断 / 取消」 | 消息 `status=interrupted`、快照类别 `cancelled` | `error` 事件同类 | 真实取消（停机 / 任务取消）会有界收尾；进程强杀由陈旧对账兜底 |
| 分析重试中还是卡住 | 快照 `retries`（当前阶段的投递重试次数）+ `nodes` 里的失败尝试 | 任务详情 `stage.nodes` | 失败尝试保留在 `nodes`，重试成功不抹掉；worker 真实状态（failed / skipped）不再一律显示 running |
| 失败后阶段停在哪 | 快照 `stage` / `error_category` | `error` 事件的 `stage` 与实际失败位置一致 | 失败不写 `final_reply`；超时是 `failed`+`timeout`，取消才是 `interrupted` |
| 工具失败但整轮成功 | `tool_calls[n].status = failed` + `error` | Langfuse 的 `tool.*` span（只记 `tool_failed`） | 工具内部失败按业务回话，不炸整轮 |
| 分析失败 | `runs.stage.error_category` + `runs.error` | `stage.nodes` 看最后完成节点；日志按 `run_id` grep | 拆解 / 检索 / 模型报错；重试看 `attempt` 与 `retries` |
| 提示「耗时较长」 | 只是 > 60 秒的提示 | 阶段仍在推进即可 | 不要凭"没收到事件"认定失败 |
| 云端找不到 trace | 三件套是否齐 | 导出有延迟（脚本会提示），稍后重试 | 或该轮早于本轮次关联功能 |
| 成本对不上 | 叶子 generation 的 usage / cost | 父层只做汇总，不跨层相加；`usage_status=unknown` 是如实标记 | 失败 / usage 缺失允许"未知"，不填零冒充准确 |
| 阶段来回跳 | —— | 「分析中」不映射阶段键是**设计使然** | 排队等待由 `runs.status=queued` 推导 |
