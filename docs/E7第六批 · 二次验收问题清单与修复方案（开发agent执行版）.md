## 二、逐项修复规则与完成条件

本节包内短路径相对 `src/xhs_agent/`，前端、脚本及迁移相对工程根。入口和函数名按`11cdd0e`定位；实施时重新搜索，不依赖旧行号。

### A01 / P1：新会话误判与恢复信息丢失

**证据类型：真库已复现。**

**触发及实际结果：**创建空会话读到complete；追加首条用户消息后变为pending/legacy_unrecovered；真实`_prepare_context`返回confirmation_required。另一个已有complete恢复结构的会话新增事实后，再次变pending。

**根因与入口：**`services/chat.py::create_session`未持久化维护起点；`services/context_state.py::load`按“有用户消息且无recovery”推断旧会话；`_commit`重建snapshot时没有默认保留recovery。

**修复规则：**

1. 新建会话在创建事务中写入明确的维护起点和`recovery.status=complete`。保存可验证的历史覆盖信息；新空会话首轮不要求用户先恢复。
2. 统一状态序列化：delta、用户动作、话题切换、版本选择等提交，默认继承已保存的完整recovery，仅显式恢复动作允许改变它。坏字段不得无声丢弃后假定完整。
3. 旧数据有用户历史却无覆盖证据时保持partial/pending；不能按迁移时间将所有旧会话标complete。off/shadow期间未维护的历史在切入enforce前按覆盖证据核对，存在缺口则要求恢复。
4. 完成恢复时同事务更新recovery结构与旧`recovery_status`，保存缺口原因及用户核对证据。完整只表示已核对当前要求，不冒充原始历史全部可恢复。

**固定回归：**新建会话→首条“请开始分析夜跑”→装配；另预置complete→新增事实“不要感叹号”→retract/reset_topic/select逐项检查。

**完成条件：**首轮ready；后续普通变更不重置恢复进度；旧历史无证据时仍partial；重启/刷新后的读取一致。

### A02 / P1：审计事件约束错误与线索部分提交

**证据类型：真库已复现；其他竞争分支须补动态回归。**

**触发及实际结果：**complete_recovery/select_object写入未获数据库允许的事件，触发`ck_chat_context_events_event_type_allowed`。线索编辑抛IntegrityError后，head已是v2，state_version仍0，选择引用为空。

**根因与入口：**`db/models.py::ChatContextEvent`及0009后库约束没有允许新事件；`services/context_state.py::edit_clue_version/select_clue_version/perform_action`调用会内部commit的`artifact_versions.commit_success`，再独立提交选择与动作终态。

**修复规则：**

1. 数据契约、ORM和新增迁移同时允许`select_object`、`complete_recovery`，保留原合法事件及`(session_id,state_version)`唯一语义。迁移编号按实际head递增，不改0008/0009。
2. 事务由用例服务控制；底层版本/状态写入提供不自行commit的事务内路径。线索版本内容、head、选定引用、state_version、审计和动作成功结果一次提交。观测在业务事务之外尽力记录。
3. 付费操作仍先短事务认领，再在事务外调用模型，最后锁会话并重读head/state做CAS。成功提交与动作终态原子保存；失败只保存失败/中断及已知消费，不推进head。
4. 动作重放先于CAS；同ID不同请求体409，处理中真实返回202，失败重放保留原失败状态，不能改为200/noop。无操作保存幂等结果但不推进状态版本。
5. 选择对象本身要验证有效目标；确认未解析对象提案时同样消费请求中的object_ref并验证，不能仅“确认”就激活不明产物要求。

**固定回归：**合法完整clue v1→编辑v2；在版本写入后、状态写入前注入失败。另分别经HTTP执行complete_recovery、select_object和clue select。

**完成条件：**正常动作无约束错误；失败后内容/head/选择/状态均未部分推进；相同action_id不重复推进；两个数据库会话竞争只有一个提交成功。

### A03 / P1：恢复不能续页、空页失败与账目不完整

**证据类型：21条续页、空候选页真库已复现；同时间戳、认领/取消/账目为代码核查，须补复现。**

**触发及实际结果：**21条历史首请求扫描20条并成功，第二请求却返回recovery_running且仍20/21；只有寒暄、合法空增量的页面被no_change判为失败。

**根因与入口：**`services/context_state.py::_run_recovery_action`用running同时表示“未扫完”和“页在飞”；游标仅比较created_at；候选、游标、费用和动作分次提交；只取最后一条caller记录。

**修复规则：**

1. 使用现有枚举：pending表示有下一页且当前无在飞动作；running仅表示当前页已认领；扫完为awaiting_confirmation；失败/真实取消分别failed/interrupted；用户显式完成后complete。不以候选为空自动完成。
2. 首次recover锁定会话并持久化recovery_id、上界`(created_at,id)`、总量、当前action_id和页范围；同事务创建assistant账目消息及turn_id，提交后才调用模型。不伪造用户消息。
3. 每页最多20条完整用户消息，以`cursor < (created_at,id) <= cutoff`稳定扫描；同时间戳不漏项，后续新消息不扩大上界。装不下整页就停止并保留游标，不裁短原文换取放行。
4. 每页成功原子保存全部候选、原始来源、游标、覆盖量、账目和动作终态。合法空增量同样推进；有任一不可验证候选则整页不推进，已发生消费照记。
5. 候选来源逐条指向真实用户消息；跨页撤回/替换作用于累积候选，不能把已撤销历史要求重新提请激活。扫描期间候选不自动生效。
6. 后续页带同一recovery_id、新action_id和最新state_version；同一页只允许一个在飞认领。重放不收费；恢复id错误或CAS竞争409。进程遗留认领核实失活后标interrupted，只有显式新action_id+retry_of才重试，不承诺供应商恰好计费一次。
7. 本页使用全部caller.records合计tokens、已知成本、prompt版本；失败/异常/真实Task.cancel也尽力结账，未知单列。修复请求同样过A06预算及A10观测。
8. complete_recovery必须检查扫描状态、未解决候选/冲突及recovery_id。历史缺口/预算无法继续时，用户补全并明确核对才允许acknowledge_partial_history=true；保留缺口说明，不能程序自动代勾选。

**固定回归：**21条“限制内容01”至“限制内容21”，假模型每页返回该页真实候选；再造21条相同created_at、仅id不同的消息；再造1条寒暄返回空增量；增加扫描中取消、CAS竞争和跨页撤回样例。

**完成条件：**覆盖21/21且无漏扫/重复；空页进入awaiting_confirmation；刷新重放零新增调用；取消后不自动重发；确认全部候选后能完成且账目可核对。

| `POST {base}/artifacts/{version_id}/select` | 仅选当前会话成功clue；保留当前动作响应字段及context，成功200；404/409不以noop掩盖 |
| ObjectRef与约束快照 | 包含目标身份、真实来源、选定版本及适用事实；共享素材可引用，但run/产物须满足当前会话归属与热点位置校验 |
| 尝试/缓存事件 | logical_call_id、attempt、repair_of、cache_request_id、generation_id及共同过滤身份贯穿生命周期 |

恢复状态复用complete/pending/running/awaiting_confirmation/interrupted/failed；当前页认领身份及完整cursor/cutoff存于recovery持久结构，旧字段仅在status=complete时返回complete。普通状态变更必须保留新增结构。

错误沿用ErrorResponse，detail至少含reason、state_version、retryable，有head竞争时返回可用head_version_id。对象不存在/跨会话404，状态/head/动作竞争409，格式400/422，依赖不可用503。202必须是实际响应状态，不能只在注释或body写“202”。

### 3.2 事务与迁移边界

- 复用chat_context_actions：会话+action_id唯一，保存规范请求摘要及可重放的原操作结果/HTTP状态；旧客户端无action_id时仅保证CAS，不宣称客户端幂等。
- 普通不付费动作：认领、状态/选择/版本写入和动作终态在用例事务控制下完成。付费动作：已提交认领→事务外请求→最终CAS事务；真实取消、失活认领只标中断，不隐式重发。
- 业务审计只记录真实state_version推进；同动作开始/结束以action_id+phase关联，各次真实推进占新版本，不能违反唯一约束。无操作不写虚假状态审计。
- 新迁移在实施时head之后分配，扩展事件约束及必要持久字段/索引；不修改旧0009。upgrade/downgrade在临时库验证；回滚前检查新增事件/数据边界，不能把schema回退称作数据完整恢复。
- 已成功文案/线索保持不可变，继续兼容旧draft/revised包裹；旧pending缺预期head/state/source时不可补猜后继续，只能显式新尝试。回退关闭新行为但保留历史数据及已有冲突保护。
