## 3. E7OBS3-01：部分工具记录与失败路径

### 3.1 [P1] 取消生成的部分工具记录缺少 API 必填字段

**定位**：

- [chat_turns.py](../src/xhs_agent/services/chat_turns.py)：`_ledger_snapshot` 内 `total_for`，约 855–865 行。
- [api/models.py](../src/xhs_agent/api/models.py)：`ChatToolCall`，约 379 行。
- [api/routers/chat.py](../src/xhs_agent/api/routers/chat.py)：会话详情响应 `ChatSessionDetail`。

**复现结果**：图片解析成功并提交分析，等待中实际取消。内部账本能保留：

| 字段 | 已知结果 |
| --- | --- |
| cost_cny | 0.004 元：supervisor 0.001 + 图片 0.003 |
| prompt_tokens / completion_tokens | 510 / 25：supervisor 10/5 + 图片 500/20 |
| prompt_versions | 图片版本已保留 |
| run_id | 提交成功取得的合法 UUID 已保留 |
| 工具状态 | interrupted，后续分析用量标 unknown |

但生成的部分工具记录没有 `args`。`ChatToolCall.model_validate(...)` 抛 `ValidationError`，缺失位置为 `args`；最小 FastAPI 路由使用此响应模型返回该记录，HTTP 状态为 **500**。

**影响**：账目虽然能够写入 JSONB，但这不等于能够通过 API 读回。取消后的历史消息可能导致会话详情响应失败。记录还没有保留真实 call_id，后续关联也不完整。

**修复要求**：

1. 工具开始时保存真实调用身份、参数及工具尝试号，部分收尾由同一调用记录派生；不靠随意填空值通过校验。
2. 部分工具记录遵守现有工具记录契约，状态如实为 interrupted / failed，不伪造成功。
3. 核对失败 / 中断记录中的来源、版本、运行引用能否穿过 API 序列化；公开字段先与契约对齐。

**复验标准**：真实 workflow + 实际取消 + 临时 Postgres 落库 + 会话 GET 返回 200；读回金额、tokens、参数、call_id、版本及运行引用正确，并确认普通历史消息仍可读取。

### 3.2 [P2] 普通异常返回路径仍未使用新增组件账本

**定位**：[workflows/chat.py](../src/xhs_agent/workflows/chat.py) 的 `run_turn` 异常分支，约 510 行；[chat_turns.py](../src/xhs_agent/services/chat_turns.py) 的 `_finish` 失败分支。

**复现**：沿用上例，在图片成功、提交分析后，让等待函数抛普通 `RuntimeError`。

- `_ledger_snapshot` 可以得到 0.004 元、510/25 tokens 及图片部分记录。
- `run_turn` 返回的失败 `ChatTurn` 却只有 **0.001 元、10/5 tokens、tool_calls=[]**。
- `_finish` 使用该返回结果写回，新增组件中的已知图片消费未进入这条路径。

**根因**：普通异常在工作流内部被转成失败结果，没有抛到外层 `_finalize_turn`；内部异常分支仍只统计旧 `records/tool_calls`。

**修复要求**：成功、失败返回、外层异常和取消使用同一账目投影；复用组件的去重及最终汇总规则，避免修取消却漏普通异常。共享投影放在符合依赖方向的位置，不通过新增反向 import 解决。

**复验标准**：同一已消费场景分别注入普通异常和实际取消，已知账目一致；状态按失败 / 中断分别表达；正常成功路径没有重复计费。测试须覆盖返回结果、收尾和存储读回。

## 4. E7OBS3-02：阶段裁决仍未闭合

### 4.1 [P2] 持久化先推断成功，绕过来源顺序守卫

**定位**：[chat_turns.py](../src/xhs_agent/services/chat_turns.py) 的 `run_turn_task.persist`，约 548–563 行。

**真实轮次入口复现**：存储依赖替换为截获写回，阶段事件依次为：

```text
同 run、同 source：report / running / source_seq=5
随后收到迟到事件：draft / succeeded / source_seq=3
实际持久化：      draft / succeeded / source_seq=5
```

**根因**：在调用合并守卫前，persist 仍按“不同阶段且当前 running”先把 report 收为 succeeded。该次 `end` 只带 run_id，没有保留当前 source_id / stage_instance_id，改变来源身份后旧事件不再按原来源比较。

**修复要求**：

1. 先完成来源、阶段实例和顺序裁决，再允许任何阶段结束推断。
2. 迟到事件只补历史，不能触发“换阶段即成功”。不能证明前序成功的转换不补造成功。
3. 当前 stage、label、status、来源、实例、序号和起点作为一致投影更新，不混用旧字段。

**复验标准**：上述顺序经过真实轮次入口后，当前仍为 report/running/source_seq=5；draft 可以补历史节点；report 不出现伪造成功节点。还须覆盖无序号旧格式兼容边界。

### 4.2 [P2] 新阶段实例仍可能被同名历史节点阻断

**定位**：[core/progress.py](../src/xhs_agent/core/progress.py) 的 `begin`，约 258 行。

**纯函数复现**：同 run、同 source，draft 实例 first 成功 → report 开始 → 更高 source_seq 的 draft 实例 second 开始，attempt 均为 1。结果仍停留在 report/running，新 draft 未启动。

**根因**：前一处节点查询包含实例身份，但后续 `done = _find_node(...)` 又只传 stage / attempt / run_id，匹配到 first 的已完成节点后提前返回。

**修复要求**：所有阶段实例判断使用一致身份键，不能局部加字段后仍由旧查询兜底阻断。同源与跨源序号只在各自作用域比较；新来源不得继承旧来源的较大序号。

**复验标准**：同名实例 first/second、同轮多热点、同工具多次执行均能合法推进；first 的迟到 begin/end 又不能重开或接管 second。

### 4.3 [P2] 前端没有消费后端合并后的权威快照

**定位**：[frontend/src/stores/chat.ts](../frontend/src/stores/chat.ts) 的 `onStreamEvent`，约 342、358 行。

**静态确认**：后端已把合并后的 `progress` 和版本放进相关事件；前端 `stage` 仍直接使用原始 data，`tool_progress` 则重新构造一个对象，遗漏来源、实例、source_seq、progress_revision 和嵌套 progress。新增版本比较因此无法保护这条实际消费路径。

**影响**：即使后端合并修好，实时显示仍可能使用迟到原始事件；刷新读取数据库后又恢复另一份状态。

**修复要求**：前端当前阶段统一消费合并后快照，原始事件继续服务工具过程展示；版本比较限定于同一消息 / turn；旧事件兼容不能覆盖已知较新快照。核对旧的同阶段 / 跨 run 守卫不会再拒绝合法的新权威快照。

**复验标准**：同 run 迟到、同名新实例、跨 run 切换、SSE 与轮询交错得到相同状态；已有耗时、worker 尝试号、取消及历史失败回归通过，并补浏览器核对。

## 5. E7OBS3-03：来源误判

### 5.1 [P2] 合法附加用量字段使实际用量变成 unknown

**定位**：[tools/llm.py](../src/xhs_agent/tools/llm.py) 的 `resolve_usage`，约 135–148 行；视觉也复用此函数。

**离线输入与实际输出**：

```json
{"prompt_tokens":10,"completion_tokens":5,"total_tokens":15}
```

```text
实际：(10, 5, unknown)
预期：合法输入 / 输出为 actual；total_tokens 按支持协议校验。
```

**根因**：仅支持四个方向字段，其他键全部归为 unsupported。它混淆了“方向字段无效”和“响应带额外字段”，可使合法请求被批量标未知。

**修复要求**：在适配器中按实际供应商协议识别总量及附加明细；合法、已理解的附加字段不能使有效方向降为 unknown；非法方向、冲突别名和不一致总量仍严格处理。保留这次明确零值修复。

**复验标准**：文本与视觉适配器真实解析固定响应，覆盖 total_tokens、常见支持的明细、0/0、缺一侧、非法值和冲突值；不能只直接构造 LLMResult 测上层。

### 5.2 [P2] 缺来源组件仍被 actual 掩盖

**定位**：[chat_tools.py](../src/xhs_agent/services/chat_tools.py) 的 `_records_usage_status`，约 387 行。

**复现**：同一模型窗口含一条 actual 和一条无 usage_status 的模型记录，汇总仍为 actual。第二条数值可以全零，仍然是模型调用事实。

**修复要求**：模型记录缺来源时按 unknown 处理，再做 unknown > estimated > actual 的汇总；缓存和纯查库按调用类型区分，不能只看金额 / tokens。保存逐组件来源或等价事实，核对 API 序列化不会丢字段。

**复验标准**：actual + 缺来源、estimated + 缺来源、unknown 混合、cached 混合、纯查询和零价格真实请求全部有确定结果；usage_complete 不因估算被偷换成“全为实际用量”。

## 6. E7OBS3-04：成本解析与一致性

**定位**：[scripts/check_trace_chain.py](../scripts/check_trace_chain.py) 的 `probe_cost`，约 254–293 行。

### 6.1 [P2] 错误类型被备用总额隐藏

```json
{"costDetails":"bad","totalCost":0}
```

实际返回 valid、0；应返回 invalid。错误的非空权威成本结构没有被拒绝，直接进入备用总额分支。需区分 missing 与 invalid，非法数据不能通过 fallback 洗成合法。

### 6.2 [P2] 多来源总额冲突没有校验

```json
{"costDetails":{"total":0},"totalCost":3}
```

实际返回 valid、0；冲突被忽略。需明确受支持成本字段的来源与优先级；同时出现时核对一致性，不能任意挑一个值。合法额外维度先理解协议再支持，不随意相加。

### 6.3 [P2] 严格等号误拒浮点表示误差

```python
{"costDetails": {"input": 0.1, "output": 0.2, "total": 0.1 + 0.2}}
```

实际返回 invalid。转换成 Decimal 字符串后，分项合计为 0.3，总额为 0.30000000000000004，直接比较不相等。

需规定并测试来源精度或数值表示误差处理：可接受已定义的表示误差，不扩大原有轮次账本容差，也不能让 input=1/output=2/total=0 通过。保留 Decimal 数据库边界和整数 token 校验。

**三项共同复验标准**：叶子校验、求和、账本核对、树展示及 JSON CLI 使用同一解析结果；非法输入失败，缺证据待验证，合法精度边界通过。unknown 不隐藏非法值；退出码与 passed/pending 结论一致。
