## 2. 实施前冻结的最小语义

| 对象 | 语义与责任 |
| --- | --- |
| 工具调用 | 真实 call_id、tool、args、tool_attempt 在开始时登记，不能等工具结束才知道调用身份 |
| 子步骤消费 | 已完成组件登记已知 tokens / 成本 / 来源 / 版本，下一次可取消 await 前完成内存记录 |
| 未知部分 | 已发出或可能发出的调用没有可靠账目；保留已知部分并单列未知，不等同于实际零 |
| 工具终态 | 普通异常为 failed，实际取消为 interrupted；子步骤成功不代表外层工具成功 |
| 账目投影 | 同一组件集合和替代关系只能得到一份已知总额，各条收尾路径共享 |
| 阶段身份 | source、stage_instance、attempt 分层；同 stage 名称不证明是同一个执行实例 |
| 来源序号 | 只在同一来源 / 执行代次比较；来源切换不取不同来源序号的 max |
| 展示版本 | progress_revision 属于同一消息 / turn 的已接受快照，与 worker 来源序号分开 |
| 用量来源 | actual / estimated / unknown / cached 按调用事实汇总，不按数值是否非零判断 |
| 成本解析 | 有效 / 缺证据 / 无效三态；错误字段不能被备用字段隐藏 |

现有 JSONB 能表达时不增加表或列；确需 schema 变更时再论证、分配 Alembic head 并验证升级 / 回滚边界。私有内部记录无需全部暴露为 API 字段。

## 4. E7OBS4-02：统一所有收尾路径的账目投影

### 4.1 问题与推荐设计

普通 RuntimeError 被 `run_turn` 转成失败 ChatTurn，其分支仍只统计旧 records/tool_calls；新增 components 在外层取消收尾可见，但在此路径未使用。

建议抽取**小型纯计算账目投影**，供工作流返回与轮次收尾共用。可置于 `core/` 中职责明确的内部模块，不依赖 services、workflows、数据库或 SDK；不从 workflow 反向 import `chat_turns.py`，不扩建通用记账框架。

投影输入使用现有轮次记录、调用元信息、组件和覆盖关系；输出至少包含工具记录、已知总额、输入 / 输出 tokens、版本、消息级 run_id，以及内部完整性 / 未知计数所需事实。

### 4.2 记账与替代规则

1. 模型记录、工具组件分别有稳定唯一键，重复登记做幂等合并。
2. 图片、拆解等子调用完成后同步登记；分析提交成功立即登记运行引用，该引用本身不是额外费用。
3. 每个工具的最终 aggregate 明确覆盖哪些组件。对已覆盖组件只取 aggregate；对未覆盖组件继续取已知部分。不得把二者全部累加，也不得用 max(金额) 代替覆盖关系。
4. 无检查点的兼容 runner 仍可使用完成后的工具记录作为唯一账目来源。部分工具有组件、其他工具没有时也不能漏掉后者；不能只依赖 zip 长度碰巧一致。
5. cached 的本轮消费为零，不从缓存对象复用历史成本；零价真实请求保留 actual / estimated 等调用事实。
6. 来源及未知调用按组件事实计数。已有 unknown 组件和外层异常不能重复代表同一未知请求；非模型的参数错误不能自动被记成一个已发生的模型调用。
7. 版本先保留 supervisor 自身，再合并工具已完成步骤版本；消息级单一 run_id 沿用确定规则，各工具仍保存自己的运行引用。
8. 投影为纯函数，不修改输入账本，不请求模型、不读数据库，不对未知历史补数。

### 4.3 接入四条终止路径

| 路径 | 接入要求 |
| --- | --- |
| 正常完成 | ChatTurn 从统一投影取账目；工具最终结果覆盖组件后只计一次 |
| 工作流内部异常返回 failed | 返回前投影 components，不能仅 sum(records + tool_calls) |
| 外层异常 | `_finalize_turn` 使用同一投影，并把活动工具收成 failed |
| 实际取消 | `_finalize_turn` 使用同一投影，活动工具 interrupted，有界写回后重抛取消 |

`_finish`、消息字段与 `finish_turn` trace 摘要使用同一份投影结果，避免消息金额与追踪摘要分别计算。取消资源 / 日志上下文仍须复位；再次取消、数据库不可用明确尽力边界，不保证强杀可恢复未落库内存。

### 4.4 固定验收样本

supervisor：0.001 元、10/5 tokens；图片：0.003 元、500/20 tokens；随后分析已提交，worker 用量未知。

已知合计必须为 **0.004 元、510/25 tokens**，图片版本及合法 run_id 保留。普通异常与取消仅改变对应终态，不能改变已知消费。

| 编号 | 场景 | 断言重点 |
| --- | --- | --- |
| B1 | 固定样本普通异常 | ChatTurn、写库读回、API、trace 已知账目一致 |
| B2 | 固定样本取消 | 同上；取消继续传播，工具 interrupted |
| B3 | 检查点重复后成功 | 与原正常成功账目一致，组件与 aggregate 不双计 |
| B4 | 一个工具有组件、另一个无组件 | 两者均计入，各自一次 |
| B5 | 缓存后异常 / 取消 | 不重计历史费用；保留本轮新运行引用 |
| B6 | 提交前失败、非计费校验失败 | 不虚构 run_id 或模型未知调用 |
| B7 | 二次取消、收尾写库失败 | 有界退出、诊断准确，不宣称全部保存 |

## 5. E7OBS4-03：先裁决事件，再更新阶段状态

### 5.1 修复入口

[core/progress.py](../src/xhs_agent/core/progress.py) 的 begin/end/apply、节点身份匹配；[chat_turns.py](../src/xhs_agent/services/chat_turns.py) 的 persist；[runs.py](../src/xhs_agent/services/runs.py) 的 set_run_stage；[worker 入口](../src/xhs_agent/tasks/analysis.py) 与 [分析工作流](../src/xhs_agent/workflows/analysis.py) 的来源生成。

现有纯函数低序号守卫不能抵消 persist 事先修改状态。节点查询局部使用新实例身份、局部仍使用旧三元组，也会阻止合法的新热点 / 阶段实例。

### 5.2 合并流程

推荐把合并分成“纯裁决”和“应用事实”两步；内部返回裁决类别与变化标记即可，无需把每次裁决都做成新 SSE 类型。

```text
接收来源事件
  → 校验活动执行、来源、阶段实例、尝试及次序
  → 裁决：推进当前 / 更新当前 / 仅补历史 / 重复 / 冲突或无法归属
  → 按裁决合并快照与历史节点
  → 若语义变化，递增本消息 revision 并持久化
  → 对外发送合并后的快照
```

**禁止先自动结束旧阶段，再调用守卫判断新事件。**

### 5.3 具体修改步骤

1. 删除 persist 现有“不同阶段 + 当前 running + run 不冲突即 succeeded”的前置推断。前序完成优先由源端明确终态表达；有明确因果保证的局部转换才允许在裁决后推断。
2. 没有可靠终态的略过阶段保持未知 / 未结束事实，不用清空 running 节点或伪造 succeeded 让快照显得完整。需要收敛时使用真实失败 / 中断语义。
3. 所有 `_find_node`、`_node_matches`、同执行比较和幂等判断使用统一实例键；已知新格式至少区分 run/source、stage_instance、attempt。stage 相同不代表实例相同。
4. 同实例重复 begin 不重置计时，已终结实例不重开；同状态终态可补可信耗时；冲突终态保留首个并记录安全诊断。
5. 不同实例拥有自己的 attempt 起点；旧实例 attempt 较高不能阻止新实例 attempt=1。不要把“热点发生次数”和“同实例重试”继续混用。
6. 同源较旧事件只能补对应历史节点，不改变当前任何身份、状态、label、起点、错误类别、source_seq 或 last_finished_stage。
7. 来源切换由编排层明确绑定新工具 / worker 代次；不能将任意不同 source 的 running 都当作合法接管，也不能一律拒绝不同 run 的可信新终态。
8. 新来源的 source_seq 取新来源序号，不使用跨来源 max。消息级 revision 可继续递增，二者不可混为一项。
9. 历史节点新增 / 耗时补报属于可见语义变化，可推进消息 revision；纯重复轮询和心跳不推进 revision、不逐轮询写库。
10. `_terminal_snapshot` 及 final_reply 等收尾入口也保留正确来源和实例身份；不能在取消时因为漏传字段把来源退回 run_id。

### 5.4 生产端与存储一致性

- 统一同一 worker 执行代次的来源与序号生成策略，检查索引阶段和主分析阶段的来源切换；不要在不同生产器重置序号后靠消费者取 max 修补。
- worker 重试使用可区分的执行代次，并在阶段写入时验证当前有效执行；旧执行迟到不能获得更大序号后覆盖新执行。
- 源快照及其 source_seq 在同次受保护更新中保存。依实际并发模型采用行锁或条件更新；不能仅 SELECT 后内存加一、无条件提交，就宣称支持多 producer 并发。
- 没有源序号的旧格式只能按明确兼容规则处理；不能在轮询接收端重新编号后声称已恢复来源次序。
- normalize、节点序列化、`_stage_update`、去重 marker、workflow、on_event 保留新语义。marker 包含影响阶段事实的来源 / 实例 / 序号变更，同时保持已通过的终态耗时修订传递。
- 心跳仍只原子续约活动时间，陈旧对账仍检查 running 与活动时间；不借本轮合并改造撤销已通过的 CAS 保护。

这些是使现有字段可信的有限改动，不要求构建完整事件历史、通用锁服务或工作流重放系统。

| C5 | 新 source 从 seq=1 开始，旧 source 曾到 100 | 新快照 seq=1；该 source 的后续 seq=2 能正常推进 |
| C6 | worker 新代次开始后旧 producer 写入 | 旧执行被拒绝或仅作为历史，不覆盖新执行 |
| C7 | 只收到可信新执行终态 | 经活动来源绑定可投影，不因缺 begin 一律忽略 |

## 6. E7OBS4-04：前端统一消费权威快照

### 6.1 具体步骤

1. 后端 stage、tool_progress、需要更新阶段的 tool_finished，以及最终成功 / 失败 / 取消事件，按既有事件兼容要求附带合并后的 progress。最终路径不能漏出一条只携带原始阶段的新事件。
2. progress 中包含该消息的 revision、来源、实例、状态、label、attempt、起点及历史节点；事件信封明确 message_id / turn_id。消息轮询恢复使用相同结构。
3. `onStreamEvent` 取得权威 progress 后只应用一次；原始 stage_key、中文 stage、done/total 继续用于工具过程，不能再独立覆盖当前阶段。
4. 拆开“新格式权威快照投影”和“旧格式兼容合并”。权威快照由后端裁决，前端不能再用旧的“不同 run 终态一律拒绝”或“同 stage 同 attempt 终态不改”挡住更高 revision 的合法快照。
5. revision 比较范围为 `(message_id, turn_id)`。切会话、新消息、新轮次重置状态；不同消息不能比较 revision 大小。
6. 同范围较旧 revision 忽略；相同 revision 视为幂等。较新 revision 完整投影允许换 run、换实例及较低 attempt；起点来自快照，不凭每次事件到达时间重置。
7. 已有明确 revision 时，无 revision 的旧事件不能覆盖；旧格式初始化与局部兼容须有测试。刷新完整快照不重复执行一次原始阶段合并。
8. `turn_started` 引发的异步刷新、SSE 更新和轮询可能交错：旧请求返回前验证当前会话 / 消息范围，不能让旧会话响应覆盖新会话。保持 SSE 断线只停止转发、后台继续执行。
9. 只有当前阶段 running 才启用计时；中断 / 失败 / 成功时停止。工具步骤列表与当前阶段更新分开，避免重复添加步骤。
10. 更新 OpenAPI 描述、模型及生成类型，不手写并行 API 类型；对全部事件入口和刷新入口检查字段确实被使用。

### 6.2 必要回归

| 编号 | 场景 | 断言 |

| D1 | 原始事件是旧 draft，嵌套 progress 是当前 report | 展示 report，不先闪回 draft |
| D2 | 较新 revision 的新实例、同 stage、attempt=1 | 合法接受，旧终态守卫不误拦 |
| D3 | 同消息乱序 revision、同 revision 重复 | 不回退、不重置起点、不重开计时 |
| D4 | 新消息 revision 较低、切会话后旧请求返回 | 以当前消息 / 会话为准，不跨范围比较 |

## 7. E7OBS4-05：正确解析供应商用量与汇总来源

### 7.1 适配器修改

## 8. E7OBS4-06：严格成本解析及有限精度处理

### 8.1 同时检查所有受支持候选字段

在 [check_trace_chain.py](../scripts/check_trace_chain.py) 的 probe_cost 中拆成“按形状解析候选”和“统一候选一致性校验”，不要读到首个合法字段就返回。

| 输入情况 | 解析要求 |
| --- | --- |
| 字段完全缺失、协议允许的 null / 空对象 | missing，可继续评估其他候选 |
| 非空错误类型，如 costDetails 为字符串 / 数组 | invalid，不因 totalCost 合法而恢复通过 |
| total-only | 有限非负金额，有效候选 |
| input + output | 两侧均合法，形成合计候选 |
| input + output + total | 检查每个值并比较合计，非法分项不能被 total 掩盖 |
| 只给一个分项 | invalid，不补零 |
| 同时给 calculatedTotalCost / totalCost / costDetails | 校验所有受支持字段，比较一致性；非法或冲突不选一个掩盖 |
| 陌生额外成本维度 | 先按明确协议判支持 / 不支持，不能盲目相加或默认有效 |

总量比较之前先核对币种、计价来源及字段语义；明确不属于同口径的候选不能强行视为金额别名，应标不支持 / 待核实并解释。现有人民币配置折算口径保持一致。

### 8.2 数值与表示误差政策

1. 金额与整数 tokens 使用不同验证器；金额可小数，tokens 必须数学值为整数。bool、负值、非有限值、任意字符串继续拒绝。
2. Decimal 保留十进制值，检验有限性 / 符号 / 范围后再转用于展示；不先转 float 丢精度。分项和及最终转换也检查溢出，不只检查单个输入。
3. 精确 Decimal / 整数来源优先精确比较；float 来源需要单独处理二进制表示误差，不能对全部金额无条件 round 到四位再比较。
4. 推荐用标准库提供的浮点表示误差界（例如由原始 float 的 ULP 形成可说明的界）或有证据的来源固定精度，写为单个明确的比较辅助函数；实现时记录所选政策及边界样本。
5. `0.1 + 0.2` 的表示误差应被接受；input=1/output=2/total=0 必须拒绝；超出所选误差界的细小真实差异也必须拒绝，不能用大范围相对容差吞掉。
6. 数值表示误差与“消息账本相对 trace 的容差”是两回事；不得因本次修复扩大后者。只有来源明确舍入时才采用相应舍入政策，不自行假定供应商精度。
7. 极大 Decimal、整数和求和溢出安全返回 invalid / 不支持及安全原因，不抛未处理异常，不返回伪零。

### 8.3 统一所有核对入口

- 叶子检查、generation 求和、账本核对和树展示消费同一解析结果；invalid 优先于 unknown 的缺证据解释。
- missing 与 invalid 分开：已知部分可展示，整体未知仍待验证；非法结构则失败。
- 保持退出码 0=完整通过、1=核对失败、2=输入 / 环境执行错误、3=待验证；JSON stdout 为单个对象，说明走 stderr，保存文件与 stdout 结论一致。
- 维持同边界轮次耗时、Decimal 落库金额、父层与叶子不双计等已通过行为。

### 8.4 必要回归

| 编号 | 样本 | 期望 |
| --- | --- | --- |
| F1 | costDetails="bad"，totalCost=0 | invalid |
| F2 | costDetails.total=0，totalCost=3 | invalid，明确冲突 |
| F3 | 其他金额别名非法但一项合法 | invalid，不被 fallback 隐藏 |
| F4 | float 0.1、0.2、total=0.1+0.2 | 按表示误差政策合法 |
| F5 | Decimal 精确值、超出误差界差异、大额实质差异 | 精确一致才通过，政策之外拒绝 |
| F6 | total 合法但分项负数 / NaN / bool | invalid |
