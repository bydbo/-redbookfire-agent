## 1. 目标、现状与决策基线

### 1.1 本批交付目标

让执行当前任务所需的**有效约束、目标对象、产物基础版本及来源证据**能够跨轮次、刷新和进程重启正确恢复，并在每次请求前检查预算。对图片结果复用及供应商缓存分项提供能够复算的事实记录。

本批保留以下已确认取舍：

1. 用户明确表达、作用域清楚且有原文证据的目标与约束自动生效；模型推断、含糊指代和替换意图不明确的冲突进入待确认。

3. 缓存隔离、复用正确性和统计正确性为硬门槛；命中率、节省金额与提速按实测报告，允许零收益或负收益。
4. 一名实施者按依赖串行推进，不假设通过多代理并行缩短工期。
5. 第五批第四份修复方案的独立验收是本批集成验收前置；可先做契约、复现与隔离开发。

## 3. 上下文可靠性的判定与失败策略

### 3.1 八项执行不变量

| 维度 | 必须满足的条件 | 验证责任 |
| --- | --- | --- |
| 作用域 | 当前会话、当前话题及目标对象一致 | 服务端归属和 scope 校验 |
| 来源 | 生效事实来自用户原文或明确确认 | 来源消息/操作与证据校验 |
| 有效性 | 应保留限制全部装入，撤回或替换限制不继续生效 | 状态与装配清单对照 |
| 引用 | run、热点、素材及基础版本实际属于目标对象 | 服务端解析，不能只信模型参数 |
| 时效 | 使用当前状态，过期生成不能覆盖新 head | 状态版本与产物 head 条件提交 |
| 结构 | 无孤立工具结果，不拆散必要往返 | 消息组结构验证 |
| 预算 | 必需输入、输出预留与安全余量可同时容纳 | 每次实际模型请求前检查 |
| 可解释失败 | 无法恢复时明确确认、停止或重试 | 稳定失败分类与可操作提示 |

验收分两层：**装配可靠性**检查代码是否交付了正确内容；**执行可靠性**检查真实模型及工具是否遵守。装入 prompt 不等于必然遵守，模型失败也不能掩盖装配遗漏。

### 3.2 失败分类与默认动作

| 分类 | 示例 | 默认动作 |
| --- | --- | --- |
| `constraint_missing` | 长消息末尾限制未进入请求 | 停止依赖该上下文的生成，不静默继续 |
| `constraint_conflict` | 新要求与旧限制冲突但没有明确替换意图 | 保存待确认提案，确认前不执行受影响任务 |
| `unsupported_inference` | 从素材或 OCR 推测用户偏好 | 不激活；必要时转待确认 |
| `scope_mismatch` | 引用另一会话或旧话题对象 | 拒绝引用，重新选择 |
| `artifact_version_mismatch` | “再短一点”指向错误基础稿 | 阻止提交，展示实际对象及基础版本 |
| `state_version_conflict` | 生成时状态已改变 | 不覆盖新状态或产物 head，保留已发生消费 |
| `history_group_broken` | 有 tool result 无对应调用 | 重组；无法恢复则停止 |
| `required_context_overflow` | 问题、有效状态及基础稿不能同时装入 | 不发出模型请求，提示缩小范围 |
| `evidence_unavailable` | 原消息、附件或目标对象已删除 | 标未知/恢复不完整，请用户补充 |
| `cache_stale_or_invalid` | 内容、顺序、版本或归属不符 | 禁止复用，按策略重新解析并记录原因 |
| `measurement_incomplete` | 缺最终 usage 或尝试结束事件 | 保留业务及已知消费，指标标不完整 |

允许一项任务有多个标签。总体失败分布按最早阻断业务的原因记主因，其余记次因，不能重复扩大总体失败分母。

## 4. 会话状态：来源、作用域、事务与恢复

### 4.1 建议领域结构

以下字段在 P0 入契约后才可实现：

| 对象 | 最小字段与语义 |
| --- | --- |
| 会话快照 | `state_version`、`topic_id`、`facts`、`object_refs`、`recovery_status`、`artifact_heads` |
| 事实 | `fact_id`、`kind`、`value`、`scope`、`scope_id`、`status`、`source_ref`、`evidence`、`created_version`、`replaces` |
| 来源 | 用户消息 ID 或用户操作 ID；不能只保留模型生成的一句解释 |
| 对象引用 | run、热点位置、素材、产物版本；保存验证结果与对象标识 |
| 审计事件 | 会话、状态版本、来源、动作、原因、增量、时间；与快照同事务 |

事实状态使用 `active / pending_confirmation / superseded / retracted`。作用域使用：

- `session`：用户明确说明整个会话或后续均适用。
- `topic`：默认作用域，绑定当前任务话题。
- `artifact`：只适用于明确产物对象；未解析对象时不得激活。

新话题归档旧话题有效项，保留历史；会话级限制继续生效。含糊的“换一个”“照刚才的”不能自动清空状态或切换对象。

### 4.2 每轮处理步骤

1. API 保存完整用户消息并取得真实消息 ID，将 ID 与本轮原文传至轮次入口；读取当前快照和版本。
2. 历史裁剪前调用独立 `context_extract` prompt，输入本轮原文、现有状态及已验证引用，输出有限类型的状态增量。
3. 抽取默认输出上限 2048 tokens；仅对已核实支持的供应商关闭推理模式。最多一次结构修复，修复也预算检查和计费。
4. 服务端验证证据是原消息中的真实片段、操作类型合法、引用属于本会话。证据匹配只是必要条件，不能据此声称模型语义判断必然正确。
5. 明确新增、撤回和显式替换按规则应用；推断、歧义及替换意图不明的冲突存提案，不自动生效。
6. 以 `expected_state_version` 条件更新快照并写审计，事务成功后才供装配器使用；失败不留半个状态。
7. 若存在阻断当前任务的待确认项，返回确认提示；不能一边询问一边继续改稿或分析。
8. 装配有效状态和完整历史组后进入 supervisor；用户明确状态可以在后续工具失败时仍保持生效。

抽取或验证失败时本轮停止依赖新状态的任务，提供可重试原因。调用已发生的 tokens、成本、延迟及未知部分先写入现有消费检查点，再进入下一次可取消等待。

### 4.3 确认、修改与旧会话恢复

确认/拒绝针对具体 `fact_id` 或提案，带 `expected_state_version`，并生成用户操作来源。撤回保留历史；替换必须记录 `replaces`。确认动作也验证对象是否仍然存在，不能激活已删除 run 或附件。

旧会话只从完整、可验证的用户消息及明确操作恢复。先判定历史扫描是否完整；扫描上限导致前文缺失、来源已删除或内容不全时设置 `recovery_status=partial`，前端显示“历史状态未完整恢复”。不得从旧摘要猜回约束，也不得用“最近记录里没有”证明用户从未设过限制。

回退关闭新行为时保留状态与审计。已有未解决冲突的会话应提示处理，不能静默回到旧逻辑继续受影响改稿。

## 5. 数据设计、接口与事务边界

### 5.1 拟新增存储

优先 PostgreSQL，不引入独立记忆库或缓存服务。迁移编号按实施时 Alembic head 分配，本方案不预占编号。

| 存储对象 | 核心内容 | 约束与索引 |
| --- | --- | --- |
| 扩展 `chat_sessions` | 状态快照、非负版本、产物 head 引用 | 默认空值兼容旧会话；更新使用版本条件 |
| `chat_context_events` | 状态增量、提案、确认、撤回、来源审计 | 会话外键级联；会话+状态版本唯一；来源可追溯 |
| `chat_artifact_versions` | 文案/线索内容、对象键、成功版本、基础版本、请求键、状态、来源、prompt 与用量引用 | 会话+请求键唯一；同对象成功版本唯一；基础版本必须属于同会话同对象 |
| `chat_image_parse_cache` | 缓存键、完整身份元数据、成功解析、原轮次、创建/到期时间 | 会话+键唯一；到期索引；会话外键级联 |
| `context_observations` | 稳定事件 ID、类型、关联标识、结构化 payload、时间 | event_id 唯一；会话/时间索引；会话外键级联 |

文案版本表可保存 `pending / succeeded / failed / refused / interrupted` 的请求记录；只有成功记录分配成功版本号。是否拆分“请求认领表”和“不可变成功版本表”在 P0 根据现有 ORM 确认，不能用失败记录占用成功序号。

最小事务边界：状态快照与状态审计同事务；产物提交与 head 更新同事务；查询型观测旁路写入。缓存写失败可以返回本次有效解析，但必须标记缓存存储错误，不能宣称已持久复用。

### 5.2 拟新增/扩展接口

| 接口 | 主要行为 |
| --- | --- |
| `GET /api/chat/sessions/{session_id}/context` | 返回有效/待确认状态、版本、来源、恢复状态与产物 heads |
| `POST /api/chat/sessions/{session_id}/context/actions` | confirm/reject/retract/replace/reset_topic，携带预期状态版本 |
| `GET /api/chat/sessions/{session_id}/artifacts` | 按对象列出版本与基础版本，不返回其他会话版本 |
| `GET /api/chat/sessions/{session_id}/artifacts/{version_id}` | 获取指定不可变版本及来源 |
| 会话详情扩展 | 可选上下文摘要和产物引用；旧客户端可忽略 |
| 会话删除能力 | 若当前无接口，补受约束删除用例；状态、版本、缓存及观测级联 |
| `revise_draft` 参数/结果 | 增加可选基础版本引用；返回实际基础、新版本和对象标识 |

错误约定：404 表示会话或所属资源不存在；不合法证据/操作沿用统一请求错误语义；409 表示状态或产物版本冲突，响应包含当前版本和可重试提示。具体响应体先入 OpenAPI，不在前端手写另一套类型。

同一请求使用相同预期版本重复到达，不得再次推进状态；根据操作身份返回既有结果，或明确版本冲突。不同接口都需服务端校验资源归属，不依赖前端隐藏选项。

### 5.3 迁移与回退

迁移采用兼容性新增，先测试空库及含旧会话数据的 upgrade，再测试新写入和旧数据读回。downgrade 只在临时数据库验证；删除新表/列会丢新增历史，不能称为完整数据恢复。运行回退优先关闭功能保留存储，真实数据回滚另行备份与授权。

## 6. 文案与线索版本：保证连续承接

### 6.1 文案对象与修订流程

对象键由“会话 + run + 热点位置”组成，原运行初稿登记为该对象首个成功版本，原快照不变。默认改稿基础为该对象最近成功版本；用户明确回初稿或指定旧版时按引用读取真实内容，不能让 supervisor 在 500 字修改要求中转述上一版。

执行顺序：

1. 服务端解析对象，验证 run、热点及基础版本归属；无明确对象时先澄清。
2. 固定 `base_version_id`、生成前 `head_version_id` 和 `expected_state_version`。
3. 持久保存修订请求键及 pending 认领，提交后再发付费调用；键关联来源消息/工具调用和对象，不能只用修改文字去重。
4. 相同请求重放返回已成功结果或“处理中”，不重复发模型调用。失败后显式重试使用新尝试身份并关联原请求。
5. 用实际基础内容、有效约束、目标对象装配 `copy_revise`；执行完整预算检查。
6. 拒绝、失败或取消只更新请求终态并保留消费，不推进成功版本。
7. 成功后在短事务内锁定/条件更新对象 head，并校验状态版本仍符合预期；冲突不提交为最新成功版。
8. 分配下一个成功版本号，保存不可变内容、基础版本和来源，更新 head，提交后返回版本引用。

显式从旧版分支生成可以成为新的 head，但仍须校验生成期间 head 未被其他请求改变。“允许旧版基础”和“允许覆盖别人刚完成的新 head”是两种语义，不能混为一谈。

若认领后进程退出，pending 不自动重发供应商请求；显示状态不明并提供受控重试。该机制保护提交一致性，不承诺供应商恰好执行/计费一次，也不替代 E10 的通用恢复。

### 6.2 线索版本与原始图片解析分离

原始视觉解析是缓存对象，用户确认/编辑的线索是业务产物。编辑新增不可变 clue 版本并记录来源、基础及选定状态；后续工具优先读取明确选定的有效编辑版。命中旧视觉缓存不得覆盖编辑版，也不得因编辑而无故重跑视觉模型。

显式“重新识别图片”绕过原缓存并保存新解析；是否替换当前选定编辑版需要用户明确选择。原始解析更新和业务 head 改变分别记事件，避免把编辑统计为缓存失效。

## 7. 完整请求预算与成组裁剪

### 7.1 统一预算口径

每次范围内请求计算：

```text
input_est = system + tools + state + history + current
            + tool_arguments/results + protocol_overhead
effective_limit = min(application_limit, verified_model_context_window)
safety = max(512, ceil(input_est × 10%))
allow = input_est + actual_max_tokens + safety <= effective_limit
```

默认应用上限 65,536 tokens；模型窗口必须显式核实并配置，不能由模型名猜测。输出预留采用该次实际 `max_tokens`，包含供应商计入其中的推理量。历史 6000 tokens 仍只是子预算。

优先使用已验证 tokenizer；没有时选保守估算并记录版本，按实测记录估算与实际偏差。即使有安全余量也不声称准确保证模型窗口。未核实模型窗口时不能进入强制启用阶段；影子阶段只记录候选判断。

### 7.2 组装与裁剪规则

固定优先级：系统规则/工具定义 → 本轮完整问题、有效事实、对象和基础版 → 当前在飞工具往返 → 最近完整轮次 → 更早结构化摘要与引用。

- 先定义轮次边界，再保留预算内的连续后缀。遇到最近一个完整组超限就停止向前，不跳过它寻找更早短消息。
- 当前轮工具调用和对应结果成组校验，不能保留孤立 tool result 或缺结果的 assistant 调用。
- 工具 JSON 优先按字段和 top-k 缩减，保留对象 ID、版本、必要证据及可实际读取的引用；不能只写“可读取”却没有读取入口。
- 当前问题、有效约束和必需基础版不能盲截断。必要内容仍超限则停止，不发请求。
- 每次工具返回后、下一次 supervisor 调用前重新检查；状态抽取及其修复、会话改稿及其修复也纳入同一预算入口。
- 固定提示词和工具定义序列化顺序稳定，动态状态置于固定前缀之后；不能为了命中缓存保留过期事实。

预算事件保存各部分估算、输出预留、安全量、上限、估算器、裁剪组数、受保护引用和放行结果。实际 usage 可用时记录偏差；视觉估算未知单列。

## 8. 图片持久缓存：身份、生命周期与消费

### 8.1 键与读取流程

建议键组成：

```text
session_id
+ ordered_image_content_sha256[]
+ provider/base_endpoint_identity + model
+ parse_parameters_digest
+ prompt_content_digest + prompt_version
+ output_schema_version
```

上传时计算并保存摘要；旧附件首次使用时补算并明确记录耗时。摘要不能替代访问校验：先确认附件属于本会话、存在且内容身份有效，再查缓存。内容可被外部修改时必须有重新校验策略，不能仅信任旧上传摘要。

一次逻辑请求依次检查轮内及持久层，但只写一条主查询结果。命中后解析/校验存储结构，再交付消费者；持久化读取错误不能记成正常 miss。失败或部分解析不能写成成功缓存。

### 8.2 生命周期规则

| 情况 | 处理 |
| --- | --- |
| 同会话、内容/顺序/模型/prompt 等均一致 | 可复用；当前增量视觉调用、tokens 与费用为零 |
| 内容或顺序变化 | 新键；只有存在可证明旧条目时才归因变更 |
| 模型/参数/prompt/schema 改变 | 不复用不匹配条目，记录可证实原因 |
| 显式重解析 | bypass；成功建立新解析引用，保留旧业务版本 |
| 到期 | 创建后七天失效，命中不续期 |
| 附件删除或归属失效 | 立即禁止复用，清理相关无效条目 |
| 会话删除 | 状态、版本、缓存和观测级联 |
| 失败/取消 | 不写成功缓存，保留实际尝试消费及未知部分 |
| 同键并发首次 miss | 允许产生分别计费的真实调用；唯一约束只保存一个有效条目，不宣称恰好一次 |

确认/编辑的业务线索随会话保存，不受原始缓存七日 TTL 自动删除。每日维护命令清理失效缓存和超期观测；不新增常驻缓存服务。

## 9. 缓存指标、事件及成本延迟

### 9.1 应用缓存指标

定义 H=有效缓存结果已返回，M=正常未命中，E=读取/校验基础设施错误，B=显式策略绕过；C=有效逻辑图片解析消费请求总数，包含自动查询、绕过及失败。入口不合法且未受理的请求另计拒绝数，不混入 C。

U_cross=实际消费其他轮次已有结果且未新增视觉调用；命中但随后取消、未用于任务的请求不算消费。

| 指标 | 分子 / 分母 |
| --- | --- |
| 主自动命中率 | H / (H+M+E) |
| 辅助正常命中率 | H / (H+M) |
| 跨轮复用率 | U_cross / C |
| 命中消费率 | 被实际使用的缓存命中请求数 / H |
| 条目复用率 | 在统计创建队列中被再次消费的有效条目数 / 该队列创建有效条目数 |
| 绕过率 | B / C |
| 缓存错误率 | E / (H+M+E) |
| 失效原因分布 | 某原因失效事件数 / 全部失效事件数 |

条目复用率注明创建队列与观察截止日，不能把窗口外创建、窗口内命中的条目直接放进分子。事件缺失时报告覆盖率和未知，不能把不完整 H/M/E/B 硬凑成 C。零分母输出 N/A。

miss 原因和失效事件分开：首次/无条目、过期、不匹配、读取错误分别记录；到期、删除、版本变化、重解析替换是失效事件。多原因保存全部，主因优先级在 P0 冻结。没有旧条目证据时记首次或未知，供应商内部原因记 `provider_unknown`。

### 9.2 供应商前缀缓存指标

完整集合 K 要求输入总量、hit、miss 均为合法非负整数，且满足协议的一致性关系，例如 hit+miss=input。缺失、非法、冲突均不纳入 K；实际零仍是实际值。

| 指标 | 口径 |
| --- | --- |
| token 命中率 | K 中 sum(hit) / sum(input) |
| 支持请求完整覆盖率 | K 数 / 支持分项的实际传输请求数 |
| 总体可观测覆盖率 | K 数 / 全部实际传输请求数 |
| 请求命中率 | K 中 hit>0 的请求数 / K 数 |
| 未知分项比例 | 支持请求中缺失/非法/冲突数 / 支持请求数 |

重试每次传输单独记录，再归入逻辑调用。不能只保留最后成功响应。流式最终 usage 读取依供应商已核实能力配置，不能对所有兼容端点盲发额外参数；供应商字段名、模型窗口、推理关闭参数及价格均在实施时核实并保存来源日期。

### 9.3 成本和延迟

分项完整且存在对应价格时：

```text
estimated_cost = (hit × price_hit + miss × price_miss
                  + output × price_out) / 1,000,000
estimated_prefix_saving = hit × (price_miss - price_hit) / 1,000,000
```

每条记录注明币种、价格版本、actual/estimated/unknown 用量来源。分项价格或用量未知时前缀收益为未知，不按统一输入价格硬推折扣。已有成本估算与供应商账单也需区分。

应用缓存“没有新增视觉调用”可确定验证；“避免多少金额”属于反事实估计，使用相同模型和解析参数的可比调用并说明依据。不能把同一个未发生调用的全部成本及假设前缀折扣重复相加。

分别测量状态读取、状态抽取、预算装配、缓存查找/校验/摘要、单次尝试、含重试逻辑调用、整轮耗时。TTFT 仅首个非空正文增量；role、reasoning 和工具调用不计，无正文为 null。非流式响应只能记录正文可用延迟，不能冒充流式首 token。

应用缓存采用相同输入的禁用/有效复用配对实验；前缀采用同模型、参数及固定前缀重复请求，按实际分项分组。首次请求不自动叫冷样本，只有实际 hit=0 才作为观测冷样本。报告 P50/P95、绝对/相对差、样本数、失败数与网络环境；小样本或无冷样本明确限制。

### 9.4 采集事件与旁路规则

| 事件 | 触发点 | 必要内容 |
| --- | --- | --- |
| `context_state_decision` | 增量验证及事务结果确定 | 应用/待确认/拒绝、原因、状态版本、来源标识 |
| `context_assembled` | 每次请求前预算完成 | 部分估算、必需引用、裁剪、上限与判定 |
| `artifact_version_committed` | 版本事务提交后 | 对象、实际基础、新版本、状态版本 |
| `cache_lookup_finished` | 一次逻辑查询结束 | H/M/E/B、层级、原因、耗时、条目身份 |
| `artifact_consumed` | 既有结果被任务实际使用 | 来源/当前轮次、是否跨轮、是否新增调用 |
| `model_attempt_finished` | 每次实际传输结束 | 状态、方向用量、缓存分项、TTFT、耗时、来源 |

稳定 `event_id` 关联 session/turn/call/attempt、模型、prompt 和策略版本；重复投递按 ID 幂等。尝试开始也须留下可关联身份，缺结束事件可识别为 incomplete，不能只统计成功结束样本。

`context_observations` 为本地指标事实源；结构化日志和 Langfuse 用于关联诊断。只聚合叶子调用，不能把 turn/tool 汇总再加一次。业务状态审计不可丢；指标写入失败走旁路诊断，不阻断业务，报告注明可见证据缺口。云端仅必要元数据，不上传用户原文、图片、工具参数正文或素材路径。

观测明细默认30日保留；按日清理，不删除既有业务账目。拟提供报告脚本按日期、模型、prompt、缓存层和实验臂导出 JSON/Markdown，保存原始分子分母、过滤条件及未知数。

## 12. 回归、真实评测与证据产出

### 12.1 确定性及真实存储矩阵

| 场景 | 必须观察的结果 |
| --- | --- |
| 长消息末尾限制、超过20轮 | 标注有效事实全部装入，不依赖60字摘要 |
| 撤回、明确替换、歧义冲突、话题切换 | 旧项正确失效，session项保留，歧义不擅自激活 |
| 两会话相同文本/图片 | 状态、版本、缓存零串用 |
| 三次改稿、指定旧版、切换对象 | 实际基础与版本链正确，原运行快照不变 |
| 失败、拒绝、取消、重复、过期提交 | 成功版本不误推进，冲突不覆盖，消费不丢 |
| 超长问题、工具返回、不可压缩状态 | 每次检查，必要超限不发送 |
| 完整轮次、工具调用/结果 | 连续后缀，无孤立组 |
| 图片跨轮、刷新、进程重启 | 持久命中且新增视觉调用为0 |
| 内容/顺序/模型/参数/prompt/schema/TTL/删除 | 失效与新键符合约定，原因有证据 |
| 编辑线索后缓存命中/重解析 | 不覆盖选定编辑版，不无故重算 |
| usage完整/缺失/零/非法/冲突 | actual零保留，未知不填零，不伪造折扣 |
| 流式无最终usage、工具无正文、重试/取消 | TTFT/null与实际尝试匹配 |
| Langfuse关闭、指标写失败 | 业务不被旁路阻断，报告缺口可见 |
| 第五批保护回归 | 账目、快照、取消、心跳、真实会话GET保持正确 |

事务、持久化和冲突使用临时 Postgres/Redis，不只检查 mock 参数。必须通过真实 HTTP 会话 GET 及新接口读回状态、版本和来源；缓存通过刷新/新进程后的调用次数证明复用。

### 12.2 真实多轮协议

新增独立冻结版本，保留现有 `evals/manifest.json` 与冻结资产。12条模板按六类各两条：后置限制/长对话、撤回替换、连续改稿、话题对象切换、预算边界、单图/多图复用。

- 两条长对话各至少24轮，其余10条各至少6轮，每臂每次至少108轮。
- 基线与候选各重复三次：12×2×3=72条执行会话，至少648轮；两臂输入、素材快照、模型参数和评分规则相同。
- 基线使用冻结代码/配置，不把候选功能提前混入；候选调参使用独立开发样例。
- 字数、版本、引用、调用次数用确定性规则；语义约束用匿名人工核对，不引入未经校准的模型评委。
- 假工具+真模型与真实工具链分表。每条场景预先定义应成功、应澄清或应停止的终点，不能靠全拒绝获得高约束分。
- 另做至少30组前缀实验，每组至少3次请求，共至少90次，报告实际命中与覆盖。
- 首轮真实评测规划上限200元，达到或剩余额度不足以安全继续时停止，保留未完成项。实际/估算/未知消费分开；存在未知时不能声称精确守住账单上限。

保存完整执行清单和失败，不删除超时、服务错误、空输出。按会话报告原始分子/分母和区间估计，不把同一长会话几十轮当成独立样本放大把握度。保留不低于基线的判定和每轮0.25元既有成本门槛，超标需要解释与修复，不能悄悄放宽。

| 风险/假设 | 应对与停止条件 |
| --- | --- |

| 附件外部修改/路径迁移 | 内容身份与访问校验并用；说明摘要重新验证策略 |
| 模型别名/协议/价格变化 | 能力、参数、模型、prompt与价格版本留档，变化按身份失效 |
| 并发首miss或中断重试额外消费 | 报告实际尝试与未知；不声称分布式恰好一次 |
| 指标漏采/重试重复 | 稳定ID、尝试开始身份、缺结束标记、覆盖率及固定集复算 |
| 旧会话历史不完整 | partial提示，用户补充，不从摘要造事实 |
| 缓存无收益/小样本 | 保留零/负结论，不扩大共享范围人为提高命中 |

发布采用 shadow → 限定会话 → 默认新会话启用。扩大范围前核对硬门槛，出现跨会话泄漏、错误基础提交、静默丢有效约束或重复计费立即停止扩大启用范围。回退关闭新行为，保留审计、产物历史和原始运行快照；不通过删除历史实现回滚。
