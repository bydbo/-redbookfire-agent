# E3 Story 划分问题清单：分配问题与功能真空

> 生成背景：E3（编排与服务）已完成 S3.0（Prompt 契约与资产）、S3.1（LangGraph 状态图）、S3.9（Prompt 版本落库）共 6.5 人日，剩余 8 个 Story 共 11.5 人日；在 S3.2 开工前对 E3 整体 Story 划分做评审。
> 结论先行：**3 个分配问题（其中 S3.4 职责过载为核心问题）+ 2 个功能真空**。按对应调整建议执行后，E3 总量 13.5 → 约 15 人日。
> 本文档是评审意见，`backlog.md` 尚未按此修改。

## 一、Story 分配的三个问题

### 问题 1（核心）：S3.4 职责过载，结果落库仓储层无显式承接

S3.4「Celery worker 与任务状态回写」表面工作量是 2 人日，实际隐含 **5 项职责**：

1. Celery 接线与生命周期（软/硬超时）；
2. `runs.status` 状态机回写；
3. **结果持久化仓储层**——`runs` / `hotspots` / `run_hotspots` / `run_matches` 四表写入、`hotspots` 按原文去重复用（数据契约 §3.2「避免重复付费」的承诺）、`(run_id, position)` 与 `(run_hotspot_id, rank)` 幂等、`reasons` 非空约束在 Pydantic 与数据库两处生效；
4. 索引新鲜度检查 + 增量索引前置（S2.4 留下的触发路径尾巴）；
5. `prompt_versions` 与 LLM 统计（llm_calls / tokens / cost / latency）落库。

其中第 3 项是数据契约用一整节（§3.2–§3.5）定义的写入语义，**没有任何 Story 的验收标准提到它**，被折叠在「状态回写」四个字里。它是纯 service 层代码，本可以先于 worker 落地、并被 S3.3 的接口集成用例（analyze 落库路径）直接复用。2 人日塞不下这 5 项，是全 Epic 最可能超支的 Story。

### 问题 2：边界重叠与验收口径

| # | 位置 | 问题 |
| --- | --- | --- |
| 1 | S3.3 vs S3.7 | **「/api 前缀」验收重叠**：S3.3 标题即「五个接口实现（`/api` 前缀）」，S3.7 验收又含「`/api` 前缀生效」。前缀验收应归 S3.3；S3.7 只保留 dist 挂载 + history 回落 + `[frontend].serve` 开关 |
| 2 | S3.2 | **验收标准不是可观察结果**：「路由分层、依赖注入、统一错误响应中间件」是实现动作，不满足 AGENTS.md §10 的 DoD（「验收标准写的是可观察的结果」）。应改写为：「错误响应结构与 `openapi.yaml` 的 ErrorResponse 逐字段一致（集成用例断言）；`/api` 下任一路由异常时响应含 code / message / fix 三键与 `X-Request-ID`」 |
| 3 | S3.5 行后 | **格式 bug**：游离的「> 补充（E2 审查项 7）……」引用行夹在 markdown 表格两行之间，会切断表格渲染，应并入 S3.5 的验收单元格 |

### 问题 3：依赖关系

1. **S3.5 依赖写 S1.2 已过时**：httpx 替换的真实消费者是 E2 的 `services/retrieval`、`services/materials`（embedding 调用）与 S3.4 的 worker，依赖应改为 S2.5 / S2.6。
2. **S3.5 与 S3.4 的执行顺序未标注（关键）**：这是 E2 审查建议 1 的时序风险——`retrieve_candidates`（async 函数）内同步调用 `client.embed()`（urllib，最长 60s 超时 + 退避重试）。脚本场景无碍，**一旦接入 Celery worker 就是现实的事件循环阻塞**。S3.5 必须在 S3.4 之前完成（或同批），当前依赖列看不出来。S3.5 验收还应补「调用方接线：两个 service 的 embed 调用改为 await」——只换客户端不动调用方，阻塞问题原样保留。

## 二、两个功能真空

（对照 E3 目标「服务化与异步，端到端可演示」，其余范围确认无缺失：CORS 同源部署不需要、鉴权本地工具不需要、容器化已排 E4 S4.4。）

| # | 真空 | 证据 | 后果 |
| --- | --- | --- | --- |
| 1 | **文案可用率补测无 Story 承接** | backlog S2.8 行写「留到 E3 的 S3.6 之后补测」；prompt 契约 §六 写「待 E3 具备撰稿产出物后一并记录，但不作为回退依据」——S3.2–S3.10 没有任何一条验收包含它 | 产品方案 §10.2 六项指标到 E3 结束仍有一项空着，「评测维度齐全」的项目卖点打折 |
| 2 | **RunStore（文件）与 runs 表（DB）双轨运行记录无收敛决策** | S3.1 仍产出 `runs/<run_id>/state.json` + `trace.jsonl`（RunStore），E3 落库后 `runs` 表是权威状态源，两者关系从未决策 | E2 审查的「双索引」问题在运行记录上重现；E4 S4.1（structlog 按 run_id 贯穿日志）会直接撞上「哪个是权威源」的问题，届时再改成本更高 |

另有一个衔接缺口（严重性低于上述两项）：**preflight 接入 API 启动未写**。配置契约 §四明确「任一步失败即中止启动」，S3.8 验收只写了 CLI 的退出码 2/3，没有「接入 FastAPI lifespan（启动事件）」——不补的话契约与实现脱节，Walking Skeleton 的 `docker compose up` 场景下 preflight 形同虚设。
