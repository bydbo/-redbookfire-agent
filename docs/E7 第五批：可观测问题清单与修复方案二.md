## 4. 详细修复任务

### E7OBS2-01：失败消息缺少工具过程和运行引用

**定位**：[workflows/chat.py](../src/xhs_agent/workflows/chat.py) 的 run_turn、轮内 ledger；[chat_turns.py](../src/xhs_agent/services/chat_turns.py) 的 _finish/_finalize_turn；[services/chat.py](../src/xhs_agent/services/chat.py) 的 update_message。基线 _finish 失败分支约 547–566 行。

**确认缺陷**：工作流能够从账本构造含 tokens、成本、tool_calls、run_id 的失败 ChatTurn，但最终失败写回没有 tool_calls/run_id。本文整理时构造带合法运行 UUID 的失败结果并截获字段，再次确认缺失。仅在 ChatTurn 层测试通过不能证明数据库已保存。

**实施步骤**

1. 沿用成功字段语义，把已知 tool_calls、非空 run_id 与账目、prompt 版本、trace 一起写回失败消息。
2. 检查直接异常、取消、收尾写库异常是否绕过账目路径。稳定边界可得的已完成记录交给统一收尾，无法获知的部分明确 unknown。
3. 修复工具内部部分成功后失败的消费丢失：图片解析已成功而后续分析超时/失败，或拆解成功后检索失败。保留已知消费和运行引用，未知另记，不能仅在成功 ToolOutcome 返回时核算。
4. 防止工具汇总与内部 generation 双计；保持初稿快照和已有成功路径语义。

**必要回归**

- 模型成功 → 工具成功 → 第二次模型失败：通过真实存储读回工具状态、run_id、版本、成本和 tokens。
- 图片成功 → worker 超时/失败：视觉已知账目保留，后续未知单列。
- 已消费后实际取消、最终写库失败：说明哪些保存、哪些只能留旁路证据，不能宣称全部保存。
- 数据库存储用合法 UUID；不能只使用 r-1 这类假运行编号。

**完成标准**：刷新读回失败消息仍有已知工具和运行引用；测试贯穿“工作流 → 收尾 → 数据库”，无重复计费。

### E7OBS2-02：迟到结束事件回退阶段、混合身份

**定位**：[core/progress.py](../src/xhs_agent/core/progress.py) 的 begin/end/apply/_upsert_node；[chat_turns.py](../src/xhs_agent/services/chat_turns.py) 的 persist；[前端 store](../frontend/src/stores/chat.ts) 的 applyProgressLike。基线 end 约 195–242 行。

**确认缺陷**：begin 已挡住部分旧尝试，但 end 会把其他阶段终态直接推为当前。已复现 report/running/run-new 收到 draft/succeeded/run-old 后，顶层 stage 回到 draft，run_id 仍为 run-new，形成混合状态。前端守卫只比 stage/attempt，没有 run 身份，新 run 同名阶段也可能被上一 run 终态拦截，此场景需补专项复现。

**实施步骤**

1. 冻结执行身份和推进规则，分清 run/job、工具 call、热点执行、worker attempt；不能简单对全部业务硬排一个全局阶段顺序。
2. 分开“补历史事实”和“推进当前状态”。迟到结束可以补历史节点，但不能回退当前；同尝试终态不能重复重开。
3. 使用可信来源版本/序号或明确状态机。跨进程时间戳只辅助，不假设时钟严格有序。
4. 不同 run 的相同 stage/attempt 属于不同执行；顶层与节点身份一致。缺身份旧快照有明确兼容规则，不允许旧事件无条件覆盖明确身份的新执行。
5. 校准 persist 的“切阶段即自动成功”推断，迟到事件不能触发它；来源未证明的略过阶段不补造。
6. 同步后端持久化、前端实时合并、契约、API 模型和生成类型。

**必要回归**：report 收旧 draft 结束；同 stage 新 run 收旧 run 结束；新 run 尝试号较低；重复开始/终态、冲突终态、旧尝试迟到、新重试；同轮多个分析/热点/同名工具及跨会话；SSE 与刷新一致。

**完成标准**：不回退、不串身份、不丢历史失败；label、错误类别、起点不残留自另一阶段；对未知顺序如实表达，不伪造成功。

### E7OBS2-03：阶段去重键与通道身份不完整

**定位**：[chat_tools.py](../src/xhs_agent/services/chat_tools.py) 的 _stage_update/_update_marker/_wait_for_run；[workflows/chat.py](../src/xhs_agent/workflows/chat.py) 的工具 progress；[chat_turns.py](../src/xhs_agent/services/chat_turns.py) 的 on_event。

**证据边界**：不同 run/job 但其他字段相同的 marker 相等，函数层确认；单次正常轮询固定 job，因此属于防御性身份缺口，不能直接声称真实运行已换 job 丢事件。

**实施步骤**

1. 按 E7OBS2-02 的身份契约改 marker，至少区分来源 run/job；来源本应固定时同时校验一致性，变化需明确报告而非静默去重。
2. 比较有意义字段，明确终态耗时/来源序号更新；不把每次轮询时间戳作为变化，避免写放大。
3. 逐层核对 handler 闭包 → workflow → on_event → 持久化 → 前端。基线 workflow progress 构造 body 没有透传结构化 latency_ms，应补端到端检查，而非只修辅助函数。
4. tool_attempt 和 worker attempt 分层；tool_finished 不得用工具次数覆盖 worker 最后阶段的重试号和状态。
5. 保留终态快照返回前发送、skip 不虚构调用、重复轮询不追加节点的现有能力。

**必要回归**：身份不同 marker 不等；同来源同状态去重；终态耗时修正；同轮两个真实分析工具调用；worker 第 2 次尝试后 tool_finished；实际 handler 至消息快照端到端。

**完成标准**：任务详情、SSE、消息快照的来源、状态、尝试及可得耗时一致；来源异常如实记录，不冒充正常串链，不引入逐轮询写库。

### E7OBS2-04：用量来源和零成本语义未闭合

**定位**：[workflows/chat.py](../src/xhs_agent/workflows/chat.py) 的 _usage_accounting；[chat_tools.py](../src/xhs_agent/services/chat_tools.py) 的 ClueRecord、工具 payload、缓存；[image_clue.py](../src/xhs_agent/services/image_clue.py) 的 ImageClueParse；[tools/llm.py](../src/xhs_agent/tools/llm.py)；[tracing.py](../src/xhs_agent/core/tracing.py)。

**静态确认**：模型记录和视觉 generation 有 usage_status，但 ImageClueParse/ClueRecord、多数成功工具 payload 未完整传递来源。汇总用 cost>0 或非空来源判断有无调用，容易混淆免费真实请求、缓存和未知。明确 actual 零 tokens 也可能被误标 unknown。

| 场景 | 必须表达的事实 |
| --- | --- |
| 有供应商 usage 的真实请求 | actual，明确零值不能因 truthiness 被替换 |
| 缺 usage，只能估算 | estimated，说明估算范围和局限 |
| 请求发生或可能发生，无可靠 usage | unknown，已知部分仍保留 |
| 缓存命中/纯查询 | 本轮无新增模型消费，与免费真实请求区分 |
| 模型价格配置为零 | 仍为真实请求，不因零成本跳过完整性核算 |

**实施步骤**

1. 来源状态和必要调用计数贯穿模型、服务、工具、轮级汇总及刷新可读结果；公开或持久化字段先同步契约。
2. 不仅凭成本或 tokens 正负判断调用存在。混合来源保留分类计数或等价结构，不能让已知总额掩盖未知。
3. 明确 usage_complete 是“记录均可解释”还是“全部为供应商实际用量”，估算和完整性是不同维度。
4. 工具与内部叶子不双计，缓存本轮增量清零但不抹历史消费；与 E7OBS2-01 和脚本口径一致。

**必要回归**：actual 零值、零单价、estimated 图片、部分 usage 字段缺失、混合未知、无模型查询、缓存、失败前已消费；从服务结果测到消息/trace。

**完成标准**：零费用不掩盖请求，估算不冒充实际，未知不清零伪装完整；数据类型、响应和契约一致。

### E7OBS2-05：非法成本仍能通过回放核对

**定位**：[check_trace_chain.py](../scripts/check_trace_chain.py) 的 has_cost/generation_cost/usage_values_valid/_ledger_check/verify_trace/main；[脚本单测](../tests/unit/test_check_trace_chain.py)。

**已复现**：非空 costDetails 字典即被认为有成本；total=字符串 bad 时叶子检查仍为通过，求和转换失败返回 0。这是核对脚本误通过残留。

**实施步骤**

1. 统一解析成本：存在、类型合法、有限且非负才有效。拒绝 bool、负数、NaN、Infinity、任意字符串；数值字符串是否支持按真实协议明确，禁止转换失败默认 0。
2. 明确 total 与 input/output 分项支持形状及一致性。不支持的非空结构判无效或缺证据，显式 0 保持合法。
3. 用量也检查有限值及支持的整数方向字段，不缺字段后擅自按零核账。
4. 叶子与账本使用同一解析结果；无效数字不能因 unknown 声明被隐藏，错误定位保持安全。
5. 缺证据/失败/不适用与退出码一致，失败轮核对可验证已知部分，未知保留待验证；不扩大容差掩盖差异，成本说明人民币与配置估算来源。
6. 补耗时边界核验：入口 span 含准备与收尾，消息 latency 在 run_turn 内计算，换用入口 span 不自动等于同口径；统一边界或明确拆开比对。
7. 补 JSON CLI：--json 的 stdout 应直接可解析为一个 JSON；当前结论或 --save 提示会混入 stdout，说明移到 stderr 或结构化字段，退出码保持一致。

**必要回归**：非法字符串、bool、负数、非有限值、显式零、合法分项/总和、缺字段、未知混合、耗时边界；success/fail/pending 的 CLI 均可机器解析。使用假 API/脱敏 trace，不调用付费模型复现解析错误。

**完成标准**：非法成本不判有效，叶子判断与账本无矛盾，JSON 和退出码可靠，差异不靠放宽阈值消失。

### E7OBS2-06：心跳与陈旧对账的并发覆盖

**定位**：[chat_turns.py](../src/xhs_agent/services/chat_turns.py) 的 _heartbeat/persist/收尾；[services/chat.py](../src/xhs_agent/services/chat.py) 的 mark_stale_turns/update_message；[存储集成测试](../tests/integration/test_chat_storage.py)。

**静态竞态风险**：心跳先复制 holder，再用独立 session 回写整个 progress，可能覆盖主流程刚写的新阶段/终态。陈旧对账的 running 与活动时间条件只在 SELECT 判断，后续 ORM 更新未再次检查；可能选中后主流程成功，对账再改 interrupted。现有心跳测试没有覆盖交错，不能称线上已复现。

**实施步骤**

1. 先用门闩和真实数据库控制交错：心跳读旧 → 主流程写新 → 心跳提交；对账选中 → 主流程成功/续约 → 对账提交。
2. 心跳优先只原子续约活动时间，不写整个阶段快照。可选 JSON 局部更新或独立租约字段，选定后同步契约；只有新增列才加迁移。
3. 心跳写入检查消息仍 running、turn 身份一致；终态后禁止续约，必要时 CAS/版本保护。
4. 陈旧对账真正 UPDATE 时重新检查 status 和活动时间，按受影响行数认定结果，不用旧 ORM 对象覆盖新终态。
5. 明确心跳停止与收尾顺序，异常/取消也停止；单次故障不阻断业务，连续故障有安全诊断。
6. 覆盖无阶段初始化、长模型无阶段变化、旧快照、多 API 进程及执行者消失，不用当前进程内存作为全局生存证明。

**必要回归**：两种交错；终态后延迟心跳；旧执行迟到写；长轮次续约；心跳死亡过期；失败/取消停跳。使用临时 Postgres、可控时钟/门闩，不真实等数分钟。

**完成标准**：续约不修改阶段事实，对账不覆盖刚成功/刚续约记录，无逐 token 或逐轮询写放大。若无法复现某风险，报告锁与事务隔离证据而非虚构修复。

### E7OBS2-07：取消与已结束阶段的终态不一致

**定位**：[workflows/chat.py](../src/xhs_agent/workflows/chat.py) 的 supervisor_node；[chat_turns.py](../src/xhs_agent/services/chat_turns.py) 的 CancelledError/_terminal_snapshot/_finalize_turn；前端中断提示。

**局部复现与真实路径**：将 supervisor/failed/error_category=cancelled 交给 _terminal_snapshot(status=interrupted)，结果仍 failed。真实 supervisor 捕获 BaseException（含取消）先发 failed，外层再标消息 interrupted，存在不一致路径。现有取消测试替换 run_turn、仅发 running，未覆盖真实 workflow 先失败的分支。

**实施步骤**

1. 使用真实 workflow+runner 组合做 Task.cancel 回归，不仅 mock 运行器。
2. 区分轮次取消与历史尝试失败：当前取消执行投影 interrupted/cancelled，既有历史失败保留；不能把所有 failed 粗暴改 interrupted。
3. 在阶段来源正确映射取消，或在统一收尾按执行身份裁决；与 E7OBS2-02 的终态守卫协调，避免后端修正被前端拒收。
4. 同一终态结果生成数据库、SSE、trace 和展示，保留 trace 和 E7OBS2-01 已知账目。
5. 有界写回后重抛取消；SSE 断线只停转发。再次取消和数据库不可用明确尽力边界，不承诺强杀仍可写回。
