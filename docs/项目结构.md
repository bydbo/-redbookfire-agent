## 二、目录职责与边界

| 位置 | 职责 | 明确不放 |
| --- | --- | --- |
| `src/xhs_agent/tools/` | 确定性能力，可独立测试 | 流程编排、跨步骤状态 |
| `src/xhs_agent/agents/` | 单点智能体：线索拆解、匹配解释、撰稿 | 底层算法、文件扫描 |
| `src/xhs_agent/workflows/` | 把各步骤串成一次完整运行 | 重复实现 `tools/` 已有能力 |
| `tests/` | 单元与集成测试，必须离线可跑 | 运行产物、真实素材 |
| `evals/` | 评测用例、标注数据、脱敏示例素材包 | 真实素材 |
| `config/` | 可公开的默认配置与密钥模板 | 真实密钥 |
| `data/materials/` | 用户本地素材库 | 任何需要提交的文件 |
| `runs/` | 运行产物与索引缓存，可随时删除重建 | 手写源码 |
| `docs/` | 全部文档（产品 + 工程） | 代码 |
| `docs/contracts/` | 四份契约，唯一事实源；改接口或数据结构先改这里 | 实现细节、可变参数 |
| `docs/adr/` | 架构决策记录；只记取舍与理由，不描述现状 | 现状说明、操作手册 |

### 依赖方向

```
workflows/  →  agents/  →  tools/  →  schemas.py
```

只能单向。`tools/` 不得反向调用 `agents/` 或 `workflows/`。

## 三、为什么 `src/`、`config/`、`data/`、`runs/` 必须并列

`src/xhs_agent/config.py` 用"上溯三层"的方式推导工程根：

```
<工程根>/src/xhs_agent/config.py  →  上溯三层  →  <工程根>
```

然后所有相对路径都基于工程根解析：`config/config.toml`、`data/materials`、`runs`。

**所以这四个目录必须保持同级。** 单独移动其中任何一个，都会导致配置读不到、素材库指向错误位置，而且不会报错，只会静默使用默认值——这是最难排查的一类故障。

## 四、不入库的东西（及原因）

| 路径 | 原因 |
| --- | --- |
| `config/.env` | 密钥，安全红线 |
| `data/materials/*` | 体积大、含个人隐私 |
| `runs/*` | 运行产物，可随时重建 |
| `.venv/`、`__pycache__/`、`.pytest_cache/` | 环境与缓存 |
| `frontend/node_modules/`、`frontend/dist/` | 前端依赖与构建产物，可由 `pnpm install` 与 `pnpm build` 重建 |

示例素材包是个例外：它要入库，所以放 `evals/fixtures/demo_pack/`，**不要**放 `data/materials/`——后者整个目录都被忽略规则挡住。

## 六、命名约定

| 用途 | 名称 |
| --- | --- |
| 项目显示名 | 小红书热点搭子 |
| 英文副标 | Hotspot-to-Material Relevance Agent |
| Python 包 | `xhs_agent` |
| 分发名（pyproject / uv.lock） | `xhs-agent` |
| 环境变量前缀 | `XHS_` |

**显示名与代码标识是有意分离的。** `xhs_agent` / `xhs-agent` / `XHS_` 都取自“小红书（xhs）”，与显示名并不冲突。因此：

- 改显示名时，**不要顺手改包名**——那会同时影响 import 语句、`pyproject.toml` 的 `name`、`uv.lock` 与 `[tool.hatch.build.targets.wheel]` 的路径配置。
- 确需改包名时，按 `AGENTS.md` 第 6 节流程单独评审，并在同一次改动里同步 `pyproject.toml`、`uv.lock`、全部 import 与本文档。

另：**“蹭点”在新命名下保留为领域术语**，指“热点中可被自家素材复刻、因而能借用的爆点要素”（如“可蹭点 / 不可蹭点”），与项目显示名无关，见 `docs/产品方案.md` 第六节的要素分层。
