# ADR 0007 · 契约唯一源 + OpenAPI 3.1

- 状态：已采纳
- 日期：2026-09-30
- 关联：`docs/contracts/` 全部文件、`AGENTS.md` 第 2 节

## 背景

方案与架构定稿之后，写代码之前还有一道"可执行化"工序。这里的风险是：如果接口与数据结构边写边定，那么每改一次就要改一片调用方；而如果只用 Markdown 描述，又无法机读、无法自动校验，文档会迅速与实现脱节。

## 备选方案

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| Markdown 表格描述接口 | 阅读最轻 | 无法机读、无法校验、必然过期 |
| Pydantic 代码优先，再导出 OpenAPI | 少写一份文件、与实现天然一致 | 契约随代码漂移，评审时没有可讨论的稳定对象；"契约先行"名存实亡 |
| OpenAPI 3.1 YAML 作为唯一源 | 机读、可生成文档与测试、可进 CI 校验 | 需要手工维护，且要写校验规则避免漂移 |

## 决策

**OpenAPI 3.1 YAML 作为 API 的唯一事实源**，与三份 Markdown 契约（数据、检索、配置）共同放在 `docs/contracts/`。代码向契约对齐；改接口必须先改契约文件，再改实现，并在 CI 中做一致性校验。

## 后果

**正面**

- 评审有稳定对象：契约冻结后再动手，避免"边写边改"；
- 可自动生成接口文档、测试用例与前端类型；
- 契约、数据模型、配置三者的交叉约束（例如 `embedding_dim` 必须同时匹配数据契约与配置契约）可以被明确检查。

**负面**

- 多一层维护成本：改接口要动两处（契约 + 实现），这也是要靠 CI 校验兜住的地方；
- 3.1 版本的工具有些支持不完整，早期可能得先人工校验。

**后续**

- P1 阶段引入 OpenAPI 校验工具，纳入 CI（见 `docs/backlog.md` 的 S4.6）；
- 契约文件的路径若因 CI 工具链需要调整（例如移到仓库根），需补一条新 ADR。
