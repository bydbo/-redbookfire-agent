# ADR 0001 · 取消运行时降级

- 状态：已采纳
- 日期：2026-09-30
- 关联：`docs/技术栈.md` 第二节、`AGENTS.md` 第 4 节、`src/xhs_agent/tools/offline.py`

## 背景

初版设计里有一条"无密钥降级"路径：没有 API 密钥时由离线规则引擎接管全链路，用内置爆点词典替代大模型，保证在任何机器上都能跑出报告，并把它当作核心卖点之一。

引入数据库与队列之后，这条路径的外延迅速膨胀：不能只考虑"没有密钥"，还要考虑"连不上数据库""连不上 Redis"——如果每种缺失都要有兜底实现，业务代码将长期维护两套甚至三套执行路径。

## 备选方案

| 方案 | 代价 |
| --- | --- |
| 保留完整降级（无密钥 + 无数据库） | 业务代码长期双轨；存储层要写文件与数据库两套适配器；测试矩阵翻倍 |
| 只保留无密钥降级 | 数据库仍然必须可用，降级承诺残缺，叙事不自洽 |
| 取消降级，缺依赖即失败 | 失去"拷走就能跑"的卖点；演示必须自带密钥与环境 |

## 决策

**取消整条运行时降级路径。** 缺密钥、连不上数据库、连不上 Redis 时，启动或执行直接失败并给出明确报错，不做静默降级。`tools/offline.py` 在 P2 阶段删除，测试改用固定样本。

边界说明：取消的是**整条运行链路**的降级。单个可选能力（如缺少 ffmpeg 时跳过抽帧）属于能力裁剪，会在产物中明确标注，不在取消范围内。

## 后果

**正面**

- 只有一条执行路径，代码、测试与排障都简化；
- 不会出现"跑出来了但结果不可信"的情况——降级模式产出质量差一档，一旦被当成正常模式使用会损害可信度；
- 把"可部署性"作为演示的依赖，用 `docker compose up` 一条命令替代降级兜底，叙事更硬。

**负面**

- 演示与试用门槛提高，必须有密钥与容器环境；
- README、产品方案与简历中原有的"零密钥可跑"卖点全部作废，需要重写（已完成）。

**后续**

- 部署文档必须把前置条件写清楚，避免用户卡在启动失败上；
- `/health` 要能分别报告 db / redis / llm 三项状态，让失败可定位。
