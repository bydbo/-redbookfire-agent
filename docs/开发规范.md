# 开发规范（详版）

> 本文件是根目录 `AGENTS.md` 的详细解释版：条文相同，但补上了"为什么这么定"。
> **冲突时以根目录 `AGENTS.md` 为准。**

---

## 一、开发规则

### 01 目录与代码位置

**规则**

| 位置 | 放什么 |
| --- | --- |
| `src/xhs_agent/tools/` | 确定性能力：词典、模型调用、素材索引、匹配打分、报告渲染、运行追踪 |
| `src/xhs_agent/agents/` | 单点智能体：线索拆解、匹配解释、撰稿 |
| `src/xhs_agent/workflows/` | 把各步骤串成一次完整运行 |
| `tests/` | 测试 |
| `evals/` | 评测用例、标注数据、脱敏示例素材包 |
| `config/` | `config.toml` 与 `.env.example` |
| `data/materials/` | 本地素材库（不入库） |
| `runs/` | 运行产物（不入库） |
| `docs/` | 全部文档 |

**为什么**

- 把"确定性能力"和"需要判断的编排"分开，是让匹配结果可复现、可测试的前提。算法混进编排层之后，测试就必须连模型一起跑，测试成本会失控。
- `schemas.py` 单独定为唯一契约来源，是因为它被所有模块引用；契约散落各处时，改一个字段要满仓库找。
- `src/`、`config/`、`data/`、`runs/` 必须同级，由 `config.py` 的工程根推导方式决定（上溯三层）。拆开不会报错，只会静默用错路径——这是最贵的故障类型。

### 02 文件边界

**规则**

- 依赖方向只能单向：`workflows/` → `agents/` → `tools/` → `schemas.py`。
- `tools/` 不得反向调用 `agents/` 或 `workflows/`。
- 数据契约只能定义在 `schemas.py`，不得另建并行结构。
- 禁止在 `src/` 下写运行时数据；禁止在 `tests/` 下写运行产物。
- 禁止把密钥、真实素材、运行产物写进任何会被提交的文件。
- 仓库根的 Markdown 只允许 `README.md` 与 `AGENTS.md` 两份，其余文档一律进 `docs/`。

**为什么**

- 单向依赖让 `tools/` 保持可独立测试、可单独替换；一旦出现反向依赖，模块就无法在无编排的情况下被验证。
- 契约唯一，才能保证"模型输出的结构"和"程序读取的结构"始终是同一份定义，不会出现两边悄悄漂移。
- 测试写产物会让测试相互污染，第二次运行结果和第一次不同，等于测试失效。
- 根目录 Markdown 限两份，是为了让"项目入口"和"AI 规范"永远显眼，不被十份散落文档淹没。

### 03 测试要求

**规则**

- 框架 `pytest`，用例放 `tests/`，文件名 `test_*.py`。
- 所有测试必须能在**无密钥、无网络**的机器上跑通；外部调用一律用假实现或固定样本。
- 涉及扫描、打分、渲染的测试，断言结构化结果（分数、命中要素、覆盖缺口），不断言自然语言措辞。
- 涉及文件系统的测试必须用临时目录，跑完不留残留。
- 当前 `tests/` 为空目录，`uv run pytest` 报"0 用例、退出码 5"是预期状态；第一个功能落地前必须先补对应测试。

**为什么**

- 这个项目的核心卖点之一就是"无密钥也能完整跑通"。如果测试自己就依赖密钥，这条承诺无法验证，也无法在别人的机器上复现。
- 不断言措辞：文案由模型生成，措辞天然会变；断言措辞会让测试随机变红，久而久之没人再信测试。
- 断言结构化结果，等于把"可解释"落到测试里——命中要素和分数是这套系统的硬输出。

### 04 依赖策略

**规则**

- 运行时零第三方依赖：核心逻辑只用标准库，外加可选的系统级 `ffmpeg` / `ffprobe`。
- 开发依赖仅允许测试工具（当前 `pytest`）。
- 依赖统一在 `pyproject.toml` 声明，由 `uv` 管理，`uv.lock` 提交入库。
- 不引入重型框架（Web 框架、Agent 编排框架、ORM）。
- Python `>= 3.11`（代码用了 `tomllib`）。

**为什么**

- 零运行时依赖带来三个直接好处：部署门槛低（拷走就能跑）、面试演示不会因为装不上包翻车、降级链路可信（缺依赖不中断主链路）。
- 锁定文件入库保证任何人在任何时间拿到同一套依赖，评测结果才可比。
- 不引框架是刻意选择：这个项目的价值主张是"把检索留在算法里"，引入编排框架会把核心逻辑藏进框架内部，反而讲不清。

## 二、测试、依赖与提交

### 01 新增功能后怎么测试

按顺序执行，缺一步不算完成：

| 步骤 | 动作 | 判定标准 |
| --- | --- | --- |
| 1 | 补测试 | 新增功能在 `tests/` 有对应用例；纯配置或纯文档改动可免测，但要在提交信息里说明 |
| 2 | 跑全量 | `uv run pytest` 全绿，既有用例没有变红 |
| 3 | 跑冒烟 | 用最小输入走一遍真实链路；涉及报告渲染的改动必须实际生成一份报告看一眼 |
| 4 | 验降级 | 任何依赖外部服务的改动，必须确认"没有密钥"时仍能跑通 |
| 5 | 同步文档 | 行为变化更新 `README.md` 与 `docs/项目结构.md`；规则变化更新 `AGENTS.md` |

**为什么**：这五步对应五类最容易翻车的地方——没测、测坏别的、跑起来是空的、有密钥能跑没密钥就崩、代码改了文档还是旧的。

### 02 什么时候允许增加依赖

默认答案是**不允许**。同时满足全部条件才可加：

1. 标准库确实做不到，或实现成本明显不合理地高；
2. 能写出一句"不加这个依赖会怎样"，放进提交信息；
3. 优先加开发依赖，避免动运行时依赖；
4. 同步更新 `pyproject.toml`、`uv.lock`、`README.md` 与 `AGENTS.md` 第 4 节。

明确禁止：为省几行代码加依赖；只为用到 5% 功能的库；会长期绑定某个云厂商 SDK 的依赖。

**为什么**：依赖是长期负债。这个项目的架构承诺（零运行时依赖 + 可降级）只有在依赖被严格看住时才成立。

### 03 提交前检查哪些内容

- [ ] `git status` 里没有 `config/.env`、`data/materials/` 内容、`runs/` 产物；
- [ ] 没有密钥、Token、账号密码出现在代码、文档或示例里；
- [ ] `uv run pytest` 通过（无用例时要确认是"没有测试"而不是"测试失败"）；
- [ ] 新增功能有测试，或提交信息里说明了免测理由；
- [ ] `pyproject.toml` 与实际 import 的依赖一致；
- [ ] 行为变化已同步文档，规则变化已同步 `AGENTS.md`；
- [ ] 提交信息前缀符合 `feat / fix / docs / test / chore / refactor`，一次提交只做一件事。

**为什么**：前两条是安全红线（一旦进了历史就很难彻底清除）；中间三条保证可运行与可维护；最后一条让提交历史本身成为可读的工程记录。

## 三、密钥与源码分开保存

**规则**

- 模板 `config/.env.example` 入库，只含变量名与空值。
- 真实密钥写 `config/.env`，被 `.gitignore` 忽略，永不提交。
- 代码读取顺序：`config/.env` → 环境变量覆盖。任何模块不得硬编码密钥，也不得把密钥写进日志、报告或 `runs/` 产物。
- 支持变量：`DEEPSEEK_API_KEY`、`DASHSCOPE_API_KEY`、`XHS_LLM_PROVIDER`、`XHS_LLM_BASE_URL`、`XHS_LLM_MODEL`、`XHS_LLM_API_KEY`。
- `config/config.toml` 只放可公开的默认值。

**为什么**

- 密钥进版本库的代价是不可逆的：即使后续提交删掉，历史里仍在，必须轮换密钥才能止损。
- 密钥与配置分离之后，`config.toml` 可以放心地进仓库、给别人看、写进截图，而不用逐行检查。
- 环境变量可覆盖，让"临时换个模型试一下"不需要改动任何被跟踪的文件。

## 四、规则复用，减少反复猜测

**读取约定**

- 任何任务开始前先读根目录 `AGENTS.md`，按第 1、2 节确认文件位置与边界。
- 全仓库只保留一份 `AGENTS.md`；子目录特殊规则写进它对应的小节，不另建文件。
- 规则与文档的作用是让下一个会话（无论是人还是 AI）不必重新问一遍"这个项目怎么组织的"。

**执行约定**

1. 读规范；
2. 搜索并读真实代码，不凭文件名猜；
3. 最小化改动，不顺手改无关代码；
4. 按第二节 01 的流程验证；
5. 更新文档与规范后提交。

**冲突时的优先级**

`不破坏既有数据契约` > `最小改动` > `顺手优化`。

**规范随代码演进**

规范没覆盖的情况要按"最小改动 + 不破坏契约"先做，并在同一次提交里把新规则补回 `AGENTS.md`。规则和代码一起长，才不会变成一份没人看的过期文档。
