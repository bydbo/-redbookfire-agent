# 开发规范（详版）

> 本文件是根目录 `AGENTS.md` 的详细解释版：条文相同，但补上了"为什么这么定"。
> **冲突时以根目录 `AGENTS.md` 为准。**

---

## 一、开发规则

### 01 目录与代码位置

**规则**

| 位置 | 放什么 |
| --- | --- |
| `src/xhs_agent/tools/` | 确定性能力：词典、模型调用、素材索引、匹配打分、报告渲染、运行追踪 |
| `src/xhs_agent/agents/` | 单点智能体：线索拆解、匹配解释、撰稿 |
| `src/xhs_agent/workflows/` | 把各步骤串成一次完整运行 |
| `tests/` | 测试 |
| `evals/` | 评测用例、标注数据、脱敏示例素材包 |
| `config/` | `config.toml` 与 `.env.example` |
| `data/materials/` | 本地素材库（不入库） |
| `runs/` | 运行产物（不入库） |
| `frontend/` | Vue 3 单页应用：源码、构建配置与前端测试 |
| `docs/` | 全部文档 |
| `docs/contracts/` | 四份契约，唯一事实源；改接口或数据结构先改这里 |
| `docs/adr/` | 架构决策记录 |

**为什么**

- 把"确定性能力"和"需要判断的编排"分开，是让匹配结果可复现、可测试的前提。算法混进编排层之后，测试就必须连模型一起跑，测试成本会失控。
- 契约的**内容**单独收敛到 `docs/contracts/`，是因为它被所有模块引用、又需要被人评审；契约散落各处时，改一个字段要满仓库找，评审时也没有稳定对象。
- `src/`、`config/`、`data/`、`runs/` 必须同级，由 `config.py` 的工程根推导方式决定（上溯三层）。拆开不会报错，只会静默用错路径——这是最贵的故障类型。

### 02 文件边界

**规则**

- 依赖方向只能单向：`workflows/` → `agents/` → `tools/` → `models/`（P1 之前为 `schemas.py`）。
- `tools/` 不得反向调用 `agents/` 或 `workflows/`。
- 数据与接口契约只能定义在 `docs/contracts/`；代码侧的类型（`models/`，P1 之前为 `schemas.py`）必须与契约逐字段一致，不得另建并行结构。
- 禁止在 `src/` 下写运行时数据；禁止在 `tests/` 下写运行产物。
- 禁止把密钥、真实素材、运行产物写进任何会被提交的文件。
- 仓库根的 Markdown 只允许 `README.md` 与 `AGENTS.md` 两份，其余文档一律进 `docs/`。

**tool 层标准（五条，权威条文见 `AGENTS.md` 第 2.1 节）**

- 一个 tool 只做一件事；输入用「用途 / 输入 / 输出」写清；输出必须同输入同输出、不得依赖系统时钟或全局状态；不反向依赖上层；每个 tool 都能被单独测试。
- 为什么把"不依赖时钟"写成硬条款：`matching` 的时效加减分原先直接读 `time.time()`，同一份输入在不同时刻跑出的分数不同——测试只能断言范围、无法回归，等于放弃保护这块逻辑。现在时间基准是显式参数（不传时仍取当前时间），生产行为不变，测试可以钉死结果。
- 为什么强调"依赖可注入"：本机装了 ffmpeg、别人机器没装，测试若直接吃系统状态就会变成"只在我这台机器上绿"。`tests/unit/conftest.py` 的 `no_ffmpeg` 夹具把 ffmpeg / ffprobe 探测固定下来，两条路径都能测。

**为什么**

- 单向依赖让 `tools/` 保持可独立测试、可单独替换；一旦出现反向依赖，模块就无法在无编排的情况下被验证。
- 契约唯一，才能保证"模型输出的结构"和"程序读取的结构"始终是同一份定义，不会出现两边悄悄漂移。
- 测试写产物会让测试相互污染，第二次运行结果和第一次不同，等于测试失效。
- 根目录 Markdown 限两份，是为了让"项目入口"和"AI 规范"永远显眼，不被十份散落文档淹没。

### 03 测试要求

**规则**

- 框架 `pytest`，用例放 `tests/`，文件名 `test_*.py`。
- 测试不依赖真实密钥与真实模型：外部调用一律用固定样本或假实现；涉及数据库的集成测试用 testcontainers 起一次性容器。**注意：这与运行时要求相反——运行时不降级，缺密钥直接失败。**
- 涉及扫描、打分、渲染的测试，断言结构化结果（分数、命中要素、覆盖缺口），不断言自然语言措辞。
- 涉及文件系统的测试必须用临时目录，跑完不留残留。
- 当前 `tests/unit/` 已有契约、配置与前置检查用例，`uv run pytest` 应全绿；`tools/` 的行为回归测试见 `docs/backlog.md` 的 S1.4。

**为什么**

- 测试的意义是“任何人 clone 下来就能验”，所以测试里不能出现真实密钥；但运行时不降级，因此测试与运行时的依赖假设必须分开写清楚，避免把“测试能跑”误当成“没密钥也能跑”。
- 不断言措辞：文案由模型生成，措辞天然会变；断言措辞会让测试随机变红，久而久之没人再信测试。
- 断言结构化结果，等于把"可解释"落到测试里——命中要素和分数是这套系统的硬输出。

### 04 依赖策略

**规则**

- 运行时依赖：当前为空（核心逻辑只用标准库）；引入任何运行时依赖都必须先按第二节的流程论证。
- 开发依赖：允许测试与代码质量工具，当前为 `pytest`、`pytest-cov`、`pytest-asyncio`、`testcontainers[redis]`、`ruff`、`mypy`、`pre-commit`。
- 系统级依赖：`ffmpeg` / `ffprobe`，用于探测与抽帧；缺失时只影响抽帧能力。
- 依赖统一在 `pyproject.toml` 声明，由 `uv` 管理，`uv.lock` 提交入库。
- 依赖现状以 `docs/技术栈.md` 为准，本文件只写规则。
- Python `>= 3.11`（代码用了 `tomllib`）。
- 前端依赖由 `frontend/package.json` 声明、pnpm 管理；`pnpm-lock.yaml` 提交入库，`node_modules/` 与 `frontend/dist/` 不入库。
- 前端直接依赖需在提交信息里写明理由；**禁止同时引入第二套组件库或第二个状态管理方案**。
- 前端工具链：Node 25.3.0 + pnpm 11.25.0（本机基线，在 `frontend/package.json` 的 `engines` 与 `frontend/.node-version` 中固定）。
- **数据库迁移**：schema 变更一律通过 Alembic 迁移脚本进行，禁止手工改库；迁移脚本与代码同提交，且必须可回滚。命令：`uv run alembic upgrade head`（建/升）、`uv run alembic downgrade base`（回滚）、`uv run alembic check`（迁移与 ORM 模型一致性自查）、`uv run alembic revision --autogenerate --rev-id 00NN -m "<english slug>"`（新迁移，文件名英文、说明中文）。
- **Celery 任务里怎么调 async**（ADR 0004 要求一次定下的口径，S3.4b 落地）：任务入口是**同步函数**，内部用 `asyncio.run(...)`；engine 与 httpx 客户端都在**任务内建、任务内关**，**禁止把连接池挂进程级**——Celery 每个任务一个新事件循环，进程级连接池会绑在已关闭的 loop 上。失败路径固定为：基础设施类错误（DB/网络/超时）走 Celery 重试（预算取 `[queue].max_retries`），分析类失败**不重试**、由任务层兜底写 `runs.status='failed'`。实现与用例见 `src/xhs_agent/tasks/analysis.py` 与 `tests/unit/test_celery_app.py`。
- **日志怎么写**（S4.1 落地）：调用点一律用**标准库** `logging.getLogger("xhs_agent.…")`（`logger.info("…%s", x)` 语法，不引入 `structlog.get_logger()`）；structlog 只做渲染管线，输出格式由顶层配置 `log_format` 决定——`console` 本机可读、`json` 一行一个 JSON 对象（容器 / CI 用 `XHS_LOG_FORMAT=json` 覆盖）。`request_id` 与 `run_id` 由上下文注入、**每条日志都带**（不在上下文里为空串）：请求内由 `api/middleware.py` 管 `request_id`，一次运行由 `core/logging.bind_run_id` 管 `run_id`（`tasks/analysis.py::run_job`、`workflows/analysis.py::run_analysis`、`POST /api/analyze` 三处绑定，用完 `finally` 复位）。**边界**：`tasks/analysis.py::execute` 里"重试 / 超时"那几行同步日志发生在查到 run 之前，只有 `job_id` 在报文里、`run_id` 是空串。**禁止**把密钥、DSN 密码写进日志（`describe()` / `_mask_dsn` 的口径见《配置契约》§六）。实现与用例见 `src/xhs_agent/core/logging.py` 与 `tests/unit/test_logging.py`。
- **陈旧 run 对账**（S4.1 落地）：worker 启动时（`celery.signals.worker_ready`）跑一次 `services.runs.reconcile_stale_runs`，把 `running` 且 `started_at` 早于 `now - [queue].task_time_limit_s × 2` 的行标成 `failed`。失败只记日志、不阻断 worker 启动；手动补跑 `uv run python -m xhs_agent.tasks.reconcile`。**断点续跑仍未做**（重跑同一 run 会重跑所有热点）。
- **调用追踪怎么接**（S4.2 落地）：业务代码**不直接 `import langfuse`**，一律走 `core/tracing.py` 的门面——`get_tracer(cfg)` 拿进程级追踪器（缺 `LANGFUSE_*` 三件套时是 `NullTracer`：只警告一次、不阻断），`run_analysis` 负责开「运行 trace → 热点 span → 模型调用 generation」三层，`TracingProvider` 把每次 `complete()` 的 token / 成本 / 延迟 / 错误写进 generation。**默认只上报元数据**（ADR 0005：不上报提示词原文），`LANGFUSE_CAPTURE_CONTENT=true` 才连正文一起上报；上报与 flush 失败都只记日志，绝不改变分析结果或 `runs` 落库。SDK 客户端**进程级懒加载**：SDK 会占用全局 OTel TracerProvider（进程内只能设一次），且 prefork 子进程不能继承父进程的导出线程。实现与用例见 `src/xhs_agent/core/tracing.py` 与 `tests/unit/test_tracing.py`。
- **span 怎么加 / 怎么跨进程**（S4.3 落地）：一律走 `core/tracing.py`，**不直接 import 任何 `opentelemetry.instrumentation.*`**。① 数据库操作：`@traced_db("db.<名字>", operation="insert|select|update|write", tables=(...))` 装饰异步函数（或 `with db_span(...)`），**绝不把 SQL 语句写进 span**（热点原文、素材路径会离开本机）；② HTTP 入口：`create_app()` 里已装 FastAPI/ASGI 自动埋点（服务端 span，`/api/health` 与文档页排除）；③ 跨进程：投递侧 `current_trace_headers()` 取 W3C `traceparent` 放进 Celery 消息头，消费侧 `use_trace_carrier(carrier)` 包住任务体（两侧都是空操作安全的）；④ OTel 的 provider 由 Langfuse SDK 提供，`should_export_span` 已放宽到 `xhs_agent.*` 与 `opentelemetry.instrumentation.*`，否则会被静默丢弃。测试用 `tests/conftest.py` 的 `otel_exporter` 夹具（真 provider + 内存导出器）断言 span 形状；同文件的 autouse `isolate_tracing` 会把本机 `config/.env` 里的真凭据置空，避免测试真的往云上传。
- **容器怎么跑**（S4.4 落地）：一条命令 `docker compose up -d --wait` 起全栈（postgres / redis / migrate / api / worker）。① **迁移不用手跑**：一次性 `migrate` 服务执行 `alembic upgrade head`，api / worker 用 `depends_on: service_completed_successfully` 等它成功，迁移失败则应用根本不起；② **一个镜像两种角色**：`xhs-agent:0.1.0` 默认 CMD 起 API，compose 里给 worker 覆盖 `command`（`--concurrency=2`）；③ **镜像里不能把项目装成 `--no-editable`**——`PROJECT_ROOT` 依赖 `/app/src` 的布局，装进 site-packages 会让配置、素材与产物路径全错；④ 素材与产物是 bind mount（`./data/materials`、`./runs`），宿主上直接能看报告与 `trace.jsonl`；⑤ 容器日志固定 `XHS_LOG_FORMAT=json`，排障用 `docker compose logs -f api`；⑥ 停机：api `stop_grace_period: 30s`、worker 180s，lifespan 退出会 dispose 连接池并清配置缓存（E3 审查建议 6）。改镜像或编排后**必须同时改** `tests/unit/test_dockerfile.py` 与 `tests/unit/test_compose_config.py` 的静态断言。

**为什么**

- 依赖少带来两个好处：部署门槛低、面试演示不容易因为装不上包翻车；但"依赖少"是当前状态，不是永久禁令。
- 依赖是长期负债，所以每次引入都要论证、都要留记录。
- 真正的价值主张是“把检索留在算法里”——它与用不用 Web 框架无关；引入服务框架、数据库与向量库不会动摇核心卖点，反而补上工程完整度。最终技术栈见 `docs/技术栈.md`。
- 运行时不做降级：缺密钥、缺数据库、缺队列时直接失败并明确报错。
- 锁定文件入库保证任何人在任何时间拿到同一套依赖，评测结果才可比。

## 二、测试、依赖与提交

### 01 新增功能后怎么测试

按顺序执行，缺一步不算完成：

| 步骤 | 动作 | 判定标准 |
| --- | --- | --- |
| 1 | 补测试 | 新增功能在 `tests/` 有对应用例；纯配置或纯文档改动可免测，但要在提交信息里说明 |
| 2 | 跑质量门与全量 | `uv run ruff check .` 零告警、`uv run mypy` 零错误、`uv run pytest` 全绿，既有用例没有变红 |
| 3 | 跑冒烟 | 用最小输入走一遍真实链路；涉及报告渲染的改动必须实际生成一份报告看一眼 |
| 4 | 跑集成测试 | 依赖外部服务的改动跑 `uv run pytest -m integration`（testcontainers 起真实 Postgres / Redis）；Docker 不可用时直接失败并说明原因，不静默跳过 |
| 5 | 同步文档 | 行为变化更新 `README.md` 与 `docs/项目结构.md`；规则变化更新 `AGENTS.md` |

**为什么**：这五步对应五类最容易翻车的地方——没测、测坏别的、跑起来是空的、本地能跑真实依赖下崩、代码改了文档还是旧的。

### 02 什么时候允许增加依赖

默认答案是**不允许**。同时满足全部条件才可加：

1. 标准库确实做不到，或实现成本明显不合理地高；
2. 能写出一句"不加这个依赖会怎样"，放进提交信息；
3. 优先加开发依赖，避免动运行时依赖；
4. 同步更新 `pyproject.toml`、`uv.lock`、`README.md` 与 `AGENTS.md` 第 4 节。

明确禁止：为省几行代码加依赖；只为用到 5% 功能的库；会长期绑定某个云厂商 SDK 的依赖。

**为什么**：依赖是长期负债，一旦失控就无法回退；所以"严格看住"的意思是每次引入都有理由、有记录，而不是一律禁止。

### 03 提交前检查哪些内容

- [ ] `git status` 里没有 `config/.env`、`data/materials/` 内容、`runs/` 产物；
- [ ] 没有密钥、Token、账号密码出现在代码、文档或示例里；
- [ ] `uv run ruff check .` 零告警、`uv run mypy` 零错误，且提交前钩子已生效；
- [ ] `uv run pytest` 通过；
- [ ] 新增功能有测试，或提交信息里说明了免测理由；
- [ ] `pyproject.toml` 与实际 import 的依赖一致；
- [ ] 行为变化已同步文档，规则变化已同步 `AGENTS.md`；
- [ ] 提交信息前缀符合 `feat / fix / docs / test / chore / refactor`，一次提交只做一件事。

**为什么**：前两条是安全红线（一旦进了历史就很难彻底清除）；中间三条保证可运行与可维护；最后一条让提交历史本身成为可读的工程记录。

## 三、密钥与源码分开保存

**规则**

- 模板 `config/.env.example` 入库，只含变量名与空值。
- 真实密钥写 `config/.env`，被 `.gitignore` 忽略，永不提交。
- 代码读取顺序：`config/.env` → 环境变量覆盖。任何模块不得硬编码密钥，也不得把密钥写进日志、报告或 `runs/` 产物。
- 环境变量全集（名称、必填性、默认值、校验规则、缺失行为）以及启动前置检查，**一律以 `docs/contracts/配置契约.md` 为准**；本文件不再自维护清单，避免两处漂移。
- `config/config.toml` 只放可公开的默认值。

**为什么**

- 密钥进版本库的代价是不可逆的：即使后续提交删掉，历史里仍在，必须轮换密钥才能止损。
- 密钥与配置分离之后，`config.toml` 可以放心地进仓库、给别人看、写进截图，而不用逐行检查。
- 环境变量可覆盖，让"临时换个模型试一下"不需要改动任何被跟踪的文件。

## 四、规则复用，减少反复猜测

**读取约定**

- 任何任务开始前先读根目录 `AGENTS.md`，按第 1、2 节确认文件位置与边界。
- 全仓库只保留一份 `AGENTS.md`；子目录特殊规则写进它对应的小节，不另建文件。
- 规则与文档的作用是让下一个会话（无论是人还是 AI）不必重新问一遍"这个项目怎么组织的"。

**执行约定**

1. 读规范；
2. 搜索并读真实代码，不凭文件名猜；
3. 最小化改动，不顺手改无关代码；
4. 按第二节 01 的流程验证；
5. 更新文档与规范后提交。

**冲突时的优先级**

`不破坏既有数据契约` > `最小改动` > `顺手优化`。

**规范随代码演进**

规范没覆盖的情况要按"最小改动 + 不破坏契约"先做，并在同一次提交里把新规则补回 `AGENTS.md`。规则和代码一起长，才不会变成一份没人看的过期文档。
