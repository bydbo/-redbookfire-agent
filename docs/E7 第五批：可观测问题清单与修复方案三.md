## 2. 统一设计约束

四项修改共用以下边界，实施前先把语义写入 [数据契约](contracts/数据契约.md)、[OpenAPI](contracts/openapi.yaml) 的受影响章节，并同步 [可观测说明](可观测.md)。

| 概念 | 必须保持的语义 |
| --- | --- |
| 已知消费 | 已完成子调用返回的 tokens、配置折算成本、版本与来源；不能因外层工具未结束而丢弃 |
| 未知消费 | 请求已发生或可能发生但无可靠账目；不虚构为准确零，也不抹掉同工具内的已知部分 |
| 部分工具记录 | 外层工具未成功完成，但已有子步骤及运行引用可保存；不得伪造工具成功 |
| 来源顺序 | 在同一明确执行范围内产生的因果次序；不能用跨进程墙上时间或轮询到达顺序代替 |
| 当前阶段 | 已接受的当前执行投影；迟到历史事实可以补节点，不能随意接管当前 |
| 用量来源 | actual / estimated / unknown / cached 的事实分类，与金额是否为零分开 |
| usage_complete | 沿用“本轮计费调用均可解释”；estimated 可解释，但不等于全为供应商实测值 |
| 核账对象 | 对话账目、工具账目和 trace 叶子按对应关系比较，不能把父层汇总和内部叶子重复相加 |

默认复用现有 JSONB 快照、工具记录及轮次字段，不预设新增数据库表或列。确需 schema 变更时，说明旧结构为何不足，并按实现时 Alembic head 编号；不能把 JSON 字段演进误称为必须建新表。

## 3. E7OBS3-01：工具内部消费在取消时丢失

### 3.1 已复现行为与根因

调用链：[chat_tools.py](../src/xhs_agent/services/chat_tools.py) 的 `run_hotspot_analysis` → [workflows/chat.py](../src/xhs_agent/workflows/chat.py) 的工具节点 → [chat_turns.py](../src/xhs_agent/services/chat_turns.py) 的 `_ledger_snapshot` / `_finalize_turn`。

固定输入序列：

1. supervisor 成功：输入 10、输出 5 tokens，成本 0.001 元。
2. 图片解析成功：输入 500、输出 20 tokens，成本 0.003 元，返回 prompt 版本。
3. 分析已提交，取得合法 UUID 的 run_id。
4. 等待分析时实际取消轮次任务。

当前收尾账本为：成本 0.001 元、10/5 tokens、`tool_calls=[]`、`run_id=""`、图片版本缺失。预期已知部分应为 **0.004 元、510/25 tokens**，保存图片版本和已取得的 run_id；分析本身未取得的用量仍标未知。

根因是账本只在整个 `run_tool(...)` 返回后追加 `ToolOutcome`。图片消费、提交结果虽然已完成并保存在工具局部变量中，但外层工具取消后没有返回，统一收尾无法读取这些事实。现有“取消保留已完成工具”用例没有覆盖“工具内部子步骤完成、外层尚未返回”。

### 3.2 修复方案

**建立工具内部的有限记账检查点，沿用现有轮次账本，不以完整 ToolOutcome 返回作为唯一登记时机。**

1. 在工具 runner 装配处传入内部账目收集器 / 回调。接口使用内部类型，业务层不直接操作数据库；避免让 tools 层反向依赖 services 或 workflows。
2. 图片解析、结构化拆解等子调用成功返回后，**在下一次可取消的 await 前**登记其账目、版本、来源。优先采用同步内存登记；若采用异步回调，须保证登记本身不会在取消间隙丢失已得到的结果。
3. `submit_analysis` 成功返回后立即登记 run_id / job_id；不等待 worker 结束才带出运行引用。引用登记与消费登记分开，提交成功不等于分析消费已知。
4. 每个组件使用轮次内稳定的唯一键，例如 `(turn_id, call_id, tool_attempt, component_id)`；component_id 区分图片解析、拆解等步骤及实际重试调用。缓存命中只登记本轮缓存事实，不重复计入历史费用。
5. 对同一个组件做 upsert；重复进度、收尾和回调不得重复加钱。已知消费由唯一组件集合求和，不能通过不断累加 payload 实现。
6. 最终 ToolOutcome 到达时，对已有工具记录做合并 / 结算。组件账目与最终工具总额只能有一个计费入口：建议最终工具总额成为已登记组件的投影；工具只提供不可拆的 worker 汇总时，将它作为独立组件，并排除其内部叶子的重复计费。
7. 出现后补“覆盖多个组件的累计总额”时，明确替换哪些组件，不能把累计总额当新增费用。不要用 `max(旧金额, 新金额)` 掩盖重复记账或合法修正。
8. 实际取消时，从同一账本生成部分工具记录及消息字段；已开始但未完成的模型调用只标未知，不估造消费。普通异常沿用相同收尾入口，保留安全错误类别。

### 3.3 持久化与取消边界

- `ChatToolCall.status` 当前只有 succeeded / failed。建议为实际取消的部分记录增补 `interrupted`，同步 OpenAPI、API 模型、前端生成类型和展示分支；内部 running 草稿不必因此公开为历史终态。
- 正常业务失败仍为 failed；工具未完成时不能为保存账目而伪造 succeeded。组件已成功与外层工具 interrupted 可以同时成立。
- `_finalize_turn` 应把部分 tool_calls、已知金额 / tokens、版本、trace_id 和运行引用一并尽力写回；真实存储读回验证，不能只检查传给 mock 的 kwargs。
- 同轮多工具可能产生多个 run_id：分别保留在各工具记录；消息级单一 run_id 沿用既定选择规则并写清，不扩展为未经设计的多运行聚合功能。
- 继续保持取消传播和有界收尾；再次取消、数据库不可用时保留可得旁路证据，不能宣称消息必定写回。
- 本方案保证协作式取消时可读的稳定边界，不承诺进程强杀、机器掉电后恢复尚未落库的内存组件；历史缺失账目不补造。

### 3.4 必要回归与完成标准

| 用例 | 必须观察到的结果 |
| --- | --- |
| 图片成功 → 提交成功 → 等待中 Task.cancel | 消息 interrupted；真实存储读回 0.004 元、510/25 tokens、图片版本、合法 run_id、部分工具记录；未知分析部分有明确标记 |
| 图片成功 → 提交抛异常 | 已知图片消费保留；不存在的运行引用不补造 |
| 图片成功 → worker failed / 超时 | 仍保留已有修复的已知部分；不重复记费 |
| 拆解成功 → 检索中取消 / 异常 | 已知拆解用量与版本保存，后续未知单列 |
| 检查点重复 → 工具最终成功 | 总账只计一次，等于成功路径的最终账目 |
| 缓存图片 → 等待取消 | 本轮不增加历史图片消费，仍保存本轮已取得的运行引用 |
| 两个工具 / 同工具两次执行 | 组件、版本、运行引用不串线；消息级引用规则确定 |
| 二次取消 / 收尾写库失败 | 取消继续传播；明确哪些字段保存失败，不伪报完整 |

至少一条用例贯穿真实 workflow、真实工具编排、轮次收尾与临时 Postgres；供应商和 worker 等待可隔离注入。全部金额、tokens、工具状态、引用及 trace 摘要相互一致才算完成。

## 4. E7OBS3-02：同 run 的迟到终态回退当前阶段

### 4.1 已复现行为与根因

定位：[core/progress.py](../src/xhs_agent/core/progress.py) 的 `begin/end/apply`，[chat_turns.py](../src/xhs_agent/services/chat_turns.py) 的 `persist/on_event`，[前端 store](../frontend/src/stores/chat.ts) 的 `applyProgressLike`。

`report/running/run-A` 收到 `draft/succeeded/run-A` 后，顶层回到 draft/succeeded，label 还可能保留 report 的标签。持久化在合并前仅检查“不同阶段、当前 running、run 不冲突”，因此还可能把仍在运行的 report 自动结束为 succeeded。

已有 run 身份隔离只解决不同 run 的一部分冲突。相同 run 可能包含多个热点、多个阶段实例及重试；仅比 stage 名、attempt 或 run_id 无法判断新旧。给所有阶段设一个全局固定排名也无法覆盖同轮重复分析、热点循环和重试。

### 4.2 推荐的最小身份与顺序设计

在现有快照 / 事件上增补有限的来源顺序，**区分来源身份、阶段实例和展示快照版本**。以下名称为建议，实施时统一冻结，不能在各层另造同义字段。

| 建议概念 / 字段 | 范围及生成责任 | 用途 |
| --- | --- | --- |
| `source_id` | 明确的工具 call / run / job 组合，轮次入口绑定当前活动调用 | 区分同轮不同工具执行，run 不存在时仍能标识本地阶段 |
| `stage_instance_id` | 来源内的阶段实例，覆盖热点位置 / 阶段发生次数；重试身份另保留 attempt | 同名阶段多次执行仍是不同事实；节点键不能只用 stage 名 |
| `source_seq` | 来源生产端在接受阶段更新时产生的递增整数；贯穿存储与转发 | 判定同一来源事件的新旧；不能在轮询接收时重新编号 |
| `progress_revision` | 轮次入口对已接受快照的语义更新递增，随消息快照和 SSE 传递 | 前端只投影较新权威快照，避免再实现一套矛盾的新旧判断 |

`source_seq` 跨 worker 重试继续可比较；使用新执行代次时也可采用明确的代次 + 序号比较，但不得直接把新代次的 1 与旧代次的高序号混比。worker 写入应校验当前任务 / 尝试的所有权，避免旧 producer 迟到写入获得一个更大的新序号。序号应与对应快照在同一次受保护更新中保存。

优先沿用现有阶段写入口（worker 的 `set_run_stage` 及对话本地阶段入口）生成事实。只给消费者加本地计数，或按 updated_at 排序，**不能证明来源次序，不算修复**。

这只是当前阶段投影的有限演进，不要求保存无限事件历史、建设事件重放系统或修改业务执行顺序。若实现选择使用等价的显式状态机，须证明覆盖下表全部场景；不能以固定阶段排名替代执行范围。

### 4.3 合并规则与自动成功推断

1. 先解析来源及顺序，得出“推进当前 / 更新同实例 / 仅补历史 / 重复 / 无法归属”的裁决，再做任何终态推断和持久化。
2. 同来源较旧事件只允许补相应历史节点，不修改当前 stage、label、status、起点、身份、错误类别和 last_finished_stage；不把当前阶段推断为成功。
3. 同阶段实例、同 attempt：重复 running 不重置起点；重复终态可补同状态耗时；冲突终态保留首个事实并给出安全诊断。迟到 begin 不重开已终结实例。
4. 不同 stage_instance、较新且属于当前活动来源的事件才有资格推进。缺失 begin 但有可信较新终态时，可直接投影该真实终态；不能因为“run 不同且状态 terminal”一概丢弃合法新执行。
5. 切换到新活动工具 / run 由轮次编排的明确开始或绑定动作确认；旧 run 的迟到 begin 也不能仅凭 running 状态冒充新执行。
6. 删除当前“换阶段即成功”的无条件推断。只有同执行范围内、已验证的顺序转换明确保证前一步成功时才允许推断；失败、取消、并行分支、未知 / 略过阶段不能推断。能从源端取得明确结束事实时优先使用明确事实。
7. 跨阶段更新所有顶层相关字段，label 从当前 stage 生成或使用该事件权威值，不保留上一阶段标签；身份、起点、错误类别同步更新。
8. 节点去重键包含阶段实例及执行身份；保持历史失败和现有节点数量上限。节点被截断后仍应有独立的新旧裁决依据，不能依赖“旧节点还在列表里”才能防回退。

### 4.4 端到端传递与旧数据兼容

- worker 快照 → `_stage_update` → `_update_marker` → workflow → `on_event` → 消息快照 → SSE / 轮询 → store，完整保留所需来源字段；有意义的序号变更参与去重，不引入逐轮询写放大。
- 推荐在现有 SSE 阶段相关事件中附带**合并后快照及 progress_revision**；前端用它更新顶层阶段，原始事件字段仍用于工具卡片等现有用途。避免同一条事件先按原始字段更新一次、再按权威快照更新一次。
- `progress_revision` 按同一消息 / turn 比较；切换会话或新消息重置比较范围，不做全局 revision 比较。相同 revision 的幂等快照不重置计时。
- 心跳只更新活动时间，不能因此增加阶段 revision；保持 E7OBS2-06 的原子续约和终态保护。
- 新字段先作为兼容性可选字段。旧快照仍可显示；无可靠来源次序的旧事件不能覆盖有明确身份 / 序号的新执行。旧事件只在空快照初始化、同一可确认实例补字段或明确兼容转换时接收。
- 刷新从数据库恢复权威快照，不重新猜阶段顺序。API 模型、normalize、序列化必须保留新字段；生成类型后检查 store / 视图是否真正消费。

### 4.5 必要回归与完成标准

| 用例 | 期望 |
| --- | --- |
| 同 run：report running → 迟到 draft succeeded | report 仍 running；label / 起点 / 身份不变；draft 只补历史；report 不被推断成功 |
| 同 run：report running → 迟到 draft running | 不回退、不重开旧实例 |
| 同 run：多个热点均有 clue / draft | 热点及阶段实例分开；后一个热点合法开始不会被全局阶段排名拦截 |
| 同名工具两次、两个 run | 新活动执行可从低 attempt 开始；旧 run 的 begin / end 都不接管当前 |
| worker 重试、旧 producer 迟到 | 新尝试不被旧尝试覆盖，来源序号及所有权检查有效 |
| 只收到可信新执行终态 | 不因缺 begin 或 run 冲突无条件丢弃；按活动来源绑定裁决 |
| 同实例重复 / 冲突终态、耗时补报 | 幂等，不翻状态；允许可信同状态耗时修订 |
| 节点超过 MAX_NODES、旧格式快照 | 截断不破坏当前守卫；兼容边界有测试 |
| SSE 与刷新 / 轮询交错 | 两条通道得到相同当前阶段、状态、身份、label、起点和 revision |
| supervisor 取消、历史失败、worker 终态 | 保持 E7OBS2-03 / 07 的已通过语义 |

完成标准是**源端生成、数据库存储、SSE、前端、刷新**使用同一裁决事实。纯 progress 函数测试通过不足以宣布收口；至少一条受控真实存储链路与前端交错事件回归，加浏览器显示核对。

## 5. E7OBS3-03：明确零值与混合来源被误标

### 5.1 已复现行为与补查范围

- [tools/llm.py](../src/xhs_agent/tools/llm.py) 的 `_result` 用 `usage.get(...) or estimate_tokens(...)`。供应商明确返回 0/0，离线复现得到 14/3 tokens，却标为 actual；金额也会随非零单价被错误放大。
- [chat_tools.py](../src/xhs_agent/services/chat_tools.py) 的 `_records_usage_status` 对 actual 的优先级高于 estimated。窗口含 actual + estimated 时，汇总返回 actual。
- [tools/vision.py](../src/xhs_agent/tools/vision.py) 也使用零值触发估算，且仅凭输入侧存在就判 actual；属于同一模式的静态确认，须补适配器回归，不应只修文本模型。

本轮从真实适配器响应解析开始验证，不能只人工构造 `LLMResult(usage_status="actual", tokens=0)` 后测试上层。

### 5.2 方向字段解析规则

1. 区分字段缺失 / null 与明确数值 0。合法非负整数（含 0）直接保留；不要用 truthiness 或 `if not tokens` 判缺失。
2. 输入、输出两个方向独立判断。均有合法供应商用量才可将整次记录标为 actual；一侧缺失且采用估算，整个调用为 estimated，并保留哪侧实际 / 哪侧估算的可查询信息。
3. 非法值（bool、负数、小数、非有限值、协议不支持的字符串）不能直接转 int 后标 actual；采用明确错误 / unknown 记账路径，保留已知合法部分，不能静默清零后伪装完整。
4. 兼容 SDK / 供应商字段别名时在对应适配器归一化，不能在各上层复制不同的兜底规则。流式、非流式和原生工具调用路径都检查。
5. 缺 usage 的文本估算只描述估算能力；视觉仅靠文字字符数不能恢复图片真实 tokens，继续明确它是下界 / 不完整估算，不包装成实测。
6. 成本使用本次保留 / 估算后的用量与现有价格配置计算。供应商零用量、价格为零都可以是实际请求，不能自动变成 cached 或无调用。

### 5.3 来源汇总规则

对确实发生的模型组件，汇总采用保守降级：**unknown > estimated > actual**。同时保留逐组件来源或等价分类计数，不能只留下一个总标签而抹掉混合事实。

| 窗口内容 | 汇总及含义 |
| --- | --- |
| 全部 actual，包括合法 0 | actual；有真实请求，数值可以为零 |
| actual + estimated / 全部 estimated | estimated；保留实际与估算部分的来源 |
| 任意 unknown，或模型组件缺来源 | unknown；已知金额与 tokens 仍保留，usage_complete 为 false |
| 全部 cached | cached；本轮无新增模型消费 |
| cached + 实际调用 | cached 不把真实调用降为缓存；按真实调用集合汇总 |
| 空窗口 / 纯查库工具 | 不凭空制造 actual / cached 请求；保留无模型消费语义 |

缺来源但全零的**模型调用记录**也不能当作纯查库；是否发生模型调用由组件类型 / 调用事实确定。纯查询工具和模型记录不能仅因为数值都为零就混为一类。

`usage_complete` 沿用“均可解释”，estimated 不必因此改成 unknown；如需表达“全为实际值”，用逐组件来源 / 计数推导，不能偷换既有布尔字段含义。字段新增先写契约，并保证 API 序列化不会丢掉来源。

### 5.4 必要回归与完成标准

- 用 MockTransport / 固定 SDK 响应覆盖文本和视觉：0/0、0/正数、正数/0、缺一侧、全部缺失、非法数值；从适配器结果断言，不绕过解析器。
- actual 零用量配非零价格后仍为零成本；非零用量配零价格仍为真实调用。
- 同一 StructuredCaller 窗口发生 JSON 修复 / 多次调用，actual + estimated 汇总不得为 actual；unknown 和缺来源组合不得被已知记录掩盖。
- 缓存与真实调用混合、纯查库、取消前部分调用，验证组件集合不双计，与 E7OBS3-01 的账本一致。
- 贯穿服务 → 工具 → 消息存储 / API → trace metadata，实际值不被中途 truthiness 替换，前端刷新可读来源按契约保留。

完成标准：**实际零保持零，估算不会宣称 actual，未知不被混合窗口掩盖**；历史记录不批量回填为 actual，不把旧错误金额当作可无损重算的事实。

## 6. E7OBS3-04：成本分项与整数用量校验不完整

### 6.1 已复现输入

定位：[check_trace_chain.py](../scripts/check_trace_chain.py) 的 `_valid_number` / `probe_cost` / `probe_usage`、叶子判断及 `_ledger_check`。

| 输入 | 当前错误结果 | 修复后 |
| --- | --- | --- |
| costDetails = {input: -1, output: 0, total: 0} | valid，0 元 | invalid：非法分项不能被 total 掩盖 |
| costDetails = {input: 1, output: 2, total: 0} | valid，0 元 | invalid：总额与分项不一致 |
| usageDetails = {input: 1.9, output: 2} | valid，(1, 2) | invalid：不能截断小数 token |

已修复的 Decimal 数据库边界、显式零值、纯 JSON stdout、同边界耗时比较继续保护，不重新改回只认 int / float。

### 6.2 解析及一致性规则

1. 分开“有限非负金额”和“有限非负整数用量”两个验证器，不让成本可用小数的规则流入 tokens。
2. 保留 Decimal，校验其有限性、符号及整数性后再转换。避免先转 float 导致溢出、精度丢失或异常；解析层应对极大值安全返回无效 / 不支持，不能崩溃或截断。
3. tokens 可以接受数学值为整数的受支持数值，如 `2`、`2.0`、`Decimal("2")`；拒绝 `1.9`、bool、负数、NaN / Inf 和任意字符串。若支持范围存在精度限制，在适配器 / 脚本说明中明确，不悄悄舍入。
4. `costDetails` 有 total 时，仍校验已提供的分项。支持 total-only、input+output-only、三者同时存在；仅提供一个方向的非空分项形状判 invalid，不擅自把另一方向补零。
5. 三者同时存在时验证 total 与 input + output 一致。使用十进制规范化处理浮点表示误差，单独规定并测试来源舍入精度；不能借此扩大轮次 / 账本的原有差异容差，不能容忍 1+2 却 total=0。
6. 支持的 usage 方向别名需要同时齐全；有 total 时验证 total 是合法整数且与方向和一致。缓存 / 推理 tokens 等可能为子集的字段不盲目重复相加，先说明支持形状。
7. 看到权威字段非法时立即判 invalid，不能再退到其他合法别名或备用总额把它隐藏；多个受支持别名同时出现且矛盾时明确报冲突。
8. 缺字段、null 或空对象可按既有协议表示 missing；非空错误类型、非法值、冲突值属于 invalid。把 missing / invalid 的映射写成测试表，不用宽泛异常捕获返回 0。
9. `unknown` 只解释缺证据，不能赦免非法数字。合法已知部分可单列展示，但包含非法组件的整体核对不能显示通过。
10. 叶子检查、树展示、求和、账本比较使用同一解析结果。对真实供应商额外成本维度先核对脱敏响应，再扩展支持；不把陌生非空结构直接视为有效。

### 6.3 CLI 与必要回归

保持现有退出码语义：0 = 全部硬口径通过且无待验证项；1 = 核对失败；2 = 输入 / 环境等执行错误；3 = 有待验证项。`--json` stdout 仍只能是单个 JSON，说明走 stderr；保存文件与 stdout 的结论一致。

新增测试至少覆盖：

- total 合法但分项为负数 / 字符串 / bool / 非有限值；分项合法但 total 错误。
- 三者一致、三者不一致、total-only、仅合法分项、仅一侧、显式全零。
- float 0.1 + 0.2 的表示误差、Decimal 精确值、极大 Decimal、精度边界；与来源精度政策一致。
- 小数 tokens、整数形式 float / Decimal、缺方向、重复别名冲突、usage total 不一致。
- unknown 与非法值同时存在；叶子校验和账本校验均失败，不出现一处通过一处失败。
- 通过 / 失败 / 待验证 / 输入错误的 CLI：JSON 可解析，退出码正确，未调用付费模型。
- 既有 Decimal 落库成本、轮次时间窗、人民币 / 配置折算说明及父子层去重全部保留。

完成标准：上述三个复现输入全部不再误通过；同一来源数据在叶子、求和和 CLI 结果中没有口径分裂。
