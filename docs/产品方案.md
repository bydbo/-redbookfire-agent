# 小红书热点搭子 · 产品方案（v1）

> 英文副标：Hotspot-to-Material Relevance Agent
> 形态：本地单人工具（按可部署标准设计）
> 能力边界：从热点输入，到候选素材 + 文案初稿
> 配套文档：《简历与面试》（`docs/简历与面试.md`）

## 一、用户视角的一天

周三晚上十点，我刷到“某顶流明星打羽毛球”冲上热搜。评论区在玩梗，品牌号已经在剪同款了。我知道这波能蹭，因为我硬盘里躺着去年秋天在球馆拍的一大堆素材——挥拍的、捡球的、跟朋友打双打的，竖屏、有光、还能用。

问题是我不知道那些文件叫什么。

`DSC_0431.MP4`、`球场_1.mp4`、`未命名 3.mov`，还有一堆导完就忘了的文件夹。我打开资源管理器，从“视频素材”翻到“录像”再翻到“剪映草稿”，一帧一帧点开看，四十分钟过去了。等我把能用的镜头挑出来，热搜已经掉出前二十，品牌号的同款早发了三轮。

热点的窗口期只有 24 到 48 小时。而我花在“找素材”上的时间，比拍这些素材的时间还长。

这天我换了个做法：把“某顶流明星打羽毛球”这句话粘进热点搭子，三分钟后拿到一张表——

五条候选镜头，按相关度排序，每条告诉我**命中了热点里的哪个点**（是“羽毛球”这个主题，还是“球场”这个场景，还是“慢动作”这个画面），**建议怎么用**（放开头三秒，还是当过程画面）。表下面还有一栏写着：这个热点你还缺“挥拍特写”，建议补拍；以及一句提醒：涉及明星本人姓名和肖像的部分不能用，走“同款动作”的表达。

最后是它给我的一版初稿：三个标题备选、一句封面字、开头三秒的设计、正文、话题标签、剪辑顺序。

我没让它替我发。我要的本来就不是“发什么”，而是**在我拍过的东西里，哪些能接上今天的热点**。

## 二、问题与机会

### 2.1 三个真实痛点

**痛点一：素材检索靠记忆，而热点不等你。**
创作者的素材库随时间膨胀到几百上千条，命名靠手写、归档靠心情。检索手段只剩下“记得大概在哪”和“一个个点开看”。热点的时间成本结构是反的——内容可以糙一点，但必须快。

**痛点二：通用大模型看不到“我有什么”。**
让大模型写“明星打羽毛球”的文案，它能写得挺好，但它不知道我手上没有羽毛球素材、只有一段攀岩视频。写出来的东西拍不出来，等于没有。文案问题是伪问题，素材匹配问题才是真问题。

**痛点三：热点分析工具给的是行业数据，不是我的可用库存。**
数据看板能告诉我“这个话题热度涨了 320%”，但答不上“我能不能蹭、用哪条素材蹭”。热度和我硬盘里的文件之间，缺一层翻译。

### 2.2 机会点

把“热点解析”和“私人素材检索”用一层**可解释的爆点要素模型**接起来。

热点不是要整体复制，而是可以拆成若干“蹭点”：哪些点是热度的真实来源，哪些点我用自己的素材也能复现，哪些点碰了会出事。把这层拆解显式化，匹配就从“猜关键词”变成了“按要素对齐”——**能对齐的就有理由，对不齐的就明确告诉你缺什么**。

### 2.3 竞品格局

| 类型 | 代表 | 提供什么 | 缺什么 |
| --- | --- | --- | --- |
| 数据看板 | 新红、千瓜 | 行业热度趋势、竞品笔记数据 | 不知道用户手上有哪些素材 |
| 通用大模型 | ChatGPT、豆包、DeepSeek | 文案、选题灵感 | 看不到私有素材库，产出无法落地 |
| 剪辑工具内 AI | 剪映 | 成片阶段的字幕、口播、配乐 | 不进素材检索环节，等素材选完才登场 |
| 平台内置创作工具 | 小红书创作助手 | 基础 AI 写作、标题优化 | 无个人素材的语义层，也不做相关性判断 |
| **小红书热点搭子（本方案）** | — | 热点 → 我的素材 → 初稿，每条结论可解释、可复现 | 单机运行，需要用户自己建素材库 |

差异化只有一句话：**别人告诉你热点有多热，热点搭子告诉你这个热点里有多少是你现在就能用的。**

## 三、目标用户与场景

### 3.1 主用户

**囤了大量素材、但找不到的个人创作者。**

特征：更新频率在一周 2 条到日更之间；素材自拍自剪，累积了几百上千条；垂类明确（运动、美食、职场、萌宠、家居等）；对热点的态度是“想蹭但怕踩雷、想快但找不到”。

不服务的人群：纯搬运号（没有自有素材）、机构级内容团队（需要多人协作与素材共享，见路线图）。

### 3.2 三个典型场景

| 场景 | 触发 | 期望产出 | 频率 |
| --- | --- | --- | --- |
| 临时蹭热点 | 刷到热搜，10 分钟内想判断能不能蹭 | 候选素材 + 命中理由 + 风险提醒 | 每天 1–3 次 |
| 备稿排期 | 一次输入 3–5 个热点，横向比较 | 哪个热点覆盖度最高、哪条最快能出 | 每周 1–2 次 |
| 复盘补拍 | 发现线索里的关键要素自己都没有 | 缺口清单 + 补拍建议 | 每周 1 次 |

第二个和第三个场景是这个工具区别于“一次性热点分析”的地方：**它同时是选题助手。** 覆盖缺口那一栏，长期积累下来就是一份“我该补拍什么”的清单。

## 四、核心流程

```
①  粘贴热点（1..N 条）
        │
        ▼
②  拆解火因  ──►  为什么能火（2–3 条机制）
        │          爆点要素表（9 类，带权重与置信度）
        │          可蹭角度 + 风险提醒
        ▼
③  要素分层  ──►  可迁移要素（羽毛球／球场／慢动作／热血）
        │          不可直用要素（明星姓名、肖像、代言暗示）
        ▼
④  素材检索  ──►  Top-K 候选，每条给出：得分、命中了哪个要素、
        │          为什么相关、建议怎么用
        ▼
⑤  覆盖缺口  ──►  哪些线索有素材、哪些没有、建议补拍什么
        ▼
⑥  文案初稿  ──►  标题备选／封面字／前 3 秒／正文／话题／剪辑顺序
        │
        ▼
    报告落盘（HTML + Markdown + 运行轨迹）
```

用户视角的操作只有三次：**粘贴热点 → 等一会儿 → 看报告**。

第③步是这套流程里最容易被忽略、但最关键的一环。用户的原话是“火的线索可能有明星 IP、羽毛球，或者两者结合”——这里其实藏着两件完全不同的事：明星 IP 是**不可直用**的（用了就是肖像和代言风险），羽毛球和球场是**可迁移**的（我拍过就能蹭）。把这两者混在一张关键词表里，结果就是要么不敢用，要么乱用。方案要求把它们显式分开（见第六节）。

## 五、功能优先级

### P0 · v1 必须能跑通

| 能力 | 说明 |
| --- | --- |
| 热点手动输入 | 支持一次粘贴 1 到 N 条热点（话题句或链接文本） |
| 爆点线索拆解 | 火因机制、要素表、可蹭角度、风险提醒、目标人群 |
| 素材库索引 | 扫描本地目录，支持旁车文件人工说明，支持多模态抽帧自动打标 |
| 增量更新 | 素材按“路径 + 修改时间 + 大小”判断是否变化，只重跑变动的 |
| 相关性检索 | 确定性加权打分，输出 Top-K 候选 |
| 匹配解释 | 每条候选必须说明命中了哪个要素、建议怎么用 |
| 覆盖缺口 | 输出缺失要素与补拍建议 |
| 文案初稿 | 标题备选、封面字、开头 3 秒、正文、话题标签、剪辑顺序 |
| 报告产出 | 单文件 HTML + Markdown，含本次运行的成本与耗时 |
| 启动前置检查 | 启动时校验密钥、数据库与队列的可用性，任一缺失立即报错（不做静默降级） |

### P1 · 有明显价值，v1.1 补齐

- 多热点横向对比：一次输入多个热点，按覆盖度与最高分排序，帮你决定先做哪个。
- 历史运行回看：复用上周拆过的线索，避免重复分析同一个热点。
- 素材复用记录：哪条素材被哪个热点用过，避免反复用同一批镜头。
- 自定义要素词典：用户补充自己垂类的词（例如“飞盘”“腰旗橄榄球”“三坑穿搭”）。
- 旁车文件模板：一键生成 `.mp4.txt` 说明模板，降低人工打标的启动成本。

### P2 · 路线图，不在 v1 范围

- 自动抓取小红书 / 微博 / 抖音热榜，主动推候选热点。
- 发布后排期与效果回流（回填播放与互动数据，反推哪类线索对账号有效）。
- 剪映草稿导出。
- 多人协作与共享素材库。

### 明确不做

- 不代替用户发布内容。
- 不生成或建议使用他人姓名、肖像、品牌代言话术。
- 不爬取平台数据（评测集为自建标注样本）。

## 六、爆点要素模型

### 6.1 九类要素

热点的“火因”被拆成九个维度。同一个维度内才互相比较，避免“羽毛球”和“热血”被算法算成相似。

| 类型 | 标签 | 默认权重 | 含义 | 明星打球例 |
| --- | --- | --- | --- | --- |
| `topic` | 主题 | 1.00 | 内容主题 | 羽毛球 |
| `ip` | 人物 IP | 0.90 | 明星、达人、企业家、素人标签 | 明星艺人 |
| `scene` | 场景 | 0.70 | 拍摄地点与空间 | 球场 |
| `conflict` | 反差结构 | 0.70 | 身份反差、预期违背 | 顶流 vs 业余水平 |
| `format` | 形式 | 0.65 | 同款、跟练、教程、测评 | 同款 |
| `emotion` | 情绪 | 0.60 | 反差、治愈、解压、共鸣 | 热血 |
| `visual` | 画面 | 0.55 | 慢动作、特写、对比分屏 | 慢动作 |
| `audience` | 人群 | 0.50 | 打工人、学生党、宝妈 | 学生党 |
| `sound` | 声音 | 0.35 | BGM、原声、口播 | 现场音 |

默认权重表达的是“这个维度对热度的贡献有多大”——主题和人物 IP 最重，声音最轻。权重可配置，不写死在算法里。

### 6.2 借势不直用：要素分层规则

这是本方案对原始想法最重要的一次修正。热点的要素**不能平等对待**：

| 要素类型 | 能否直接使用 | 处理方式 |
| --- | --- | --- |
| `topic` 主题 | 可迁移 | 正常加权，是蹭热点的主力 |
| `scene` 场景 | 可迁移 | 正常加权 |
| `visual` 画面 | 可迁移 | 正常加权，慢动作、特写这类手法可以复刻 |
| `format` 形式 | 可迁移 | 正常加权，同款、跟练是最常见的蹭法 |
| `emotion` 情绪 | 可迁移 | 正常加权 |
| `audience` 人群 | 可迁移 | 正常加权 |
| `conflict` 反差结构 | 可迁移 | 结构可复用，但不涉及具体人身 |
| `sound` 声音 | 谨慎 | 有版权风险，只建议原创或已授权音频 |
| `ip` 人物 IP | **不可直用** | 降权，转为“同款动作 / 原型”表达，禁止姓名与肖像 |

落地方式：通过配置项 `match.element_type_weights` 把 `ip` 权重压到 0.3–0.5，即可让“素材里没有明星”不再拉低匹配分——**因为素材本来就不该靠明星才能成立**。这一点不需要改算法，是配置层面的规则。

于是“明星打羽毛球”这个热点，在系统里长这样：

```
可蹭点（我拍过就能用）        不可蹭点（碰了会出事）
─────────────────────        ─────────────────────
topic    羽毛球               ip      明星本人姓名
scene    球场                         肖像、代言暗示
visual   慢动作
format   同款
emotion  热血
audience 学生党
```

用户拿到的不是“你要有明星才能发”，而是“**把你去年在球馆拍的挥拍镜头，用慢动作剪一遍，配一句‘以为是新手，结果是高手’的开头**”。

## 七、匹配与解释机制

### 7.1 为什么不让大模型排序

大模型排序有三个问题：结果不稳定（同一批输入两次结果不同）、无法复现（自己或面试官都无法复算）、成本随素材量线性增长（一千条素材就是一千次调用）。

热点搭子的分工是：**大模型负责“判断”，算法负责“检索”。** 拆解火因、写解释、写初稿交给模型；素材排序交给确定性算法。

需要说清楚的是：引入向量召回**不违反**这条原则。语义召回同样是确定性检索（同一批向量、同一套相似度计算，结果可复算），改变的是召回手段，而不是把排序权交给模型。

### 7.2 打分口径

对每个线索要素，计算它在某条素材上的贡献：

```
贡献   = 要素权重 × 要素置信度 × 类型权重 × 最佳相似度
相关度 = Σ贡献 / Σ(要素权重 × 要素置信度 × 类型权重)
最终得分 = 相关度 × (0.9 + 0.1 × 画质适配度) + 时效加成
```

- **相似度**三档：完全相等记 1.0；互相包含按长度比例记 0.72–0.95；否则按中文二元字组重合度计算。
- **命中阈值**：相似度 ≥ 0.5 才算命中，低于阈值计入“缺失要素”。
- **画质适配度**：竖屏、分辨率高、时长 4–60 秒的素材得分更高（贴合小红书的形态偏好）。
- **时效加成**：30 天内入库 +0.02，365 天以上 -0.03。
- **关键词直击**：线索里的关键词如果在素材文案里原样命中，相似度直接记 0.9。

### 7.3 举一个能复算的例子

线索取三个要素：`ip 明星艺人`（权重 0.9、置信度 0.75）、`topic 羽毛球`（1.0 / 0.75）、`scene 球场`（0.7 / 0.75）。

素材是 `球场挥拍-傍晚-羽毛球_双打.mp4`，1080×1920 竖屏、25 秒、上周入库。它命中了 `topic` 与 `scene`，未命中 `ip`：

```
分母 = 0.9×0.75×0.9 + 1.0×0.75×1.0 + 0.7×0.75×0.7 = 1.725
分子 = 0              + 1.0×1.0      + 0.7×1.0      = 1.1175

相关度 = 1.1175 / 1.725 = 64.8%
画质   = 竖屏 + 高清 + 时长合适 = 1.0
得分   = 0.648 × (0.9 + 0.1×1.0) + 0.02 = 0.67 → 67%
覆盖度 = 64.8%（三个线索要素里有两个被这条素材覆盖）
```

把 `ip` 权重压到 0.4 之后，分母变成 0.27 + 0.75 + 0.3675 = 1.3875，相关度升到 80.5%，得分 83%。**素材一个字没改，是“不该靠明星”这条产品规则在起作用。**

### 7.4 可解释性的硬约束

每条候选素材必须带三样东西，缺一不可：

1. **命中了哪个要素**（类型 + 线索取值 ↔ 素材取值），例如“主题：羽毛球 ↔ 素材标签 羽毛球”。
2. **为什么相关**（一句人话解释）。
3. **建议怎么用**（放开头 3 秒 / 当过程画面 / 作收尾提问镜）。

系统里不允许出现“无理由相关”的候选。分数再高，也要能说出它是靠哪个要素拿到的分。这条约束同时是可信度的来源和评测的基础——**可解释的分数才能被人工判定对错**。

### 7.5 覆盖缺口

所有线索要素逐个检查是否有素材命中，加权汇总成覆盖度：

- 覆盖度高 → “线索要素都有素材覆盖，可以直接剪”。
- 覆盖度低 → 逐条列出缺口，例如“缺少 [画面] 慢动作相关素材 → 建议补拍或去素材库再捞”。

## 八、产出物形态

### 8.1 报告结构

一次运行产出一份单文件 HTML（自带样式，双击即开，方便发给别人看）和一份 Markdown（方便复制到别处）。

| 区块 | 内容 |
| --- | --- |
| 机会总览 | 一张表：每个热点的覆盖度、最高分、首选素材 |
| 为什么能火 | 2–3 条机制，说明这个热点靠什么留住人 |
| 热点线索 | 要素表：类型、取值、权重、置信度、依据 |
| 可蹭角度 | 3–4 条具体切入方式，用“不侵权”的表述 |
| 素材匹配榜 | 排名、素材、得分、命中要素、建议用法，附关键帧缩略图 |
| 覆盖缺口 | 缺失要素 + 补拍建议 |
| 初步文案 | 标题备选、封面字、开头 3 秒、正文、话题标签、剪辑顺序、合规提醒 |
| 本次运行 | 模型调用次数、Token 用量、预估成本、总耗时、**向量覆盖率**（本次参与检索的素材中有向量的比例，用于暴露语义召回是否静默退化） |

### 8.2 落盘结构

```
runs/20260929-213000-某明星打羽毛球/
├── state.json      # 每一步的状态、耗时、token、成本
├── trace.jsonl     # 逐条事件流，便于排查
├── report.html     # 给人看的报告
└── report.md       # 给复制用的版本
runs/_index/        # 素材索引缓存与关键帧
```

产物落盘带来两个好处：**可回看**（这周判过哪些热点、当时怎么判的）、**可审计**（哪一步花了多少钱、哪次调用失败了）。

### 8.3 演示证据（供面试与开源展示）

为了让方案可被验证，需要两份配套材料：

**脱敏示例素材包**：12–20 条视频/图片，外加同名旁车说明文件。构图覆盖四类场景——运动（球类、跑步）、美食（家常菜、探店）、职场（工位、通勤）、宠物（猫、狗），并刻意混入若干“命名混乱、无说明”的文件，用来展示视觉打标前后的对比效果。

**样例报告**：用示例素材包跑一次“明星打羽毛球”、一次“节后减脂”，产出真实报告，作为 README 的展示图和面试时的现场演示材料。

## 九、合规边界

蹭热点这件事的风险不在技术，在使用。方案把三条红线写进产品，而不是塞进免责声明：

**红线一：不输出他人身份信息。**
报告中不出现明星、达人、企业家的姓名，也不建议在文案中使用。涉及人物 IP 的要素一律降权，并转换为“同款动作”“原型”“平替”这类表述。

**红线二：不使用他人肖像与未授权素材。**
用户素材库中的文件由用户自行保证来源与授权。系统只做相关性建议，不判断版权归属，并在每份报告的合规提醒里显式说明这一点。

**红线三：不暗示代言与合作关系。**
当线索中出现人物 IP 时，系统主动提示“不要暗示商业合作或代言关系”。

此外，声音类要素单独标注版权风险，只建议使用原创或已授权音频。

> 本工具输出的是**相关性建议**，不构成法律意见。是否发布、如何表述，由用户自行决定并承担责任。

## 十、评测与指标

### 10.1 评测集设计

20 组“热点 → 正确素材”标注样本，每组包含：一条热点文本、素材库快照、人工标注的正确答案（哪几条素材算相关）。

| 场景类型 | 组数 | 示例 |
| --- | --- | --- |
| 明星运动 | 5 | 明星打球、明星跑步、明星健身房 |
| 节目与影视梗 | 4 | 综艺名场面、热播剧台词梗 |
| 节日与节气 | 3 | 节后减脂、入秋穿搭 |
| 生活方式 | 5 | 露营、咖啡、收纳改造 |
| 职场话题 | 3 | 通勤、加班、跳槽 |

样本自建标注，不爬取平台数据。标注者与被评测者分离，避免自己判自己。

### 10.2 指标口径

> 七维度评测口径（事实准确率 / 幻觉 / Tool 选择 / 任务完成率 / 输出结构 / 成本 / 速度）与用例格式见 `docs/评测集.md`；下表给的是对外展示的目标值。

| 指标 | 口径 | 目标值（待实测） | 测量阶段 |
| --- | --- | --- | --- |
| Top-5 命中率 | Top-5 候选中至少一条属于人工标注正确答案的比例 | ≥ 80% | E2（检索层） |
| 首选命中率 | 排名第一的候选属于正确答案的比例 | ≥ 50% | E2（检索层） |
| 线索覆盖度 | 被素材命中的线索要素权重 / 全部线索要素权重 | ≥ 60% | E2（检索层） |
| 单次耗时 | 单个热点从输入到报告完成（不含首次建索引） | ≤ 60 秒 | E2（仅拆解 + 检索）；E3 端到端复测 |
| 单次成本 | 单个热点的模型调用成本（按 DeepSeek 高价时段折算人民币） | ≤ 0.05 元 | E2（仅拆解 + 检索）；E3 端到端复测 |
| 文案可用率 | 人工 1–5 分打分（是否可直接改写使用），取均值 | ≥ 3.5 | **E3 之后**（撰稿编排在 LangGraph，E2 阶段无产出物可打分） |

### 10.3 基线对比

简历上的量化成果必须来自可复现的对照实验，因此设计两组对照：

| 方案 | 做法 |
| --- | --- |
| 基线 | 纯关键词子串匹配：热点文本切片后直接在素材文件名与说明里做包含判断 |
| 本方案 | 要素类型加权 + 爆点词典 + 视觉标签 + 关键词直击；改造后升级为 pg_trgm 字面召回 + pgvector 语义召回的混合检索（RRF 融合） |

在同一批 20 组用例上跑，输出两组指标与提升幅度。**这是整个项目最硬的证据**：它证明的不是“我做了个工具”，而是“我知道怎么度量一个 AI 应用有没有变好”。

### 10.4 验收标准

1. 密钥、数据库与队列都可用的前提下，端到端跑通并对同一批输入产出结构完整的报告（项目不做运行时降级，缺依赖时报错是预期行为）。
2. 20 组用例全部可复现：同样的素材库快照 + 同样的热点，得到同样的排名（检索环节确定性）。
3. 每条候选都有命中要素与用法说明，不存在无理由候选。
4. 评测结果表填入本文档，替换掉“待实测”。

## 十一、Agent 技术架构

### 11.1 为什么这是 Agent，而不是一条流水线

面试官的第一个问题大概率是“这不就是 if-else 吗”。回答要落在三个地方：

**第一，有自主决策环节。** 热点是开放文本，要素怎么拆、拆出几个、权重给多少，没有固定规则，必须由模型结合上下文判断。同一句“明星打羽毛球”，在不同账号定位下该拆出的可蹭点并不相同。

**第二，有失败自愈。** 模型输出的结构化 JSON 解析失败时，系统会把错误信息回灌给模型要求自修重试，而不是直接崩掉、也不是在报告里显示一段乱码。这是 Agent 与“提示词加正则”的区别。

**第三，有显式状态机与全链路追踪。** 编排由 LangGraph 状态图承担：每一步是一个节点，节点之间按条件流转，失败可重试、可断点续跑；每次运行的 token、成本、延迟与失败原因都写入 Langfuse 与结构化日志，按 run_id 串起来。能说清“这一步为什么被触发、花了多少、失败在哪”的系统，才是可运维的系统。

### 11.2 四层分工

| 层 | 职责 | 用什么实现 | 为什么 |
| --- | --- | --- | --- |
| 编排层 | 状态流转、重试、断点续跑、进度上报 | LangGraph 状态图 | 需要显式、可观测、可恢复的执行流程 |
| 线索拆解层 | 火因、要素、可蹭角度、风险、目标人群 | 大模型 + 结构化契约 + 解析失败自修 | 需要语言理解与领域判断 |
| 相关性检索层 | 素材打分、排序、覆盖度 | 确定性算法 + 混合召回（字面 + 向量） | 需要可复现、可解释、可评测 |
| 解释与撰稿层 | 命中原因、建议用法、文案初稿 | 大模型 + 结构化契约 | 需要自然语言生成 |

大模型只出现在两头，中间最关键的排序环节留给算法——**这条边界是整个架构的核心决策**，它同时决定了可复现性、可解释性和成本结构。

编排框架负责流程，检索算法负责质量——两者职责不重叠。

### 11.3 数据契约

五类结构构成系统对外接口，全部由 **Pydantic v2 模型**定义（改造后替换当前的 dataclass 实现），既是代码契约，也是 API 与数据库写入的校验层。所有模型产出必须先落成结构，才允许进入下一步：

| 结构 | 关键字段 |
| --- | --- |
| 爆点要素 Element | `type`（ip／topic／scene／visual／emotion／sound／conflict／format／audience）、`value`、`weight`、`confidence`、`evidence` |
| 热点线索 HotspotClue | 火因机制、要素列表、匹配关键词、目标人群、可蹭角度、风险提醒 |
| 素材 Material | 路径、类型、标题、描述、标签、要素、时长与分辨率、关键帧、打标来源 |
| 匹配结果 MatchCandidate | 得分、排名、命中要素、未命中要素、相关理由、建议用法 |
| 覆盖度 Coverage 与文稿 Draft | 覆盖比例、已覆盖要素、缺口要素；标题备选、封面字、开头 3 秒、正文、话题、剪辑顺序、合规提醒 |

契约先行的好处是：**模型说人话、程序看结构，两边不会互相污染。** 解析失败能被明确捕获并触发重试，而不是悄悄地污染下游产物。

### 11.4 素材索引链路

素材入库按优先级三层兜底：

1. **旁车文件**（`素材名.mp4.txt` / `.md` / `.json`）：人工写的标题、标签、描述，优先级最高，也最准。
2. **文件名分词**：按 `-` `_` 等分隔符切词作为标签。
3. **视觉理解**：抽取关键帧（默认 3 帧，取 12% / 50% / 85% 时间点）交给多模态模型，输出标题、标签、一句话描述。

索引按“路径 + 修改时间 + 大小”做增量，只有变动过的素材才重新识别——**重复运行时不会重复付费**。

### 11.5 工程完整度（按可部署标准设计）

v1 是本地单人工具，但按企业级标准交付：

- **服务化**：FastAPI 在 `/api` 前缀下提供五个接口（`POST /api/analyze`、`GET /api/jobs/{job_id}`、`GET /api/runs/{run_id}`、`GET /api/runs/{run_id}/report`、`GET /api/health`）；根路径由前端单页应用接管。
- **前端工程**：Vue 3 + Vite + TypeScript 单页应用，含分析台、结果详情与运行历史三个页面；接口类型由 `openapi.yaml` 自动生成，契约一改前端在编译期就能发现偏差。
- **持久化**：PostgreSQL 16 + pgvector 存素材、线索、运行记录与向量；SQLAlchemy 2.0 async + Alembic 管理迁移。
- **异步任务**：Redis + Celery 承接建索引与批量分析等长任务，接口不阻塞。
- **配置外置**：pydantic-settings 统一读取 `.env` 与环境变量，密钥不进版本库。
- **可观测**：structlog 结构化日志 + Langfuse 调用追踪（token、成本、延迟），run_id 贯穿全链路，每次运行可回放。
- **交付**：Docker Compose 一条命令起 api / worker / postgres / redis 四个服务；GitHub Actions 跑 lint、类型检查与测试。
- **质量门**：ruff + mypy + pre-commit；测试用 testcontainers 起真实依赖跑集成用例。
- **不做运行时降级**：缺密钥、连不上数据库或队列时启动即失败并明确报错，用“跑不了就直说”替换“能跑但结果不可信”。

## 十二、成本模型

### 12.1 计量口径

文本模型按 **DeepSeek 官方价目表**计费（美元／百万 token）：`deepseek-flash` 输入缓存未命中 $0.15（低价时段）／$0.3（高价时段），输出 $0.6／$1.2；缓存命中另有更低档位（$0.003／$0.006）。低价时段为 UTC 16:30–00:30，对应北京时间 00:30–08:30，日常使用基本落在高价时段。

项目内部统一按**人民币**记账（`runs.cost_cny`），折算单价在 `config.toml` 的 `[llm]` 段维护。当前示例按 **1 美元 ≈ 7.2 元**、取**高价时段**折算：输入 2.16 元／百万 token，输出 8.64 元／百万 token——取高价是为了不低估成本。中文按约 1.5 字／token 估算。

改造后还需计入两类成本：**嵌入 API**（每条素材与每条线索各一次向量化调用）与**基础设施**（本机 Docker 自托管接近电费级；若上云按最小 Postgres 实例 + Redis 实例估算）。

### 12.2 单次热点分析（素材索引已建好）

| 环节 | 调用次数 | 输入 token | 输出 token | 估算成本（高价时段） | 估算成本（低价时段） |
| --- | --- | --- | --- | --- | --- |
| 线索拆解 | 1 | ~700 | ~900 | ~0.0093 元 | ~0.0046 元 |
| 文案初稿 | 1 | ~1500 | ~900 | ~0.0110 元 | ~0.0055 元 |
| 合计 | 2 | ~2200 | ~1800 | **~0.020 元** | **~0.010 元** |

考虑重试与更长的提示词，实测区间按 **0.02–0.05 元／热点**（高价时段）规划，低价时段约为其一半。一天蹭 5 个热点，月成本约 3–8 元——这是它有机会成为“日用工具”而不是“偶尔打开一次”的关键。

### 12.3 一次性素材索引（视觉打标）

每条素材抽 3 帧，每帧约 1000–1300 图像 token，合计约 3500 输入 token：

```
单条素材成本 ≈ 3500 / 1,000,000 × 视觉模型输入单价
500 条素材首建成本 ≈ 500 × 单条素材成本（一次性，之后增量更新）
```

视觉打标走通义千问 VL（`qwen-vl-max`），输入单价按官方价目表在 `config.toml` 的 `[vision]` 段维护。图像 token 的实际消耗与分辨率相关，量级在几元到几十元之间，且**只在新增或修改素材时才产生**——落地后按首次全量索引的真实用量回填。

### 12.4 成本对比

| 做法 | 单次成本 | 可复现 | 可解释 |
| --- | --- | --- | --- |
| 全部交给大模型（含排序） | 随素材量线性增长 | 否 | 弱 |
| 本方案（模型只在两端） | 与素材量无关 | 是 | 强 |

素材库越大，这个架构决策省下的钱越多。**这是“确定性检索 + 模型判断”这条边界的商业理由，不只是工程洁癖。**

## 十三、路线图

| 阶段 / 版本 | 目标 | 关键内容 |
| --- | --- | --- |
| P1 工程骨架 | 契约与质量基线 | Pydantic v2 契约重构、pydantic-settings 配置、ruff + mypy + pre-commit、`tools/` 首批单测 |
| P2 数据与检索 | 持久化与语义召回 | Compose 起 Postgres + Redis、SQLAlchemy async + Alembic、素材索引与向量入库、混合召回 + RRF、删除离线规则引擎 |
| P3 编排与服务 | 服务化与异步 | LangGraph 状态图、FastAPI 五个接口（`/api` 前缀）、Celery 异步任务、httpx 替换 urllib |
| P4 可观测与交付 | 可运维、可交付 | structlog + run_id、Langfuse、OpenTelemetry、多阶段 Docker 镜像、GitHub Actions CI |
| P5 前端工程 | 把演示页升级为可交互的单页应用 | Vue 3 + Vite + TS、Naive UI + Tailwind、ECharts、`openapi-typescript` 生成接口类型 | 三页可交互跑通；前端类型与契约零偏差 |
| v1.1 | 提升日常使用效率 | 多热点横向对比、历史运行回看、素材复用记录、自定义词典、旁车模板 |
| v2 | 从工具走向助手 | 自动抓热榜、发布后排期、效果回流（用真实数据反推哪类线索有效）、剪映草稿导出 |
| 远期 | 团队场景 | 多人协作、共享素材库、账号矩阵管理 |

### 项目的长期价值

v1 解决的是“这次热点我能不能用”。但每跑一次，系统都会多出一条“热点 → 要素 → 我的素材 → 结果”的记录。当这些记录积累到一定量，就能回答一个更有价值的问题：**我这个账号，历史上靠哪一类线索真正涨过粉。**

那是从“相关性匹配”走向“效果预测”的路。v1 不做，但数据结构必须先留出来。
