## 3. 已冻结的设计

### 3.1 身份与路径

- `materials.id` 继续使用 UUID，不批量重建，不改为路径哈希。
- `materials.path` 为相对当前素材根的正斜杠键，例如 `运动/夜跑.mp4`。绝对文件位置只在文件操作边界按本进程配置解析。
- 一个数据库对应一个逻辑素材库。宿主与容器可以配置不同绝对根，但必须映射同一份完整目录；部分挂载、多素材库不在范围内。
- 路径区分大小写，保留原始 Unicode。大小写歧义进入预检问题清单；不能全局转小写、模糊匹配或按内容相似度合并。
- 不合并不同相对路径下的相同内容，不追踪重命名后的身份。
- `keyframes` 使用其独立索引目录基准；聊天附件使用原有基准，均不能套用素材路径规则。

规范键必须非空，使用 `/`，拒绝盘符、UNC、绝对根、反斜杠、空路径段、`.`、`..` 及控制字符。文件读写在解析后仍须位于允许的素材根 / 回收站根内，不能只做字符串前缀判断。

素材根可以在项目外或其他盘符。根下符号链接、junction、大小写冲突应明确失败；扫描不能静默跳过后把文件当成已删除。保持“空扫描不清库”和“根不可访问明确失败”的既有保护。

历史路径按声明的 Windows、POSIX 或相对来源解析，不依赖当前系统 `os.path` 推断。映射按完整目录段匹配；重叠映射只有得到同一键时才可接受。未知来源、未知根或歧义保持原样并阻断 `apply`，补充映射后重新生成计划，不能删行凑验收。

### 3.2 保留行与候选规则

素材按以下顺序选择整行：`source=sidecar` 优先；其次 `indexed_at` 降序；最后 UUID 升序。保留其整组元数据、向量及向量模型，不拼接出没有真实来源的新记录。其他版本归档。单行也归一化，但文件缺失不能成为删除依据；仅路径变化不改变 `indexed_at`、不清空向量、不重新打标。

候选按 `(run_hotspot_id, canonical_material_id)` 分组，依次按 `score` 降序、原 `rank` 升序、原素材 UUID 升序选整条记录。保留获胜记录原排名，允许空位，不补足 Top-5、不重算分数、不拼接理由。

归档受影响热点的**完整候选集合和运行热点记录**。旧草稿、产物版本、聊天消息、上下文事件及既有报告不批量改写。迁移只改数据库身份及对应候选，不移动、删除或重写媒体、旁车和报告文件。

### 3.3 旧 ID 兼容

持久化 `旧 UUID → 规范 UUID` 的直接映射，禁止链和环；别名不能随当前素材删除级联消失。

详情、关键帧、编辑、回收站、会话素材选择和改稿共用解析能力。当前素材不存在时返回原有明确缺失结果，不能按相同路径重新绑定后来上传的新素材。新引用使用规范 UUID；既有历史引用保留原值。别名解析不能绕过会话、运行及版本归属校验。

改稿依据**实际基础文案的 `material_id`**读取对应候选 / 素材，不能无条件取第一候选。引用缺失、无法确定或不唯一时，调用模型前失败。新结果必须使用规范 ID，且不得修改原草稿和成功版本关系。

### 3.4 持久化与契约

| 数据 | 必须保存的内容 |
| --- | --- |
| 迁移批次 | 批次 ID、规则版本、代码及迁移版本、计划摘要、来源根映射、执行时间、状态、前后计数 |
| 迁移归档 | 批次、实体类型、原主键、完整原始记录和摘要；包括向量、向量模型、时间、Decimal 和 JSON |
| ID 别名 | 旧 UUID、规范 UUID、批次；不依赖当前素材行存在 |

归档来源标记为 `migration_capture`，只证明迁移时数据库保存了什么，不能证明旧运行当时实际使用了什么。默认长期保留，至少 E8 验收前不得自动清理。

表结构由 Alembic 管理并同步 ORM。公共路由保持不变，`MaterialSummary`、`MaterialItem`、`MaterialDetail.path` 统一为素材根相对路径；上传、回收站原有相对路径语义保持一致。同步 [数据契约](contracts/数据契约.md)、[OpenAPI](contracts/openapi.yaml)、[配置契约](contracts/配置契约.md)、[检索契约](contracts/检索契约.md)、[ADR 0017](adr/0017-material-root-relative-identity.md) 及生成类型。

字段仍为 `string` 不代表行为兼容。验收必须断言真实返回值，不能只看 OpenAPI 结构检查。

### 8.2 固定切换顺序

1. 暂停上传、编辑、删除、分析及索引写入，等待在途 API / worker / CLI 任务结束，确认没有旧版本继续写入。
2. 备份数据库，并核验备份可恢复；记录备份标识、代码和迁移版本。演练使用隔离目标。
3. 升级到扩展结构 revision（初稿 `0012`，实施时核对），不改业务数据。
4. 停写状态重新生成最终 plan，审查根映射、问题清单、数量变化、保留 UUID、候选和归档范围。问题非零不继续。
5. 对已审查计划 apply，随后精确 verify；保存结果和批次 ID。失败保持停写，不跳组继续。
6. 升级到约束收口 revision（初稿 `0013`，实施时核对），验证非法写入被拒绝。
7. API、worker、CLI 同步切到审查过的代码及完整挂载视图，通过启动检查和切换冒烟后恢复业务。

空库可直接 `upgrade head`；已有数据的库必须按两阶段流程。不能先在旧系统运行时合并，再逐步替换消费方。不得依赖 Compose 自动 `upgrade head` 绕过预检和数据应用。

### 8.3 回退与恢复定义

- 空库 / 未应用数据迁移：验证 schema upgrade、downgrade、再次 upgrade 的支持边界。
- 已经合并的非空库：不通过简单 downgrade 拼接绝对路径冒充原库；不支持的降级必须明确拒绝，归档与别名不能丢失。
- 数据恢复：将切换前完整备份恢复到隔离数据库，核对原 UUID、路径、候选、草稿、会话、产物版本及其他受保护数据，验证旧版本应用能读取。记录实际 `pg_dump` / `pg_restore` 或等效命令、工具版本和结果；不要只验 JSON 可反序列化。
- 切换后新数据：切换前备份不会包含它们。恢复业务后发生故障应先评估向前修复与增量保全，不能自动覆盖新数据。
