# E3 代码审查问题清单：契约漂移与改进建议

> 生成背景：E3（编排与服务）S3.0–S3.10 全部完成后、E4（可观测与交付）开工前，对 api/、tasks/、core/、services/、workflows/、serve.py、probe.py 扩展等做整体代码审查（只读审查）。验证基线：单元 639 + 集成 95 全过、ruff 零告警、mypy strict 41 文件零问题、Walking Skeleton 真实跑通。
> 总体结论：无新的代码级严重缺陷；本清单收录 **1 项契约漂移（MaterialSummary 丢 keyframes 字段）与 6 项改进建议**。端到端成本超标问题（0.09–0.12 元 vs 目标 ≤0.05 元）属独立决策，另行处理，不在本清单。
> 代码与契约文档尚未按此修改。

## 一、严重问题：MaterialSummary 契约漂移（keyframes 字段已声明但实现丢弃）

`docs/contracts/openapi.yaml` 的 `MaterialSummary` 声明了 `keyframes` 字段，但 `src/xhs_agent/services/runs.py` 的候选素材投影（`_matches_by_run_hotspot`）只带 `id / path / type / title / description / tags` 六个字段——**实现与契约不一致**，项目自己的纪律是「两者不一致视为未完成」。直接后果是报告 HTML 里关键帧缩略图渲染不出来（`<img>` 数为 0，显示「无预览」占位），尽管 `runs/_index/keyframes/` 里确实有关键帧文件。

backlog 风险表目前把它与「图片引用方式待决策」捆在一起搁置到 E5 前。**建议拆开处理**：

| 部分 | 性质 | 处置 |
| --- | --- | --- |
| 字段补齐：候选投影加 `"keyframes": list(material.keyframes or [])` | 一行改动，无决策依赖 | **立即修**——契约漂移每多活一个 Epic 周期，S4.6 的契约一致性校验（计划进 CI）都会撞上它 |
| 图片怎么渲染：内联 base64 / 新增取帧接口 / 渲染时复制到报告目录 | 独立产品与技术决策 | 维持 E5 前决策不变 |

捆绑搁置的代价：API 响应缺字段会让前端（E5）按契约生成的类型拿到 `undefined`，届时排查成本远高于现在补一行。

## 二、建议改进（6 项，按优先级）

| # | 位置 | 问题 | 建议 |
| --- | --- | --- | --- |
| 1 | `tools/vision.py`（urllib 同步） | S3.5 显式裁剪时它的调用方是脚本路径，阻塞无碍；**现在是长驻 Celery worker 的 async 上下文**（`sync_materials` 里打标一条素材阻塞事件循环数秒）。`tools/http.py` 基建已就绪 | E4 前重评这条裁剪：迁 httpx 约半天，或用 `asyncio.to_thread` 包一层临时兜底 |
| 2 | `services/runs.py submit_analysis` | **enqueue-before-commit 竞态**：broker 消息先出、事务后提交，worker 若快于 commit，`load_job` 查无此 job → 任务空转一次并告警。当前只处理了「enqueue 失败回滚」，反向窗口未覆盖 | 先 `commit` 再 `enqueue`，投递失败时删 run 行（补偿事务）；或 worker 端对「job 不存在」做 1 次短重试（sleep 0.5s）。概率低，修法便宜 |
| 3 | `tasks/`（无 stale-run 对账） | 已知边界「worker 崩溃吞任务（`acks_late=False`）会让 run 停在 running」与**硬超时 SIGKILL**（soft 600s 的 `mark_failed` 来不及跑时）同族：极端情况下 run 永远 `running`，前端轮询永不到终态 | 轻量对账：worker 启动时（或 `beat` 定时）把 `running` 且 `started_at` 超过 `task_time_limit_s × 2` 的 run 标 `failed`。E4 可观测时一并做 |
| 4 | `workflows/analysis.py:296` | `status = "succeeded" if not errors else "failed"`——10 个热点成功 1 个失败，整 run 记 `failed`。`run_hotspots` 有细粒度状态兜底，但**批次成功率的统计口径**会失真（E5 前端「运行历史」将直接展示） | 接受现状则在数据契约 §3.3 注明「failed = 任一热点失败」；不建议现在引入 partial 状态（契约 + 前端联动改动大） |
| 5 | `api/routers/ops.py` vs openapi 契约 | 契约写「逐项返回……**模型服务**的可用性」，实现只查配置不发请求（理由正当：烧钱 + 抖动误判，与 probe 口径一致）。文字与实现有歧义 | 改契约描述为「模型配置就绪性」——一行文档修订，消除 S4.6 契约校验的潜在摩擦 |
| 6 | `api/deps.py` | `get_engine` 的 `lru_cache` 引擎无 shutdown 清理钩子。本地进程退出无碍；E4 容器化 SIGTERM 优雅停机时应关闭连接池 | E4 接入时在 lifespan 的 `yield` 之后加 `await get_engine().dispose()`（顺带处理 `get_config` 的 cache_clear） |

## 附：处置建议

1. **立即**（无依赖、零风险）：S2 的字段补齐（一行）+ 建议项 5（契约一行）——合计十分钟内完成，消除两处契约漂移。
2. **E4 开工时打包**：建议项 3（stale-run 对账）与 6（连接池 dispose）天然属于 S4.1（structlog + run_id 贯穿）与 S4.4（全栈 compose）的范围；建议项 1（vision 异步化）可在 S4.4 容器化冒烟前顺手完成。
3. **随手修**：建议项 2（投递顺序 + 补偿）改动小、独立，任一时间点插入即可。
4. **仅文档**：建议项 4 在数据契约补一句口径说明即可。
