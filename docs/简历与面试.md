## 一、简历项目条目（主版本）

**小红书热点搭子 · 热点相关性 Agent**（个人项目 · 独立设计并实现）
技术栈：Python / FastAPI / Pydantic v2 / LangGraph（状态图 + 工具循环）/ 原生 function calling + SSE 流式 / PostgreSQL + pgvector / SQLAlchemy + Alembic / Redis + Celery / Vue 3 + Vite + TypeScript / Naive UI + ECharts / Docker + GitHub Actions / Langfuse + OpenTelemetry / 大模型结构化输出与失败自修 / 混合召回

面向创作者“热点来了、素材找不到”的时间差问题：热点窗口期只有 24–48 小时，而创作者花在“翻素材”上的时间常常超过拍素材本身。设计并实现一个本地可部署的 AI Agent，输入热点后自动拆解爆点要素，在个人素材库中检索可用镜头，输出带匹配理由的候选素材与文案初稿。

- 设计 9 类爆点要素模型，把热点的“火因”拆为可迁移要素与不可直用要素，通过配置化权重实现“借势不直用”（人物 IP 权重压到 0.4），规避肖像权与代言暗示风险。
- 相关性检索采用确定性加权算法（要素类型权重 × 置信度 × 相似度），并叠加 pg_trgm 字面召回与 pgvector 语义召回的混合检索（RRF 融合）；排序环节不交给大模型，结果可复现、每条候选可复算，成本不随素材量增长。
- 接入多模态模型对素材抽帧打标，素材索引按“路径 + 修改时间 + 大小”增量更新，重复运行不重复付费。
- 编排层用 LangGraph 状态图实现，每步可重试、可上报进度；每次运行的 token、成本与延迟经 Langfuse 与 OpenTelemetry 落库，按 run_id 全链路可回放。
- 对话式入口把整条流水线外放为工具集：LangGraph supervisor ⇄ 工具循环（6 个工具）+ 原生 function calling + SSE 流式，模型只决定“调不调、调哪个”，**不介入检索与排序**；工具选择回归两臂 100%、越界改写拒绝 3/3。
- 自建 20 组标注评测集并与纯关键词基线做两臂对照，把这套口径固化成可重复的回归脚本；单次分析成本实测 0.0926 元（门槛 ≤ 0.15 元/热点）。
- 前端用 Vue 3 + Vite + TypeScript 构建单页应用（对话首页／分析台／结果详情／运行历史／素材库五个页面），接口类型由 OpenAPI 契约自动生成，契约变更在编译期即暴露。

## 二、精简版（版面紧张时用）

- 独立设计并实现热点相关性 Agent：热点拆解 → 私有素材库检索 → 文案初稿，全链路可复现、可解释；对话式入口（6 个工具 + 原生 function calling + SSE）已端到端跑通。
- 用确定性加权 + 混合召回（字面 + 向量）替代大模型排序，成本与素材量解耦；排序结果可复现、每条候选可复算。

## 三、电梯陈述（30 秒口述版）

> 这个项目解决的是创作者一个很具体的时间差问题：热点只有一两天窗口期，但素材库几百上千条、命名混乱，找素材的时间比拍素材还长。
> 我做的工具是把热点拆成九类“爆点要素”，再把其中能做和不能做的分开——比如明星打羽毛球这个热点，明星本人不能用，但羽毛球、球场、慢动作这些可以复刻；然后在用户自己的素材库里按要素做相关性检索，给出候选镜头、命中理由、缺什么素材，最后配一版文案初稿。
> 关键设计是排序不用大模型、用确定性算法，所以结果可以复现也可以评测；编排用 LangGraph 状态图显式化，每一步都可追踪、可重试；整条链路跑在 FastAPI 与 PostgreSQL(pgvector) 上，`docker compose up` 一条命令起全栈。

## 四、高频追问与回答要点

### Q1 这不就是一条 if-else 流水线吗，凭什么叫 Agent？

四个点：**开放文本的要素拆解决策**（拆什么、拆几个、给多少权重，没有固定规则）、**失败自愈**（结构化输出解析失败时把错误回灌给模型要求自修重试）、**显式状态机与全链路追踪**（LangGraph 状态图编排，节点级重试，token／成本／延迟按 run_id 落库可回放）、**工具选择与多步决策**（对话层是最外层的 supervisor ⇄ 工具循环：模型自己决定直接回答还是调工具、调哪一个，工具结果回来再决定下一步）。

重点讲第二条和第四条，因为这两条最能区分“Agent”和“提示词加正则”：普通实现遇到模型输出格式错误就直接崩了或在报告里显示乱码，这里的实现是带着错误信息重试，并且把每次尝试都记进运行轨迹；普通实现也不能在“跑完整分析 / 查素材库 / 读历史结果 / 只看要素拆解 / 改写文案”之间自己选。

**被追问时的诚实边界**：断点续跑**没做**——重跑同一个 run 会重跑所有热点（只保证写回幂等）；进程被杀后的陈旧 `running` 行靠 worker 启动时的对账标成 `failed`，不续跑。这条主动说出来比被问出来好。

### Q2 为什么用大模型拆线索，却不用它排素材？

三个理由：**不稳定**（同样输入两次结果不同）、**不可复现**（自己和别人都无法复算，也就无法评测）、**成本随素材量线性增长**（一千条素材就是一千次调用）。

招聘方真正想听的是后面半句：检索必须确定性，评测才有意义。把模型放在“判断”的位置（拆解、解释、撰稿），把“检索”留给算法，是成本和可信度的共同要求。

### Q3 “为什么能火”这类结论会不会是模型胡说？

分两层看。要素拆解由模型产出，但每个要素都必须带 `evidence` 字段说明依据，没有依据的输出过不了结构校验。匹配分数由算法产出，可以手算复算。

再补一句：评测集里对“要素拆得是否合理”有人工判定，所以不是模型自己说了算。

### Q4 为什么不做“没有密钥也能跑”的降级设计？

这是一个主动取舍。降级版本要用规则引擎替代模型，产出质量差一个档次，一旦被当成“正常模式”使用，反而损害可信度；同时它要求业务代码长期维护两套实现路径，测试与维护成本都翻倍。

我选择把边界画清楚：缺密钥、连不上数据库或队列时**启动即失败并给出明确报错**，而不是静默降级到一个结果不可信的模式。演示时我带上自己的密钥，`docker compose up` 一条命令起全栈——靠的是可部署性，不是降级。

### Q5 20 组用例怎么来的，指标怎么算？

自建标注，覆盖明星运动、节目影视梗、节日节气、生活方式、职场五类场景共 20 组；每组由人工标注哪几条素材算正确答案。

- Top-5 命中率：前 5 条候选里至少有一条是正确答案的比例。
- 首选命中率：排名第一的候选就是正确答案的比例。
- 线索覆盖度：被素材命中的线索要素权重之和 / 全部线索要素权重之和。

标注与调参分离，避免“自己判自己”。基线是纯关键词子串匹配，用同一批用例跑，输出提升幅度。

### Q6 用户没有素材库，冷启动怎么办？

素材打标有三层兜底：人工旁车文件（最准）→ 文件名分词 → 多模态模型看画面自动打标（最省事）。另外我准备了一份示例素材包，可以零配置跑通。

补一句产品的看法：素材少的时候，报告里“覆盖缺口”那一栏本身就是价值——它会告诉你为了能蹭上这类热点，你该补拍什么。

### Q7 蹭明星热点，你怎么避免侵权？

产品层做要素分层：人物 IP 类要素权重压低，并强制转换为“同款动作 / 原型 / 平替”这类表述，报告中不出现姓名，也不建议文案里使用；声音类要素单独标注版权风险。

这个设计的价值在于：**用户不需要自己判断哪部分能蹭，系统已经把能蹭和不能蹭分开了。** 同时明确输出的是相关性建议、不构成法律意见，责任边界写在报告里而不是埋在免责声明里。

### Q8 素材库到十万条会怎样？

打分是纯文本匹配，单次遍历十万条在秒级到十秒级量级；真正的瓶颈在建索引，而索引是增量的，只有新增和修改的素材才重新打标。

召回侧**已经**是双通道（pg_trgm 字面 + pgvector 余弦 + RRF 融合），所以再往下要动的是"索引结构与参数"，不是"把向量加进来"：十万条量级下 `pg_trgm` 的 GIN 索引选择度、HNSW 的 `ef_search`、以及 `recall_limit` 的截断位置才是决定因素。面试里把这个回答清楚比提前做优化更有说服力——说明知道瓶颈在哪，也知道现在（几百到几千条）不需要动它。

### Q9 这个项目最大的取舍是什么？

**把“写文案”降级成副产品。** 写文案是红海，平台自带工具就能做，而且用户真正卡住的不是写不出来，是手里有什么能拍。

选择做“热点 × 私有素材库”这个交集，代价是用户得先有一个素材库（冷启动门槛高），换来的是别人抄不走的差异点：大模型看不到你的硬盘。

### Q10 如果重做一次，你会改什么？

**先做评测集，再做功能。** 打分函数改了很多轮，每轮都靠感觉判断有没有变好，效率很低；如果一开始就有 20 组标注用例，调参会快得多。

这也是我后来把评测写进方案的直接原因——它不只是一个验证环节，而是调参依据。

### Q11 哪些是你自己写的，哪些用了现成方案？

自己写：爆点要素模型、相关性打分与混合召回算法、素材索引与增量策略、LangGraph 状态图编排、报告渲染、评测设计。

用现成：大模型接口（OpenAI 兼容协议）、ffmpeg 抽帧、多模态模型。取舍原则是——**核心判断逻辑必须自己掌握，通用能力不重复造轮子。**

### Q12 为什么不做自动抓热榜、不做一键发布？

两个理由。一是边界：这个工具的价值在“热点 × 我的素材”这个交集，热榜获取是公开信息，接进来不增加核心价值；发布环节涉及账号授权与平台风控，风险高且与定位无关。

二是工程判断：v1 先把手动输入的单条链路做扎实、做到可评测，比铺开三个半成品功能更有价值。这两项都写在路线图里，不是没想到，是排后了。
