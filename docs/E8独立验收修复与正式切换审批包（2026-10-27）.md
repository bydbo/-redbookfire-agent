## 4. 待批准的具体正式切换范围

只有最终质量门、固定镜像、隔离演练与独立复核全部通过后，申请以下一次明确授权：

1. 暂停 API 入口，排空 worker／队列，确认无在途任务、上传、回收站、索引或其他写连接；期间业务不可用。
2. 校验目标数据库身份、当前版本及批准影响。制作最终 `pg_dump -Fc`，记录 SHA-256，恢复到隔离库验证原业务值及旧版本读取。
3. 使用固定候选版本升级到 `0014`；生成最终计划并核对来源、数量和缺失分布，超出批准范围立即停止。
4. apply、精确核验，通过后升级 `0015`。不使用 Compose 自动升级抢先绕过此顺序。
5. API／worker／管理工具统一切至固定镜像，检查数据库身份、历史详情、报告、别名、缺失说明及符合内容证据的预览。
6. 恢复服务，保存正式执行记录和只读验收结果；完成后更新 S8.3／M13，放行 S9.2 的 E8 依赖。

真实素材始终只读，删除／恢复冒烟仅在临时素材和隔离栈完成。不新增付费模型请求。

**失败与恢复边界**：apply 失败整体回滚并保持停写；超出计划或核验失败不恢复不兼容服务。恢复旧正式备份须另行明确授权，并保全切换后的新增数据；schema downgrade 不等于数据恢复。`0015` 存在孤儿候选时拒绝 downgrade。收口后使用 verify 做审计，原 `0014` apply 计划因 schema 绑定不能在 `0015` 重放。
