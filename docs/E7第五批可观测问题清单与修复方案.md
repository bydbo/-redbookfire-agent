## 3. 详细问题与修复方案

### OBS-01：追踪上下文创建或收尾失败可能阻断业务

**位置与归因**

[core/tracing.py](../src/xhs_agent/core/tracing.py)：`LangfuseTracer.turn/tool/node` 约 400–429 行、`generation` 约 323–332 行、`TracingProvider.complete_with_tools` 约 615 行。新门面由 cb28a88 引入、60de74d 接入运行路径。旧 generation 已有相同模式，不是本批首次出现。

**触发、证据与影响**

SDK 创建观测或进入上下文失败时，异常发生在业务块之前；退出失败也未统一隔离。现有保护主要覆盖初始化、更新和 flush。注入 `SDK_START_FAILED` 后，业务块没有执行，错误向外传播。对话兜底分支还会用同一 tracer 再建 turn，可能再次失败。

旁路故障因此可能导致模型 / 工具未执行或整轮失败；业务已成功时，SDK 收尾错误也可能改变最终结果。

**修复方案**

1. 在追踪门面内部统一实现安全观测上下文，覆盖创建、进入、更新、退出和导出，调用点不重复写兜底。
2. 建观测失败时使用空观测继续业务；业务块只能执行一次，禁止捕获整个 with 后重跑业务。
3. 分开处理业务异常与 SDK 异常；SDK 清理不得覆盖原业务异常，也不能吞掉取消等控制异常。
4. 创建成功后尽力恢复上下文和结束观测；故障日志遵循 OBS-02 的安全载荷规则。
5. 一并检查旧 run/hotspot/generation，统一同类隔离行为。

**回归与验收**

- 对创建调用、进入、更新、退出、flush 分别注入失败；turn/tool/node/generation 均覆盖。
- 业务成功时执行一次、结果不变；业务失败时异常不变；取消按取消语义传播。
- 流式增量、工具参数和返回值与追踪关闭时一致。
- 失败兜底不能再次因追踪创建故障而崩溃。

### OBS-02：错误原文绕过正文采集开关

**位置与归因**

[core/tracing.py](../src/xhs_agent/core/tracing.py)：`complete_with_tools` 异常约 620 行、`_fill_generation`、`finish_turn` 约 468–469 行、`_apply_generation/_apply_span`。本批新增路径扩大旧 complete/finish_run 的同类问题。

**触发、证据与影响**

异常或 result.error 含用户输入、图片 / 素材路径、供应商错误正文时，代码直接写 status_message。合成错误包含 `SYNTHETIC_PRIVATE_TEXT /private/material.png`，capture=False 时假 SDK 仍收到完整文本。截断长度不等于脱敏，阶段 error_category 白名单也不能证明最终外发载荷安全。

**修复方案**

1. 定义统一安全错误投影，仅允许安全类别、状态码、尝试号和关联 ID；默认不用任意异常的 str(exc) 作为云字段。
2. 返回错误与抛出异常走同一投影，覆盖 generation/tool/node/turn/run。
3. 明确正文开关允许的字段；显式开启也不能发送凭据等禁止数据。
4. 核对当前 SDK / OTel 自动记录的异常消息、事件和堆栈，防止只清理手写字段却遗漏自动采集。
5. 检查外发 warning / exc_info 的数据边界，诊断尽量使用安全编码和关联 ID。

**回归与验收**

- 用合成哨兵覆盖用户原文、图片路径、素材路径和模拟凭据，断言最终导出载荷不含哨兵。
- 同时覆盖抛异常、返回错误、worker 失败和 SDK 自身异常。
- 采集关闭和显式开启分别验证；测试不用真实凭据或私密素材。

### OBS-03：失败快照矛盾，最终回复阶段边界失真

**位置与归因**

[services/chat_turns.py](../src/xhs_agent/services/chat_turns.py)：run_turn_task 约 379–389 行、_finish 约 439–456 行；[workflows/chat.py](../src/xhs_agent/workflows/chat.py)：supervisor_node 的流式输出和阶段。60de74d 无条件发最终回复阶段，e3e21b3 将其持久化，2b8f2e0 仅完善空快照保护。

**触发、证据与影响**

run_turn 返回 failed 后仍先写 final_reply/running，失败分支再原样保存快照。已复现数据库为消息 failed、阶段 final_reply/running；SSE 又发 final_reply/failed，事件与数据库不一致。错误事件 stage 固定为空，也丢失真实失败位置。

成功路径 final_reply 在正文已生成、流式回吐结束后才开始，测到的主要是写库 / 整理，不是回复生成耗时。

**修复方案**

1. 先按轮次结果分流；失败禁止无条件进入 final_reply，保留并终结真实失败阶段。
2. 用同一个终态快照生成消息字段与终端事件，包含阶段、尝试号、错误类别、最后完成节点及 trace。
3. 明确生成回复与持久化收尾的边界。final_reply 若表示生成，应覆盖实际生成区间；若只能区分模型决策调用与落库，应先调整契约和展示含义。
4. 对工具决策与最终正文共用一次流式模型调用的情况，定义调用区间和子事件，不靠事后补写虚构精确阶段耗时。

**回归与验收**

- supervisor 返回失败、工具失败后模型解释、最终模型超时、落库失败分别覆盖。
- 失败刷新后没有 running 当前阶段，失败位置准确，SSE 与详情接口终态一致。
- 正常流式阶段覆盖实际生成区间，落库时间不冒充生成耗时。

### OBS-04：异常路径重建业务入口，trace 未可靠落库

**位置与归因**

[services/chat_turns.py](../src/xhs_agent/services/chat_turns.py)：原 turn 约 371 行、异常分支约 393–406 行及 _mark_failed。60de74d 新增，后续未统一收尾。

**触发、证据与影响**

原 turn 内抛异常后，先退出原观测，再建同名 chat.turn 发送失败事件。无外部父上下文的假 tracer 复现 trace-1、trace-2；错误事件引用第二个，消息没有 trace_id。继承 HTTP 上下文时两者可能同 trace，但仍是同轮两个入口。

**修复方案**

1. 成功、返回失败、异常和取消在同一个业务入口生命周期内收尾。
2. 进入 turn 后获取可用 trace ID 并尽早保存；错误事件和写回复用已捕获关联，不依赖异常展开后重读上下文。
3. 原业务入口从未建立时可以留独立故障记录，但不能伪装成另一条完整轮次，也不能重跑已发生业务。
4. 失败写库尽力执行；数据库不可用时记录持久化缺失，不宣称已经保存。

**回归与验收**

- 正常、返回失败、模型 / 工具 / 写库异常均只有一个可识别的轮次业务入口。
- 消息、日志、SSE、worker 使用同一 turn_id；可持久化时 trace ID 一致。
- 无 HTTP 父上下文、继承 HTTP、两个会话并发分别验证。

### OBS-05：worker 阶段状态和重试信息丢失

**位置与归因**

[services/chat_tools.py](../src/xhs_agent/services/chat_tools.py)：_wait_for_run 约 825–845 行；[workflows/chat.py](../src/xhs_agent/workflows/chat.py)：tools_node.progress 约 160–171 行；[services/chat_turns.py](../src/xhs_agent/services/chat_turns.py)：persist/on_event 约 310–368 行。60de74d 转发名称，e3e21b3 将其合并进快照。

**触发、证据与影响**

轮询只比较 stage 名称、转发中文标签，worker 的 status/attempt/retries/error_category 未穿过回调，终态 job 在提取快照前返回。合成“draft 失败 attempt=1 → draft 运行 attempt=2 → report 成功”，仅转发“撰稿”和“分析中”。

对话 progress 固定 running，attempt 使用本轮同名工具执行次数，与 worker 重试号不同。切阶段又自动把上一个 running 标成功，无法忠实区分失败、跳过和重试。

**修复方案**

1. 扩展内部回调传递结构化快照，保留 run_id/job_id/call_id、阶段、状态、源尝试号、重试次数、错误类别和时间。
2. 按结构化变化合并；终态 job 的最后快照在返回前处理。重复轮询不重复追加节点或建 span。
3. 工具第几次调用、worker 第几次尝试、模型内部重试分字段或分层表达，不能代用。
4. 失败与 skipped 使用来源真实状态，只在来源能证明时推断上一步成功。
5. 当前 tool_finished 已携带 stage_key，应保留并接入统一合并；问题不是该字段完全缺失。

**回归与验收**

- queued、素材同步、回填、五节点、预置线索 skipped、同阶段重试均可区分。
- SSE、消息快照、任务详情对应状态一致；重试成功后仍可追查失败尝试。
- 快速阶段被轮询略过时如实标记观测缺失，不补造精确时间或成功记录。

### OBS-06：视觉调用没有完整 generation 追踪

**位置与归因**

[services/chat_tools.py](../src/xhs_agent/services/chat_tools.py)：_image_clue_for；[services/image_clue.py](../src/xhs_agent/services/image_clue.py)：单图约 92–97 行、多图约 147–153 行；[tools/vision.py](../src/xhs_agent/tools/vision.py)：实际视觉客户端。视觉路径为旧功能，但本批明确要求覆盖单图、多图及跨轮回落，属于验收缺口。

**现状与影响**

视觉请求直接走独立客户端，未经过文本 TracingProvider，也没有等价 generation。工具 span 与图片解析标签不能核对视觉模型、调用耗时、tokens、错误和成本。历史纯文本 trace 不能证明视觉链路覆盖。

**修复方案**

1. 在装配 / 服务边界为真实视觉调用增加等价 generation，保持 tools 依赖方向，避免适配器反向依赖业务编排。
2. 使用真实视觉模型与对应单价，保留供应商实际用量；缺字段明确未知。
3. 一组多图一次请求只记一个逻辑 generation；真实重试保留尝试事实及已知用量。
4. 缓存只记命中、数量和安全标识，不虚构 generation 或新增费用；跨轮引用默认不外发图片和附件路径。
5. 复用 OBS-01 / 02 的隔离和载荷规则。

**回归与验收**

- 单图、多图、跨轮回落、同轮缓存命中、失败、超时分别覆盖。
- 真实视觉请求可沿工具父子关系回看；模型调用数与命中次数可核对。
- 真云用包含视觉调用的新样本，不能以文本样本代替。

### OBS-07：用量完整性标记固定为真

**位置与归因**

[services/chat_turns.py](../src/xhs_agent/services/chat_turns.py)：_turn_totals 约 413–418 行；[core/tracing.py](../src/xhs_agent/core/tracing.py)：_fill_generation/finish_turn。60de74d 新增固定汇总，底层 usage_status 未可靠上卷。

**触发、证据与影响**

_turn_totals(ChatTurn(status="failed")) 仍返回 usage_complete=True。调用缺 usage 或失败结果没有累计账目时，父层可能继续宣称完整。零 tokens 不能区分真实零用量、没有调用和调用已发生但用量未知。

**修复方案**

1. 调用记录保留实际、估算、未知状态，根据调用集合计算完整性，不能仅依据轮次是否成功。
2. 区分已知 tokens 和按配置价格估算的成本，不能把估算称为实际账单。
3. 聚合已知部分，单列未知 / 估算调用数或等价信息；新增公开字段先更新契约。
4. 父 turn/tool/run 只展示汇总，核账仅加可计费叶子，不跨层相加。
5. 没有取得调用结果的中断保留未知；结合 OBS-10 保存已知部分，不清零后宣称准确。

**回归与验收**

- 全实际、部分估算、部分未知、失败前已消费、无模型调用分别断言。
- 重试、多图和缓存无重复计费；消息汇总与 trace 汇总不重复累加。

### OBS-08：真云核对脚本误通过与口径不足

**位置与归因**

[scripts/check_trace_chain.py](../scripts/check_trace_chain.py)：verify_trace、trace_wall_ms、has_usage/has_cost/is_unknown_usage。2b8f2e0 新增。

**已确认问题**

1. no_cost 只拼说明，判定仍用 not missing；移除样本全部 generation 成本后“叶子用量”仍通过。
2. 只检查已出现 generation，不核对场景预期调用；缺视觉请求或漏导出可能不被发现。
3. 主要检查字段存在，没有把已知叶子 tokens / 成本与同口径消息汇总数值对账。
4. 耗时取整条 trace 最早开始至最晚结束；消息 latency_ms 在 run_turn 内计算，HTTP、准备、落库边界不同。2000 ms 容差不能证明同口径。
5. ERROR 可直接视为未知用量；错误状态不能替代 usage 完整性声明，字段非空也不保证数值有效。

**修复方案**

1. 明确通过、失败、缺证据、场景不适用的语义；缺成本按规则失败或待验证，不能只写说明。
2. 对样本提供预期清单：入口唯一、工具、真实视觉 / 文本调用、worker 节点、缓存 / skipped 例外；以调用标识匹配，不绑定自然语言。
3. 校验叶子字段类型、非负值与已知 / 未知关系，允许真实零成本，不以非零作为唯一存在判断。
4. 按同轮次、同计费边界对账 tokens 与估算成本，单列未知覆盖率，不伪装完整账单。
5. 选明确的业务入口区间或统一起止边界，区分 HTTP / 轮次 / 模型耗时；容差只解决精度。
6. 检查断父级、重复入口、跨 turn 子树、导出未齐全；延迟用有界重试和明确待验证状态处理。

**回归与验收**

- 删除成本、删除预期视觉调用、错 parent、重复 turn、错汇总、HTTP 外层等待均能识别。
- unknown、真实零成本、缓存、不适用 worker 场景得到正确结果。
- CLI 文本 / JSON / 退出码一致，“缺证据”不能被机器视为完整通过。
- 旧“5 项硬核对全过”只代表旧脚本条件通过；修复后用新样本重验。

### OBS-09：实际取消没有统一持久化终态

**位置与归因**

[services/chat_turns.py](../src/xhs_agent/services/chat_turns.py)：run_turn_task 的 except Exception/finally；[workflows/chat.py](../src/xhs_agent/workflows/chat.py)：run_turn。未覆盖 asyncio.CancelledError 的行为基线已存在；本批承诺的取消收尾仍需补齐。

**触发与现状**

后台任务真正被取消时，可能只清理资源，消息仍 running。supervisor 发失败阶段也不能保证消息终态。TimeoutError 测试不等价于 Task.cancel() 验收。

**修复方案**

1. 浏览器 / SSE 断线只停转发，后台任务取消单独处理。
2. 捕获取消控制异常，在有界时间内尽力写消息 interrupted、阶段 interrupted、类别 cancelled，沿用合法枚举。
3. 写回、观测收尾和清理后重新抛出取消，不吞掉系统停机控制流。
4. 再次取消或数据库不可用时明确尽力边界，由 OBS-11 恢复机制兜底；进程强杀不能承诺 finally 执行。

**回归与验收**

- 真正 Task.cancel() 覆盖模型、视觉、worker 等待、写库、清理阶段。
- 有界结束、取消继续传播、日志上下文复位，数据库可用时没有永久 running。
- SSE 断开后后台仍正常落库，与真实取消分开断言。

### OBS-10：失败丢失已知用量和业务引用

**位置与归因**

[workflows/chat.py](../src/xhs_agent/workflows/chat.py)：run_turn 约 240–244 行；[services/chat_turns.py](../src/xhs_agent/services/chat_turns.py)：_finish 失败分支。主要行为在基线已存在，不是本批新回归；但本批要求失败已知用量与引用可查。

**触发与影响**

前面的模型 / 工具已成功，后续调用失败时返回空 ChatTurn，会丢失已知消费与调用记录；失败写回也未保存这些字段。真实请求已发出但无 usage 的情况还需保留“已尝试、用量未知”。

**修复方案**

1. 在稳定边界维护轮次内账目，完成一次模型 / 工具尝试即保留已知记录，不仅依赖图最终成功结果。
2. 失败结果带已知用量、工具状态、prompt 版本和 run_id；工具汇总与内部叶子不能双计。
3. 失败消息也保存已知字段，通过 OBS-07 标记未知 / 不完整。
4. 不强行引入完整事件溯源、通用恢复或整套 E10 幂等。若确需持久化账目，再按必要性更新契约和迁移。

**回归与验收**

- “模型成功 → 工具成功 → 第二次模型失败”保留前两段消费和引用。
- “请求发出但无 usage → 超时”保持未知，不伪造零消费。
- 失败 / 取消 / 重试汇总与可得叶子一致，不反向补造旧失败行的历史账目。

### OBS-11：创建时间不能单独代表活跃性

**位置与归因**

[services/chat.py](../src/xhs_agent/services/chat.py)：mark_stale_turns 约 375–401 行。基线已有 created_at 超时判定；本批只补了阶段中断。

**触发与现状**

创建超过 turn_stale_seconds 后，即使后台仍活跃、阶段近期更新，读会话也可能标 interrupted；后台稍后成功再写回，造成界面反复。来自明确筛选条件，尚未对真实长模型任务注入。

**修复方案**

1. 区分最大业务时长、多久无活动、进程重启失去执行者，不能用创建年龄代替三者。
2. 阶段更新时间只作为一个信号，长模型调用和排队期间可能不切阶段。
3. 复用执行登记、worker/job 状态或有界租约 / 心跳，不逐 token 写库；多 API 进程不能只看当前进程内存断言执行者消失。
4. 对账条件写入，避免覆盖刚完成终态；旧行缺活跃信息时使用明确兼容策略。
5. 判定规则涉及公开配置 / 数据语义时先改契约，新增字段按实际需要决定。

**回归与验收**

- 创建很早但活跃、无阶段变化长调用、worker 排队、执行者消失、正常成功、并发对账分别覆盖。
- 刷新不误判活跃轮次；执行者消失后按约定收敛。
- 使用可控时钟，不靠真实等待数分钟验证。

### OBS-12：迟到开始事件回退状态，执行身份不足

**位置与归因**

[core/progress.py](../src/xhs_agent/core/progress.py)：begin/end/apply 约 148–221 行；[前端对话 store](../frontend/src/stores/chat.ts)：applyProgress。属于本批状态机。当前契约按 (stage, attempt) 去重，并要求旧尝试不覆盖新状态。

**已复现与风险边界**

- draft/attempt=2 运行中再输入 attempt=1 的 begin，尝试号回退为 1。
- draft/attempt=2 已 succeeded 后再输入相同尝试的 begin，回到 running。
- end 只在部分路径阻止旧尝试，begin 缺少对应保护。
- 同轮不同工具 / 分析执行共用 (stage, attempt) 还存在身份冲突风险；该场景需专门集成复现，不当作已发生串线。

**修复方案**

1. 统一定义迁移规则：同一执行 / 尝试终态不因重复 begin 重开，更高尝试才能启动新阶段。
2. 开始、进度、结束全部检查迟到事件，必要时用来源版本 / 序号辅助有序合并。
3. 明确身份是否应包含 call_id/run_id/job_id、热点执行标识。变更去重键前先改数据 / API 契约并兼容旧快照，不能只在前端另造规则。
4. 后端持久化和前端实时合并规则一致；工具次数与 worker 重试次数分层。

**回归与验收**

- 顺序、重复、乱序、旧尝试迟到、新尝试启动全部断言。
- 同尝试终态不重开，旧事件不覆盖新状态，失败尝试不因成功重试被抹去。
- 同轮两个分析、多个热点同名节点、两个会话并发保持身份隔离。
